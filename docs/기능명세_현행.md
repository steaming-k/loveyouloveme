## 1. 제품 정의와 데이터 위계

### 1.1 한 문장

> 상대를 사랑하는 과정에서 **나에 대해 더 깊게 이해하고**, 나를 사랑하는 방법을 알아가는 서비스.
> 궁합은 시작점이고, **관계 속의 나를 보는 것**이 핵심이다.

궁합 점수는 **입구이지 결론이 아니다.** 제품의 Aha Moment는 "이 사람과 잘 맞는다/안 맞는다"가
아니라 **"내가 말한 나와 관계에서 나타난 내가 다르다"**는 발견이다.

### 1.2 캐릭터 — 러비(Lovy)

인간의 사랑을 관찰하러 온 외계인. 역할은 **관찰자**이며 상담가·점쟁이·전문가가 아니다.

| 쓴다 | 쓰지 않는다 |
|---|---|
| `~인가 봐` · `~일 수도 있겠네` · `~구나` | `당신은 ~한 사람입니다` |
| `실제로 그런지는 확인해봐` | `이 관계는 성공할 확률이 78%입니다` |
| `없는 건 없다고 할게` | `심리학적으로 ~` · `천생연분` · `상극` |
| `이건 아직 잘 모르겠네`(혼잣말 자리) | `헤어져야 해` · `너는 회피형이야` |

### 1.3 데이터 위계 — **점수에 들어가는 것은 단 하나**

```
CORE          실제 관계 행동 신호 4축        →  동기화율 계산에 들어간다
              (연락 · 갈등 해결 · 개인 시간 · 애정 표현)
   ↓
SUPPORTING    MBTI                          →  대화 포인트만. 점수 미반영
   ↓
ENTERTAINMENT 사주 · Astrology               →  참고 렌즈. 점수 미반영
   ↓
RETENTION     Relationship History           →  변화 기록. 점수 미반영
   ↓
PREMIUM       Deep Report                    →  관찰 사이의 연결. 점수 미반영
```

> **동기화율(Sync Rate)은 관계 행동 신호 4축만으로 계산한다.**
> MBTI·사주·별자리·History·Premium은 **어느 것도** 점수·`comparedCount`·`TARGET_MIN_KNOWN`
> 판정에 합산되지 않는다. 이건 구현 디테일이 아니라 **제품 원칙**이다 — 근거 없이 판정하지
> 않기 위해서다.

### 1.4 정보 위계 — 4단계 읽기 깊이 (v1.23)

결과 화면의 모든 정보는 **사용자가 그 답을 원하는 시점**으로 분류한다.
같은 정보를 여러 Level에서 반복하지 않는다.

| Level | 시간 | 사용자의 질문 | 담는 것 |
|---|---|---|---|
| **LEVEL 1** | 5초 | 그래서 우리 관계는 어떤데? | 동기화율 · **핵심 한 문장** · 러비의 의문 · YOUR SIGNAL |
| **LEVEL 2** | 30초 | 왜 그렇게 나왔는데? | 잘 맞는 신호 · 확인이 필요한 신호 · 근거 · LOVY OBSERVATION |
| **LEVEL 3** | 1~3분 | 그래서 우리가 뭘 해볼 수 있는데? | 다가갈 때 · 이야기해볼 질문 |
| **LEVEL 4** | Deep | 이 신호들이 서로 왜 연결되는 건데? | Premium Deep Report |
| (보조) | — | 다른 관점으로는? | Lens — Core·Action 뒤 |

이 구조는 **Compatibility Result(S21R)에 실제로 적용돼 있다**(§6 S21R).
Typography도 이 4단계에 대응한다(§4.13).

### 1.5 절대 규칙 (전 버전 공통)

| # | 규칙 |
|---|---|
| 1 | **근거 없이 판정하지 않는다.** 수집하지 않은 데이터를 계산에 넣지 않는다 |
| 2 | **AI는 판정을 만들지 못한다.** 규칙이 판정하고, AI는 그 판정을 근거와 함께 설명만 한다 |
| 3 | **못 한 것을 숨기지 않는다.** `limitations`를 화면에 그대로 나열한다 |
| 4 | **실패를 성공인 척하지 않는다.** demo/mock/fallback/real을 화면에서 구분해 말한다 |
| 5 | **상대의 마음을 읽지 않는다.** 사용자가 알려준 상대 정보만 쓰고, 성격·감정을 단정하지 않는다 |
| 6 | **무료에서 Core Value가 완성된다.** Premium은 제품 중심을 대체하지 않는다 |
| 7 | **연출 때문에 실제 처리를 늦추지 않는다.** motion은 presentation layer 전용 |

```

  ├─ S02~S04 온보딩 3단
  ├─ S05 관계 상태 선택

  │   S06 인트로 → S07 사진 → S08 분석 → S09 Observed Me ⭐
  │                                   → S10~S13 Declared Me (+ 내 MBTI)

  │                                   → S18 Relationship Profile ⭐
  │   ⚠️ S18은 세 Source를 **나열만** 한다. 아직 비교하지 않는다.
  │
  ├─ S19 상대 정보 입력 (4축 + 상대 MBTI + 좋아하는 것)
  ├─ S20 궁합 관찰 (LovyObservation 4단계)
  │

  │      #summary #why #good #friction #lenses #approach #questions
  │      ↑ 여기서 FIRST SURPRISE + YOUR SIGNAL (무료 Aha)
  │
  ├─ S26 Mirror Teaser ⭐  ←── 제품의 시선 전환점 (Primary KPI)
  │      "너와 그 사람"에서 "말한 나 vs 관계 속 나"로
  │
  ├─ S27R Relationship Mirror Result ⭐ ── "나는 관계에서 어떤 사람인가?"
  │      → 내 관찰 기록에 저장 → F3 Change Moment
  │
  └─ S29 분석 후 홈  ── Current Result Revisit 진입점
       │

       ├─ X1 러비의 다른 관측 렌즈 → X1-a MBTI / X1-b Astrology / 사주
       └─ P1 Premium Paywall → (현재 Fake Door) → Deep Report
```

### 2.1 두 Mental Model의 분리

제품에는 서로 다른 두 질문이 있고, **화면 전환은 질문이 바뀔 때만** 일어난다.

| Mental Model | 질문 | 화면 |
|---|---|---|
| **Compatibility** | 우리 둘은 어떻게 맞는가? | S21R (구 S21~S25 통합) |
| **Mirror** | 나는 관계에서 어떤 사람인가? | S27R (구 S27~S28 통합) |

같은 질문의 답을 읽는 동안에는 **한 화면에 머문다**(anchor 이동). 질문 자체가 바뀌는
순간(Compatibility → Mirror)에만 새 화면으로 전환하고, 그 사이에 S26 Teaser를 둔다.

### 2.2 자기 발견은 딱 한 번만 일어난다

S18(Relationship Profile)과 S26/S27R(Mirror)은 **서로 다른 코드 경로**를 쓰고 어느 쪽도
서로를 호출하지 않는다.

| 화면 | 함수 | 하는 일 |
|---|---|---|
| S18 | `buildRelationshipProfile()` | 세 Source를 **나열**. 판정 없음 |
| S27R | `buildMirrorReport()` | MATCH / GAP / CHANGE **판정** |

S18에서 미리 "말한 것과 실제가 다르다"를 말해버리면 S26의 Aha가 '이미 본 내용의 반복'이 된다.

### 2.3 Current Result vs History

| | Current Result | Relationship History |
|---|---|---|
| 데이터 | 세션에서 **매번 다시 계산**되는 순수 함수 | 저장된 **불변 Snapshot** |
| 저장소 | `localStorage['lym.session.v1']` | `localStorage['lym.history.v1']` |
| 진입 | `?view=revisit&source=...` | `/history` |
| 답을 주는 질문 | "지금의 나는?" | "그때의 나는 어땠지?" |

수정(Declared·Experience·Target)은 Current Result에만 반영되고, **History Snapshot은 다시
쓰지 않는다.** 새 Entry는 사용자가 Mirror를 다시 저장했을 때만 생긴다.

## 4. 전역 사양

### 4.1 레이아웃 골격 — `ScreenLayout`

모든 화면이 공유하는 3단 구조다.

| 영역 | 규칙 |
|---|---|
| **Header** (flex-none) | `ScreenHeader` — 뒤로가기(←) · progress bar(선택) · 카운터(`질문 1/4`) · 우측 액션(공유/수정) |
| **Body** (flex-1, scroll) | 좌우 여백 20px(`px-gutter`) 고정. `centered` 옵션이면 세로 중앙(스플래시·로딩·Empty·Error) |
| **Footer** (flex-none, sticky) | Primary CTA + 보조 액션. 하단 safe-area 26px |
| **Nav** (선택) | `BottomNavigation` — Post-analysis 화면에서만. footer와 겹치지 않고 아래에 쌓인다 |

> ⚠️ **스크롤 주체는 `document`가 아니라 Body의 `overflow-y-auto` 컨테이너다.**
> 이 컨테이너에는 `data-screen-scroll` 표식이 붙어 있고, 스크롤 위치 복원이 이 표식으로
> 컨테이너를 찾는다(§6 S21R · §4.9). 브라우저·Next.js의 native scroll restoration은
> document 스크롤만 되돌리므로 이 앱에서는 **원리적으로 동작하지 않는다.**

스크롤바는 전역 CSS(`* { scrollbar-width: none }`)로 숨기되 스크롤 동작은 유지한다.

### 4.7 관찰 시퀀스 — `LovyObservation`

분석 화면은 스피너가 아니라 **러비의 관찰 과정**이다.

```
OBSERVE  →  COLLECT  →  CONNECT  →  REPORT
관계 신호를   서로 다르게   신호들이      관찰 기록을
살펴보는 중   나타난 신호를  어디에서      정리하는 중
             모으는 중     이어지는지
```

| 항목 | 값 |
|---|---|
| 단계당 체류 | **1400ms** (`OBSERVATION_STAGE_MS`) |
| 총 시간 | `1400 × 4 + 500 = **6.1초**` |
| 시각 표현 | 인라인 SVG `ObservationField` — 신호 토큰이 모여 기록지가 된다 |
| 상태 텍스트 | 단계 코드 + 한국어 문장. **색·모션만으로 진행을 전달하지 않는다** |
| Reduced Motion | 4단계를 **목록으로 한 번에** 보여주고 1200ms 뒤 이동 |
| 실패 시 | E2 에러 화면 (`?error=1`로 재현 가능) |

> ⚠️ **연출 때문에 분석을 늦추지 않는다.**
> S08(사진)은 `연출 완료 && 실제 분석 완료` **둘 다** 만족해야 이동한다 — 실제 응답이
> 더 늦으면 마지막 단계에서 기다리므로 이 값이 대기를 늘리지 않는다.
> S20(궁합)은 순수 계산이라 이 시간이 그대로 **최소** 연출 시간이 된다.

### 4.8 승인된 줄바꿈 — `Lines`

한국어는 자동 줄바꿈 위치가 화면 폭마다 달라진다. 기획에서 "이 두 문장은 각각 한 줄"로
정한 카피는 CSS 흐름에 맡기지 않고 `Lines` 컴포넌트가 각 줄을 `block` `span`으로 그린다.

⚠️ `<br>`을 쓰지 않는다 — 스크린리더가 한 문단을 억지로 끊어 읽지 않도록 문장 단위
`span`으로만 나눈다.

| 화면 | 줄 1 | 줄 2 |
|---|---|---|
| F1 caption | 누구와 몇 번 만났는지는 기록하지 않아. | 네 기준이 어떻게 움직였는지만 남겨. |
| F1 변화 요약 / F2 Empty | 아직 비교할 과거 기록이 하나뿐이야. | 다음 관찰이 쌓이면 변화를 알려줄게. |

| 항목 | 규칙 |

| 저장소 | `sessionStorage['lym.scroll.v1:<key>']` — **스크롤 오프셋 숫자만**. 답변·사진·분석 내용 미포함 |

| 실패 내성 | 읽기·쓰기 전부 `try/catch` — sessionStorage가 막힌 환경(프라이빗 모드)에서도 앱이 죽지 않는다 |

### 4.12 Card Density 정책 (v1.23)

카드는 **정보가 독립된 객체일 때만** 쓴다. 문단을 구분하려고 카드를 만들지 않는다.

| 표현 | 쓰는 곳 |
|---|---|
| **CARD** (`rounded-card` + border) | 그 자체로 완결된 단위 — PRIMARY 신호 1개, PRIMARY 힌트 1개, 대화 질문 |
| **DIVIDER LIST** (1px `border-t`) | 같은 종류가 반복되는 목록 — compact 신호·힌트, Lens index |
| **SECTION** (`ReportSection`) | 번호 + hairline divider + 제목. 카드가 아니다 |
| **ANNOTATION** (`LovyNote`) | 러비의 생각. mint 좌측 rule |
| **EVIDENCE BLOCK** (`ReportEvidenceBlock`) | 근거·메타. neutral 좌측 rule |
| **INLINE TEXT** | 나머지 전부 |

**PRIMARY / compact 두 단계** — 같은 규격 카드를 3~4개 쌓으면 무엇을 먼저 볼지 사라진다.
대표 1개만 카드로 두고 나머지는 divider 행 + 한 단계 낮은 typography로 내린다.
⚠️ **정보를 빼는 것이 아니다** — 상황·근거·AI 설명은 compact에도 그대로 붙어 있다.

├─ birthProfile        BirthProfile              ← 선택. 사주·Astrology 공용
├─ legacyZodiac        ZodiacSign | null         ← v1.3 잔재. 읽기 전용
├─ deepAnswers         DeepAnalysisAnswer[]                   (Premium)
├─ share               { includeTargetInfo, includeDimensionScores }
├─ currentAnalysisMeta { funnelAnalysisId, updatedAt, ... }
└─ completed           { onboarding, observed, declared, experience,
                         profile, compatibility, mirror }
```

#### `TargetRelation` — 관계 맥락 (v1.22에서 2개 추가)

```ts
type TargetRelation = 'crush' | 'talking' | 'friend' | 'work' | 'intro' | 'unsure';
```

| 값 | 라벨 |
|---|---|
| `crush` | 알아가는 중 |
| `talking` | **썸 타는 중** |
| `friend` | 친구 |
| `work` | 같이 일하는 사람 |
| `intro` | 소개로 만남 |
| `unsure` | **잘 모름** |

> ⚠️ **계산 근거가 아니다.** 동기화율·4축 similarity·`comparedCount`·`TARGET_MIN_KNOWN`·
> Mirror·History 판정 어디에도 들어가지 않는다. 실사용처는 세 곳뿐이다.
>
> 1. `RelationshipHistoryEntry.context.targetRelation` (기록 metadata)
> 2. `target_profile_complete` 이벤트의 `relation` 속성 (**새 이벤트 아님**)
> 3. `buildCompatibilityContext`의 `targetRelation` — 지금도 항상 `null`을 보낸다
>    (상대 관계 맥락을 Provider에 넘기지 않는다)
>
> 그래서 옵션을 늘려도 점수가 바뀌지 않는다.
> `Record<TargetRelation, string>`(`TARGET_RELATION_LABEL`)이 라벨 누락을 컴파일에서 막는다.

**`잘 모름`의 의미 경계** — `unsure`는 '이 사람과 나의 **관계 이름**을 모르겠다'는 뜻이다.
'상대의 관계 행동을 모른다'와 혼동하지 않는다 — 그건 4축의 `x`(모름)가 담당하고, `x`만
`comparedCount`에서 빠진다. 관계 이름을 모른다고 점수에서 빠지는 항목은 없다.

**Migration** — 값을 추가만 했다. 기존 세션의 `crush`/`friend`/`work`/`intro`는 그대로
유효하고, `resetTargetContext()`는 `relation: null`로 초기화한다.

#### 왜 MBTI를 `declared` 안에 넣지 않았는가

`DeclaredPreference`는 사용자가 직접 표현한 **관계 기준**(연락 중요도·갈등 해결 방식)이고,
MBTI는 별도의 **Self-described Personality Lens**다. 두 데이터를 섞으면 MBTI가 관계 기준의
하나처럼 취급되기 쉬우므로 `answers.mbti`로 분리했다.

#### 제거된 축 — `talk` · `rhythm`

`TargetProfile`/`TargetAxisKey`/`AXIS_DEFINITIONS`에서 `talk`(대화 방식)·`rhythm`(생활 리듬)
축이 **완전히 제거**돼 있다. 예전에는 이 두 축의 '나의 값'을 사진 관찰 고정값(`talk=4`,
`rhythm=3`)으로 하드코딩해서 계산에 넣었는데 **사용자가 실제로 준 데이터가 아니었다.**
질문을 늘리는 대신 축 자체를 뺐다 — 그래서 S19도 6개가 아니라 **4개 필드**만 받는다.

### 5.3 `ObservedProfileResult` — 사진 분석 결과

```
PhotoObservation                     ← LEVEL 1. 사진 1장 = Provider 1회
├─ photoId
├─ scenes · activities · objects · environment   ObservedLabel[]
├─ evidenceSummary
└─ usable                            ← 흐리거나 판단 불가면 false
     ⚠️ 반복·occurrenceCount 필드가 **애초에 없다** — Provider는 사진 1장만 봤다

ObservedSignal                       ← LEVEL 3. 규칙이 집계한 결과
├─ category        'sports'|'outdoor'|'travel'|'food'|'cafe'
│                  |'culture'|'reading'|'pet'|'social'|'other'
├─ label · evidence[]
├─ photoIds        string[]          ← Evidence Provenance
├─ occurrenceCount number            ← **사진 장수가 아니라 서로 다른 장면 그룹 수**
├─ strength        'single'|'repeated'|'strong_repeated'
└─ hasDuplicateLikePhotos

ObservedProfileResult
├─ traits            AiObservedTrait[]   (최대 6개. 0개도 정상)
│   ├─ id · observation · confidence('low'|'medium'|'high')
│   ├─ evidence      ImageEvidence[]   ← 어느 사진에서 봤는지
│   ├─ evidenceText  string?           ← 샘플 세션용 서술
│   └─ signal        ObservedSignal?   ← **실제 분석 결과에만** 있다
├─ evidenceCoverage  { imageCount, usableImageCount, level }  ← **코드가 판정**
├─ observedState     ObservedAnalysisState?
├─ limitations       string[]          ← 못 한 것을 숨기지 않는다
└─ meta              AiAnalysisMeta
    ├─ mode          'real'|'mock'|'demo'|'fallback'|'legacy-demo'
    ├─ promptVersion · analysisVersion
    └─ inputFingerprint                ← 사진이 바뀌었는지 판단
```

#### `ObservedAnalysisState` — 7가지 상태를 구분한다

| 값 | 뜻 |
|---|---|
| `repeated_found` | Vision 성공 + 반복 신호 있음 |
| `single_only` | Vision 성공 + 단일 관찰만 (**No Pattern ≠ No Information**) |
| `no_observation` | Vision 성공했지만 쓸 만한 관찰이 안 나옴 |
| `insufficient_photos` | 분석에 쓸 사진이 부족 |
| `provider_failed` | Provider 실패 |
| `mock` | 개발용 mock |
| `demo` | Provider 미연결 |

**'분석 실패'와 '반복 없음'과 '데모 모드'가 같은 말을 하지 않는다.**

| 항목 | 내용 |
|---|---|
| 사진 원본 | **저장하지 않는다.** 분석 후 메모리에서 사라지고 관찰 결과와 `imageId`만 남는다 |
| 지문 변경 시 | 사용자 확인 상태(`observations`)를 **초기화한다** — 다른 사진의 확인을 재사용하면 거짓이 된다 |
| 구 세션 복원 | `mode: 'legacy-demo'`로 복원하되 **trait은 만들지 않는다**(v1.22) |

### 5.4 `RelationshipHistoryEntry` — 영구 기록

`SessionAnswers`와 **완전히 분리된** 영구 데이터다. 저장소도 다르다.

```
RelationshipHistoryEntry
├─ id                     string            (crypto.randomUUID)
├─ analysisId             string            분석 입력 지문 — 중복 저장 방지 키
├─ createdAt              string            ISO
├─ context
│   ├─ relationshipStatus RelationshipStatus | null
│   └─ targetRelation     TargetRelation | null   ← 관계 '맥락'만. 상대 식별 정보 아님
├─ profileSnapshot
│   └─ mbti               MbtiType | null   ← metadata 전용. 변화 판정에 쓰지 않는다
├─ declaredSnapshot       DeclaredPreference
├─ relationshipEvidence   { important, hardest, selfGap, adaptive }
├─ mirrorSnapshot
│   ├─ insights[]         { axis, state, declaredText, relationshipSignal }
│   └─ focusAxis          MirrorAxisKey | null
├─ coreInsight            { original, userCorrection, verdict }
└─ evidenceCoverage       Confidence
```

**저장하지 않는 것** — 사진 원본 · 상대 이름 · 상대 사진 · 상대 자유서술 원문 · 민감정보.
History의 주체는 '상대'가 아니라 **'나'**다. 그래서 `target`에서도 `relation`만 가져오고,
`experience.note`(자유서술)와 `photos`는 아예 스냅샷에 넣지 않는다.

| 항목 | 값 |
|---|---|
| 저장 키 | `localStorage['lym.history.v1']` (세션과 분리) |
| 접근 경계 | `historyRepository.ts`가 localStorage를 만지는 **유일한 지점**. 화면은 `useHistory()`만 쓴다 |
| 정렬 | 항상 `createdAt` 오름차순 (오래된 것 → 최신) |
| 손상 데이터 | 스키마가 안 맞는 항목은 복원 시 **조용히 버린다** — 깨진 기록으로 화면을 터뜨리지 않는다 |
| 항목 식별 | **분석 시점(날짜)으로만** 표시. 상대 이름·연애 기간·'몇 번째 관계'로 라벨링하지 않는다 |
| MBTI 변화 | **해석하지 않는다.** INFP → ENFP가 되어도 '관계를 통해 외향적으로 변했다' 같은 Insight를 만들지 않는다 |

| 헤드라인 | `repeated_found` → "사진에서 반복해서 보인 활동이야" · `single_only` → "사진에서 이런 장면이 보였어" · 그 외 → "사진에서 이런 모습이 보였어" |
| `single_only` 안내 | 목록 맨 위에 "같은 활동이 여러 번 반복해서 보이지는 않았어"를 먼저 말하고 **단일 관찰은 그대로 보여준다** — No Pattern ≠ No Information |
| 카드 구성 | **활동 이름**(`스포츠 관람·운동`)과 **반복 근거**(`사진 3장에서 비슷한 장면이 반복해서 보였어`)를 분리. 반복 횟수는 규칙이 센 값이라 활동 이름과 한 줄에 섞으면 단정처럼 읽힌다 |
| 사용자 검증 | 맞아 / 조금 달라(수정) / 분석 제외 |
| 수정 시트 | 러비의 **원래 관찰 문장을 함께 보여준다** — AI Original을 덮어쓰지 않고 `original`에 보존 |
| `limitations` | 분석이 못 한 것을 하단에 그대로 나열한다 |
| 금지 표현 | **'생활 패턴'을 쓰지 않는다.** 사진 몇 장으로 판정할 수 있는 것이 아니다 |

#### Stale 판정 (v1.22)

저장된 `analysis.meta.inputFingerprint`를 현재 `photoFingerprint(answers.photos)`와 대조한다.
지문은 사진 id와 순서를 모두 반영하므로 **한 장만 바꿔도** 값이 달라진다.

```
photosChanged =
  !photosGone
  && analysisFingerprint !== null
  && analysisFingerprint !== 'legacy'   // v1.5 이전 세션 복원
  && analysisFingerprint !== 'sample'   // 샘플 세션
  && analysisFingerprint !== photoFingerprint(answers.photos)
```

다르면 trait과 **예전 `limitations`까지 모두 숨긴다** — 예전 한계 문구가 현재 상태처럼
읽히면 안 된다.

**재현 경로:** 새로고침 → `deserialize()`가 `source:'upload'` 사진을 제거 → 샘플 사진이
남아 있으면 `photos.length > 0`이라 `photosGone`에 걸리지 않음 → Profile Revisit이나
Declared 1단계 back으로 이 화면에 재진입.

| Validation | 최소 1개 항목에 확인 또는 수정을 남겨야 다음으로 진행 |
| Analytics | `photo_observation_confirm` `{ category, strength, ai_mode }` · `observed_profile_complete` `{ confirmed, corrected, excluded }` |
| 다음 | `/profile/declared/1` (또는 `from=profile-revisit`이면 `/profile/result?view=revisit`) |

#### 핵심 한 문장 — `selectResultHeadline()`

LEVEL 1에서 '그래서 우리 관계는 어떤데?'에 답하는 **한 문장**이다.

```
score === null(E3)                 → null (이 화면은 LowConfidenceView로 빠진다)
friction[0] && good[0]             → "{good}에 대한 기대는 비슷해 보이는데, {friction}에서는 차이가 보여."
friction[0]만                       → "{friction}에서 두 사람의 답이 서로 다르게 나왔어."
good[0]만                           → "{good 상위 2개}에 대한 기대가 비슷해 보여."
전부 neutral                        → "아주 다르지도, 아주 비슷하지도 않은 신호들이야."
```

- **새 계산 0 · 새 AI 호출 0 · 랜덤 0.** 이미 규칙이 판정한 tone 결과의 **라벨만** 읽는다
- friction을 먼저 말한다 — 사용자가 먼저 알아야 할 것은 차이다
- good이 여러 개여도 **상위 2개까지만.** 4개를 나열하면 문장이 목록이 된다
- 모든 축이 neutral이면 **판정을 만들지 않는다**

#### FIRST SURPRISE + YOUR SIGNAL

무료 결과를 이해한 **직후**, 근거를 읽기 전에 한 번 나온다. Summary와 본문 사이.

| 요소 | 내용 |
|---|---|
| 목적 | "궁합 점수를 주는 서비스인 줄 알았는데, 관계를 보는 방식이 다르네" |
| variant `gap` | hook `잠깐. 숫자만 보면 놓치는 게 하나 있어.` (friction이 있을 때) |
| variant `alignment` | hook `궁합 점수가 높아도 확인은 필요해.` *(v1.22)* |
| **YOUR SIGNAL** | 그 관찰이 **이 사용자의 어떤 답에서 나왔는지** 한 줄 |
| CTA | `실제 관계 신호 보기 ↓` — **무료 본문**으로만 내려간다 |
| 금지 | Premium 광고가 아니다. 가격·잠금·결제 CTA를 넣지 않는다 |
| E3에서는 | **표시하지 않는다** — 관측 정보가 부족한데 사람에 대한 생각을 지어내지 않는다 |

**YOUR SIGNAL 생성 규칙** — 이미 계산된 `CompatibilityResult`에서만 파생된다.

```
근거 축 = frictionSignals[0] ?? goodSignals[0] ?? 비교 가능한 첫 축
tone 'watch' → "{label}에서는 두 사람의 답이 서로 다르게 나왔어. (나: X · 상대: Y)"
tone 'good'  → "{label}에 대해서는 둘이 비슷하게 답했어. (나: X · 상대: Y)"
그 외        → "{label}은 아주 다르지도, 아주 비슷하지도 않게 나왔어. (나: X · 상대: Y)"
비교 가능한 축이 없으면 → null (렌더하지 않는다)
```

**새 계산 0 · 새 AI 호출 0 · 랜덤 0.** 같은 결과면 언제나 같은 문장이다.

#### 조합 패턴 (`lib/logic/mbtiPattern.ts`) — v1.25 P3-2

**왜 만들었나** — P3-1 배포 후 실사용 피드백이 **"구조는 좋아졌는데 정보가 적다"** 였다.
4축 표는 글자 위치만 보여줬고, 러비의 한 줄 관찰은 그 표를 문장으로 옮긴 것이라 새로
얻는 게 없었다. **축 설명을 늘려서 채우지 않고**(MBTI 교육 페이지가 되면 실패다),
무료가 반드시 세 가지를 주도록 블록을 신설했다.

⚠️ 이 모듈은 `CompatibilityResult`를 **import조차 하지 않는다** — 관계 답변을 억지로
MBTI와 연결하지 않는다. 관계 신호와의 대조는 아래 Bridge의 일이다.

**① 조합 패턴 — 궁합표가 아니다**

유형쌍(INFP × ESTJ)마다 문장을 두면 그 순간 궁합 사전이 된다. 그래서 **4축 같음/다름이
만드는 구조**만 읽는다. 축 묶음은 MBTI 자체의 표준 구분을 그대로 쓴다:

- **INNER** 정보를 받아들이고(S/N) 판단하는(T/F) 과정
- **OUTER** 에너지를 회복하고(E/I) 생활을 조직하는(J/P) 리듬

| 패턴 | 조건 | 이름 |
|---|---|---|
| `all-same` | 4개 같음 | 네 축이 모두 같은 쪽 |
| `all-different` | 0개 같음 | 네 축이 모두 다른 쪽 |
| `inner-same` | INNER 둘 다 같음 + OUTER는 아님 | 판단은 비슷한 쪽, 리듬은 갈리는 쪽 |
| `outer-same` | OUTER 둘 다 같음 + INNER는 아님 | 리듬은 비슷한 쪽, 판단은 갈리는 쪽 |
| `mixed` | 그 외 | 축마다 갈리는 쪽 |

**상호 배타적이고 256개 조합 전부를 덮는다** (같음 3개는 구조상 `mixed`가 될 수 없고
INNER/OUTER 중 한쪽으로 반드시 떨어진다). 각 패턴은 `body`(2~3문장) + `watchFor`(한 줄)를 갖는다.

**② 러비의 심리/철학적 관찰** — 패턴당 하나, `MBTI_PATTERN_OBSERVATION`.
관찰 대상은 **인간 일반**이지 이 사용자가 아니다. 진단·애착유형·트라우마·감정조절 추론 금지.
문장은 늘 러비가 아직 모른다는 데서 끝난다.

**③ 확인해볼 질문 1개** — 새 질문 데이터를 만들지 않고 `MBTI_AXES[].question`을 쓴다.
고르는 규칙(고정): 갈린 축이 있으면 축 정의 순서상 첫 번째 갈린 축, 없으면 첫 번째 축.
`why`가 갈린다 — 갈린 축은 *"실제로도 그런지는 물어봐야"*, 같은 축은
*"같은 글자가 같은 뜻인지는 물어봐야"*. **답을 예측해서 말하지 않는다.**

> **v1.25 Audit — 축 질문의 층위 교정**
> `MBTI_AXES[].question`은 두 사람의 글자가 **다를 때만** 노출된다. 그래서 질문이 특정
> 연애 행동을 지목하면 "너희가 이 축에서 다르니 그 행동도 다를 것"이라는 **예측이 질문의
> 형태로** 숨어든다. 두 개를 축 층위로 되돌렸다.
> - `lifestyle`: "데이트 계획은 미리 정하는 게 좋아…" → "일정을 미리 정해두는 게 편한 편이야…"
> - `decision`: "서운한 일이 있을 때 어떤 반응을…" → "중요한 걸 정할 때, 어떻게 하는 게 맞는지를…"
>   (후자는 P3-1에서 Bridge 매핑으로는 이미 기각한 T/F ↔ 갈등 대응을 질문에서는 그대로 하고 있었다)
> **id · 개수 · 순서 · tag · 저장/공유 동작은 그대로다** — 바뀐 것은 문장뿐이다.

#### MBTI × Relationship Signal Bridge (`lib/logic/mbtiBridge.ts`)

**새 점수를 만들지 않는다.** 이미 계산이 끝난 `CompatibilityResult`(tone 판정)와
`MbtiLensReport`(축별 같음/다름)를 **읽기만** 하는 presentation layer 비교다.

3개 층으로만 말한다: `MBTI 렌즈` → `네가 답한 관계 신호` → `해석`.
출처 표현을 섞지 않는다 — MBTI는 '성향 렌즈에서는', 신호는 '네가 답한 / 실제 관계 답변에서는'.

**의미적 매핑 (4축 중 1축만 사용)**

| MBTI 축 | 후보 관계 신호 | 연결 이유 | 위험 | 사용 |
|---|---|---|---|---|
| ENERGY (E/I) | 개인 시간(`alone`) | ENERGY 축 문구 자체가 이미 "혼자 있는 시간으로 회복 / 함께 활동하며 회복"이고, `alone`은 "혼자 있는 시간이 얼마나 필요한가"를 1~5로 저장한 값 — **같은 대상**을 말한다 | I가 곧 '개인 시간을 많이 원함'은 아니다 | **사용** (예측 아닌 비교로만) |
| INFORMATION (S/N) | 없음 | 구체·추상 정보 처리에 대응하는 관계 질문이 없다 | 억지 연결 | **사용 안 함 → UNKNOWN** |
| DECISION (T/F) | 갈등 해결(`conflict`) | 표면적으로만 관련 | **높음.** `conflict`는 이야기를 꺼내는 **시점**, T/F는 판단 **기준** — 서로 다른 것을 잰다. 연결하면 'T라서 공감 못 함' stereotype | **사용 안 함 → UNKNOWN** |
| LIFESTYLE (J/P) | 없음 | 계획·구조에 대응하는 질문이 없다 | 'J/P = 데이트 계획' 하드코딩 | **사용 안 함 → UNKNOWN** |

**상태 판정** — `성향에서 비슷함 === 신호에서 비슷함` 이면 `ALIGNS`, 아니면 `DIFFERS`.
tone이 `unknown`(한쪽 모름)이면 `UNKNOWN/no-signal`, `neutral`이면 `UNKNOWN/inconclusive`.
**ALIGNS는 '잘 맞음'이 아니다** — 두 관점이 같은 방향을 가리킨다는 뜻뿐이다(둘 다 '다름'을
가리켜도 ALIGNS).

**전체 그림 비교** — MBTI `sameCount`와 관계 신호 `goodSignals/frictionSignals` 개수를
**나란히 읽는다.** 더하거나 평균 내지 않는다 — 합산하는 순간 MBTI가 점수에 들어간 것이 된다.

**동일시 방지 장치 (Release Checkpoint에서 추가)** — 화면에서 두 라벨이 붙어 있으면
`ENERGY = 개인 시간`으로 읽힐 수 있어 사이에 비교 기호(`↔`)를 두고, 축 비교 블록 아래에
한 줄을 고정한다: *"두 줄은 같은 것을 잰 값이 아니야. 성향 렌즈의 축과 네가 직접 답한 관계
질문을 나란히 놓고 본 거라, 한쪽이 다른 쪽을 결정한다는 뜻은 아니야."*
해석 문장에도 인과 표현(`~라서` · `~때문에` · `예측`)을 쓰지 않는다 — 전수 grep으로 확인.

**Surprise 선정 (랜덤 없음 · 고정 우선순위)**

| 순위 | 조건 | 예시 (실측) |
|---|---|---|
| 1 | 축: MBTI 같음 + 실제 답 다름 | "성향 렌즈에서는 둘 다 I로 묶이는데, 개인 시간에 대한 기대는 오히려 다르게 답했네." |
| 2 | 축: MBTI 다름 + 실제 답 비슷 | "성향 렌즈에서는 서로 다른 쪽으로 나뉬는데, 개인 시간에서는 비슷한 걸 원한다고 답했네." |
| 3 | 전체 그림이 다른 방향 | "MBTI에서는 비슷한 축이 더 많은데, 실제로 답한 신호에서는 다른 쪽이 더 많네." |
| 4~5 | 같은 방향(축 → 전체) | "두 관점이 같은 방향을 가리켰네. 그래도 같은 방향이라고 같은 뜻인지는 더 봐야겠어." |
| 6 | 비교 가능한 것 없음 | `null` — 없는 Surprise를 만들지 않는다 |

근거(Evidence)는 Surprise **바로 아래 블록**이 보고서 톤으로 말한다. 실제 저장된 answer
label만 인용한다(`나: 혼자 있는 시간 5/5 · 상대: 거의 안 챙김`) — 자유서술 원문은 쓰지 않는다.

## 7. 핵심 계산 로직

> ⚠️ **심리 검사나 과학적 진단이 아니다.** 입력값의 공통점·차이를 사용자가 직관적으로 읽을 수
> 있게 만든 **규칙 기반 로직**이다. 전부 `src/lib/logic/**`의 **순수 함수**이고, 화면은 계산을
> 직접 하지 않는다.

### 7.1 동기화율 (Sync Rate) — `logic/compatibility.ts`

**하한선(Floor) 없음. 관계 행동 4축(`contact`/`conflict`/`alone`/`affection`)만 사용.**

```
difference     = |나의 값 - 상대의 값|          // 둘 다 1~5 척도
axisSimilarity = 1 - (difference / 4)            // 0~1
score          = round( mean(비교 가능한 축의 axisSimilarity) × 100 )
```

| 차이 | 동기화율 |
|---|---|
| 완전히 동일 | **100** |
| 1단계 차이 | 75 |
| 2단계 차이 | 50 |
| 3단계 차이 | 25 |
| 완전 반대(4단계) | **0** |

| 규칙 | 내용 |
|---|---|
| E3 조건 | 비교 가능한 축이 **3개(`TARGET_MIN_KNOWN`) 미만**이면 `score = null` |
| '모름'(`x`) | 계산에서 **완전히 빠진다**. `comparedCount`에도 안 들어간다 |
| 항상 함께 표시 | "비교 가능한 N개 신호 기준" + **"연애 성공확률이 아니야"** |
| UI 게이지 | `alignment = round(axisSimilarity × 5)` — 완전 반대일 때 **0칸** |

> **과거 문제(고쳐짐)** — v1.0은 `score = 40 + floor(평균비율 × 52)`라는 인위적 하한선이 있어
> 축이 다 어긋나도 최소 40점이 나왔다. 그리고 `talk`/`rhythm` 두 축의 '나의 값'을 사진 관찰
> 고정값(4, 3)으로 하드코딩해서 계산에 넣었는데 **사용자가 준 데이터가 아니었다.**

#### tone 판정과 문장 선택

```
tone(similarity) =
  null      → 'unknown'
  >= 0.75   → 'good'
  <= 0.25   → 'watch'
  그 외      → 'neutral'
```

`evidence`/`scene` 문장은 **tone별로 따로** 정의돼 있다(`AxisCopyByTone`). 축당 문장 하나를
tone과 무관하게 붙이면 **판정과 반대되는 문장**이 나간다 — 실제로 있었던 문제다.

| 실제 발생했던 모순 | 원인 |
|---|---|
| 개인 시간 1/5 vs 상대 '중요해 보임' → 배지는 '관찰 필요'인데 "…거절로 받아들일 가능성이 **비교적 낮아** 보여" | 축당 문장 1개 고정 |
| 갈등 해결이 양쪽 다 '바로 대화'(일치)인데 "한쪽은 대화를 피한다고 느끼고…" | 〃 |
| 연락 중요도를 5/5로 답해도 "연락 중요도는 **낮게** 답했지만…" | 데모 페르소나 기준으로 쓴 문장 |

계산(`similarityOf`·`toneOf`·`alignment`·`score`)은 건드리지 않고 **문구 테이블만** tone별로 나눴다.

### 7.2 MBTI Lens (Supporting) — `logic/mbtiLens.ts`

**점수가 아니라 대화 포인트를 만든다.** 4개 선호 지표를 각각 **독립적으로** 비교하고 합산하지 않는다.

```
buildMbtiLens(mine, theirs)   // 둘 중 하나라도 없으면 null → TOGETHER 비교만 안 만든다
  → axes[4] : { key, eyebrow, label, mineLetter, theirsLetter, same, note }
  → sameCount / differentCount

buildMbtiSelfLens(type)       // 한 사람 유형만으로 항상 만들 수 있다 (Self First)
  → axes[4] : { key, eyebrow, label, letter }
  → note
```

| 축 | key | 글자 |
|---|---|---|
| 에너지를 회복하는 방식 | `energy` | I / E |
| 정보를 받아들이는 방식 | `information` | S / N |
| 결정할 때 먼저 보는 기준 | `decision` | T / F |
| 계획과 유연함 사이 | `lifestyle` | J / P |

> ⚠️ **표현 규칙.** 같은 글자를 '좋음', 다른 글자를 '나쁨'으로 표현하지 않는다.
> 화면 라벨은 **`비슷한 성향` / `다르게 나타날 수 있는 성향`** 두 가지만.
> **금지:** GOOD/BAD MATCH · 최고의 궁합 · 천생연분 · 상극 · 완벽한 조합 · MBTI 궁합 N점 · 퍼센트
> **톤:** `~할 수 있어` / `~로 이야기되기도 해` / `실제로 그런지는 확인해봐`

**관계 신호와의 관계** — MBTI로 실제 관계 신호를 *설명해버리지 않는다.* 갈등 방식에 실제 차이가
있고 MBTI `decision` 축도 다를 때, **두 현상이 같은 원인이라고 단정하지 않는다.**
Relationship Evidence가 우선이고 MBTI는 Supporting이다.

#### 왜 한 번 넣었다가 되돌렸는가

MBTI 4글자 중 같은 글자 수를 `matches / 4`로 similarity화해서 관계 행동 축과 **동일한 가중치**로
score 평균에 넣은 구현이 있었다. E/I·S/N·T/F·J/P가 많이 같다고 더 좋은 관계라는 근거가 없어
**'근거 없이 판정하지 않는다'** 원칙과 정면 충돌했다. `buildMbtiDimension()`과 `mbtiSimilarity()`를
삭제했다.

두 사람 비교는 **4원소**(fire/earth/air/water)로 '비슷/다름'만 만든다. 점수·확률 없음.

### 7.5 Relationship Mirror 판정 — `logic/mirror.ts`

**숫자를 빼지 않고, '근거의 종류'로 카테고리 판정한다.**

```
evidenceStrength(axis) =
  hardest(가장 힘들었던 순간)가 이 축과 강하게 연결됨  → 'hardest'    (가장 강한 근거)
  important(중요했던 요소)에 이 축이 포함됨             → 'important'  (중간 근거)
  둘 다 아님                                            → 'absent'     (근거 없음)

state(declaredValue, strength) =
  'hardest'   && declared >= 4   → MATCH
  'hardest'   && declared <  4   → GAP
  'important' && declared <= 2   → GAP
  'important' && declared >  2   → MATCH
  'absent'    && declared >= 4   → CHANGE    (말했지만 근거가 안 보임)
  'absent'    && declared <  4   → UNKNOWN   (판정하지 않음)
```

| 규칙 | 내용 |
|---|---|
| `hardest` 대응 | `contact_drop→contact` · `fight_silence→conflict` · `no_time→alone`. `value_gap`은 5축 어디에도 명확히 대응하지 않아 **대응표에서 뺐다** |
| **UNKNOWN** | `insights` 배열에 **아예 포함되지 않는다** — 근거 없는 축을 억지로 MATCH로 채우지 않는다 |
| 헤더 표시 | "비교 가능한 N개 기준에서" = 실제 판정 개수 |

**화면 표시 규칙**

| 값 | 표시 |
|---|---|
| Declared | **실제 1~5로 수집된 축만**(`alone`·`contact`) `N/5`로 표시. `hobby`·`conflict`·`affection`은 3지선다를 내부 계산용으로 매핑한 값이라 **숫자를 보여주지 않고 문구만**(`declaredHasScale` 플래그) |
| Relationship | 숫자가 아니라 `relationshipSignalText()`가 만든 **문장** ("이전 관계에서 연락 감소가 가장 힘든 순간으로 선택") |

> **과거 문제(고쳐짐)** — 과거 관계 질문은 전부 선택형이라 1~5로 수집된 적이 없는데
> `important.includes('contact') ? 4 : 2` 같은 규칙으로 **억지로 숫자화**했다. Declared(실제
> 척도)와 이 가짜 숫자를 빼서 판정하니 실제보다 정밀하게 측정된 것처럼 보였다.
> Declared 미응답을 중립값 3으로 채운 것도 문제였다(Missing data ≠ 중립).

### 7.6 Focus 축 선정 (Teaser · Core Insight)

```
1순위: hardest 근거의 GAP 축
2순위: 그 외 GAP 축
3순위: CHANGE 축
4순위: 첫 번째 판정된 축 (모두 MATCH인 경우)
```

`contact`가 GAP으로 뽑히면 고정 헤드라인("너는 연락 자체보다…"), 그 외에는
`"너는 {label}에서 말한 기준보다 실제 관계에서 더 크게 반응하는 사람일지도 몰라."` 템플릿.

### 7.7 Adaptive Follow-up 트리거

```
pickAdaptiveTriggerAxis(declared, experience) =
  experience.skipped                       → null
  buildInsights()의 focus 축이 GAP이면      → 그 축
  그 외                                     → null
```

### 7.8 Relationship Profile Summary (S18) — `logic/profile.ts`

```
declaredHighlight(declared)       // Declared 중 가장 두드러진 특징 1개 (우선순위 표)
relationshipHighlight(experience) // 관계 경험 중 신호 1개 (hardest 우선, 없으면 important[0])

summary =
  둘 다 있으면  → "{declared 특징}, {relationship 신호}."
  하나만 있으면 → 있는 쪽만
  둘 다 없으면  → "아직 뚜렷한 특징을 관찰하기엔 정보가 조금 더 필요해."
```

두 문장은 **판정 없이 나란히 붙인다.** "~라고 답했지만 실제로는" 같은 비교·모순 표현은 이 함수
안 어디에도 없다 — Mirror와 코드가 완전히 분리돼 있어 **애초에 그런 문장을 만들 수 없다.**

### 7.9 History Change — `logic/history.ts`

> ⚠️ **Mirror State와 History Change State는 완전히 다른 축이다.**
>
> | | 비교 대상 |
> |---|---|
> | **Mirror** (MATCH/GAP/CHANGE) | 하나의 Snapshot 안에서 Declared vs Relationship Evidence |
> | **History** (STABLE/SHIFT/NEW/INSUFFICIENT) | 과거 Snapshot vs 현재 Snapshot |

UI에서 비교를 계산하지 않는다 — 전부 이 파일을 거친다.

| 함수 | 역할 |
|---|---|
| `analysisFingerprint()` | 중복 저장 방지용 분석 지문 |
| `buildHistoryEntry()` | 세션 + Mirror → 저장할 Entry (불가하면 `null`) |
| `compareDeclaredSnapshots()` | **직접 1~5로 수집한 축만**(contact/alone) 값 비교 |
| `compareMirrorSnapshots()` | 축별 과거/현재 Mirror 상태 |
| `buildHistoryChanges()` | 축별 `HistoryAxisChange` |
| `getMostMeaningfulChange()` | SHIFT 우선 → NEW. 없으면 `null` |
| `buildHistorySummary()` | 러비 한 줄 요약 |
| `buildHistoryReport()` | 기록 2개 미만이면 `comparable: false` |
| `findRepeatedRelationshipSignals()` | 같은 축에서 GAP/CHANGE 반복 |
| `pastObservationFor()` | 특정 축의 Past Observation 한 줄 |

**판정 규칙**

```
pastState === null   → nowState ? 'NEW' : 'INSUFFICIENT'
nowState  === null   → 'INSUFFICIENT'        // 사라졌다고 단정하지 않는다
pastState !== nowState || declared 값이 실제로 달라짐 → 'SHIFT'
그 외                 → 'STABLE'
```

| State | Copy 규칙 |
|---|---|
| STABLE | "이전 관찰과 비슷하게 유지되고 있어." — **'일관된 성격' 같은 Personality 판정 금지** |
| SHIFT | 척도 축이면 `(2/5 → 4/5)`까지 표시. "지난번보다 ~ 더/덜 중요하게 보고 있어." — **'성장했다' 금지** |
| NEW | "이번 관찰에서 처음 보였어." |
| INSUFFICIENT | "아직 ~ 비교할 정보가 부족해." — **판정하지 않는다** |

**척도 비교 제약** — `contact`/`alone`만 트랙 위 점으로 비교한다(직접 1~5로 수집한 값).
`conflict`/`affection`/`hobby`는 선택형이라 증감으로 말하지 않고 문장으로만 대조한다.
**Relationship Evidence는 절대 숫자로 만들지 않는다.**

#### 7.9.1 반복 신호 (Repeated Relationship Signal)

같은 축에서 **GAP/CHANGE가 2회 이상** 나타난 기록. **MATCH는 반복 신호로 보지 않는다** —
'말한 대로 나타났다'가 되풀이되는 건 발견이 아니다.

- 기준은 **Mirror Evidence만.** MBTI 변화는 절대 반영하지 않는다
- Copy: `이 신호… 처음 보는 게 아닌데.` / "이 기준은 이전 관찰에서도 비슷한 신호가 있었어."
- **금지:** '너는 항상 이래' / '반복되는 문제야' / '너의 연애 패턴은 이거야'

#### 7.9.2 Past Observation — Supporting Evidence

| 화면 | 위치 |
|---|---|
| S27R `/mirror` | Mirror Gap Map **아래**(반복 신호 알림) · '이렇게 생각한 이유' 마지막 항목 |
| S21R `/compatibility` | Friction Signal **뒤**, Lens **앞** (참고 섹션) |

> ⚠️ **Past Observation은 현재 판정을 바꾸지 않는다.**
> 현재 Mirror = 현재 데이터만 / Past History = Supporting Evidence.
> 현재 Evidence가 없으면 과거만으로 Gap을 만들지 않는다.
> 현재 분석이 이미 저장돼 있으면 그 항목은 과거에서 제외한다(**자기 자신을 반복으로 세지 않는다**).

**정보 위계:** `① 실제 관계 신호 → ② 근거/상황 → ③ Past Observation → ④ MBTI Lens`
History도 MBTI도 실제 관계 신호보다 위에 오지 않고, **둘 다 동기화율에 들어가지 않는다.**

### 7.10 Evidence Coverage (구 '확신도')

이름을 '확신도'에서 **'관측 정보 충분/보통/부족'**으로 바꿨다. 이 값은 'AI가 얼마나 확신하는가'가
아니라 **'얼마나 많은 입력 근거가 확보됐는가'**를 뜻한다.

```
experience.skipped                              → 부족
!(important.length >= 3 && selfGap !== null)     → 부족
note(서술)가 비어있지 않음                        → 충분
그 외                                            → 보통
```

자유서술을 많이 했다고 분석이 사실일 확률이 높아지는 건 아니다 — 그래서 이름을 **근거량**으로
한정했다.

사진 관찰 쪽 Coverage는 **코드가** 판정한다(AI가 '충분하다'고 말하지 못한다).

```
evidenceCoverageLevel(usableImageCount, traitCount) =
  usable >= 5 && traits >= 3   → 'high'
  usable >= 3 && traits >= 2   → 'medium'
  그 외                         → 'low'
```

### 7.11 Approach Hints — `logic/approachHints.ts`

> ⚠️ **호감도 예측이나 공략법이 아니다.** '네가 알려준 상대의 모습'을 기준으로, 관계 속도를
> 맞출 때 참고할 것을 규칙으로 만든다. 최대 3개.

| 종류 | 조건 |
|---|---|
| 연락 힌트 | 상대 `contact` 값 기준 |
| 표현 힌트 | 상대 `affection` 값 기준 |
| 갈등 힌트 | **실제 friction이 있을 때만** 만든다 |
| 취향 힌트 | `target.preferences.interests`가 있을 때 |

- 항상 하단에 "이건 공략법은 아니야. 실제론 직접 물어보는 게 가장 정확해."
- 힌트가 0개면 "아직 이 사람이 좋아하는 걸 많이 알진 못하네." + 질문 섹션으로 유도
- **AI는 의도적으로 미연결** — 규칙만으로 만든다
- Analytics에 **raw interest 텍스트·힌트 문장 원문을 절대 보내지 않는다**

**완전히 결정론적이다.**

### 7.13 러비 관찰 노트 · FIRST SURPRISE — `data/lovyNotes.ts`

감성 문구를 화면 곳곳에 하드코딩해 흩뿌리지 않는다. **한 곳에 `trigger × axis`로 등록하고
현재 결과에서 결정론적으로 고른다** — 같은 결과면 언제나 같은 문장이다(**랜덤 생성 금지**).

```

  score === null                  → null   (데이터가 없는데 생각을 지어내지 않는다)
  frictionSignals[0]이 있으면       → 그 축의 gap 노트
  goodSignals[0]이 있으면           → 그 축의 alignment 노트
  그 외                            → align-default
```

> ⚠️ 이 문장들은 **결과를 만들지 않는다.** 이미 계산이 끝난 `CompatibilityResult`를 보고 러비가
> 떠올린 '생각/질문'일 뿐이다 — Compatibility Score·4축 계산·tone 판정은 이 파일을 **읽지도
> 않는다.**

**화법 규칙** — 인간을 처음 보는 외계인의 호기심. 짧은 혼잣말. `~일 수도 있겠네` / `~인가 봐`.
금지: `당신은 ~한 사람입니다` · `이 관계는 성공할 확률이 ~` · `심리학적으로 ~`.

`selectFirstSurprise(result)`는 §6 S21R 참고.

## 8. AI 분석 파이프라인

### 8.1 가장 중요한 원칙 — 역할 분리

> **AI는 럽유럽미의 '판정자'가 아니다.**
>
> ```
> Evidence  →  Rule  →  AI Explanation  →  User Verification
> ```

| | 담당 |
|---|---|
| **Rule Logic** (deterministic) | 동기화율 · Mirror MATCH/GAP/CHANGE · History STABLE/SHIFT/NEW · MBTI 축 비교 · Sun Sign · Evidence Coverage |
| **AI** | 관찰 · 정리 · 설명 · 개인화 문장 · 질문 생성 |

**AI가 생성할 수 없는 것** — Compatibility Score · Mirror State · History State · MBTI 결과 ·
Sun Sign · 사주 계산 · Premium 가격/가용성.

**구조적 보장**

- `buildCompatibility()`는 **AI 결과를 인자로 받지 않는다**
- Mirror state는 서버에서 **규칙 값으로 덮어쓴다**(`attachRuleStates()`) — AI가 `state`를
  바꿔 보내도 무시된다
- `focusAxis`는 규칙이 고른다. AI가 고르지 않는다
- **실측:** AI 분석 결과를 통째로 조작해도 동기화율 55 · 신호 2/2 · Mirror 판정이 불변이었다

| `SessionProvider` 복원 | v1.5 이전 세션 | `traits: []` (사용자 확인·수정 기록은 보존) |

> **왜 고쳤는가** — v1.21까지 이 함수는 `OBSERVED_TRAITS`(ob1~ob4 고정 문장)를 사진 **개수만**
> 보고 돌려줬다. 그래서 Provider가 붙지 않은 배포에서 **음식 사진만 올린 사용자에게
> "영화관·상영 시간표가 담긴 사진이 반복적으로 관찰됐어"가 자기 관찰로 보였다.**
> 화면에는 이미 "실제 사진 내용을 분석하지 않았어. 그래서 관찰 결과도 만들지 않았어."라는
> 정직한 문구가 있었고 **코드만 그 약속을 어기고 있었다.**
> 문구를 지우는 대신 **코드를 문구에 맞췄다.**

**샘플 세션은 분리돼 있다** — `buildSampleObservedResult()`가 고정 문장을 쓰는 유일한 함수이고,
`createSampleAnswers()`만 이 함수를 호출한다. 진입점은 dev 전용 `PrototypePanel`과
S06 `/profile/intro`의 '샘플 답변으로 결과부터 볼게' 두 곳이다(§6 S06 참고).
**사진을 업로드한 사용자의 결과 경로와는 완전히 분리돼 있다.**

### 8.5 Observed Me — 사진 분석 (Vision)

#### 4계층 분리 — 한 장의 사진에서 바로 '생활 패턴'을 만들지 않는다

| 계층 | 내용 | 만드는 주체 |
|---|---|---|
| LEVEL 1 Observation | 사진 1장에서 직접 보이는 것 (`야구장으로 보이는 장소`, `유니폼`) | **AI** (사진 1장씩) |
| LEVEL 2 Activity Signal | 관찰 라벨 → 활동 범주 (`야구장 + 유니폼` → `스포츠 관람·운동`) | 규칙 |
| LEVEL 3 Repeated Signal | 서로 다른 장면 몇 개에서 반복됐는가 | 규칙 |
| LEVEL 4 Hypothesis | `평소 즐기는 활동 중 하나일 가능성이 있어 보여` | 규칙 문장 템플릿 |

```
analyzePhoto(photo)              → PhotoObservation    (사진 1장 = Provider 1회)
aggregatePhotoObservations(...)  → ObservedSignal[]    (반복 판정은 여기서만)
```

> ⚠️ **Provider에게 반복 여부·`occurrenceCount`를 묻지 않는다.** Provider는 사진을 한 장씩
> 보므로 애초에 알 수 없고, 물어보면 **지어낸다.** 응답에 그런 필드가 섞여 와도 **스키마가
> 읽지 않는다**(Contract Test `photo_observation_repetition_claim`으로 고정).

**비용 주의** — 사진 1장당 Vision 1회다(사진 9장 = 9회). 동시 요청은 `PHOTO_CONCURRENCY = 3`.

#### 반복 기준

| 서로 다른 장면 수 | `strength` | `confidence` | 화면 문구 |
|---|---|---|---|
| 1 | `single` | low | 사진 한 장에서만 확인했어. 아직 평소 활동이라고 보긴 어려워 |
| 2 | `repeated` | medium | 사진 2장에서 비슷한 장면이 보였어. 반복인지는 아직 조심스러워 |
| 3+ | `strong_repeated` | high | 반복해서 보였어. 평소 즐기는 활동 중 하나일 가능성이 있어 보여 |

**세는 단위는 사진 장수가 아니라 장면 그룹이다.** 관찰 라벨 집합이 **Jaccard 0.75 이상** 겹치는
사진들은 '같은 날 같은 장소에서 연속 촬영한 것 같다'고 보고 한 그룹으로 묶어 **1회로** 센다.

> 픽셀·EXIF를 보지 않는 근사치라 다른 날 같은 카페 사진도 묶일 수 있다.
> **반복을 덜 세는 방향의 오류를 일부러 택했다** — 반대 방향은 없는 생활 근거를 만들어내는 것이다.

#### 절대 추론 금지

| 범주 | 내용 |
|---|---|
| **민감 범주** | 성적 지향 · 정치 · 종교 · 정신건강 · 질병 · 장애 · 경제 수준 · 범죄성 · 성생활 · 임신 · 민족/인종 · 연애 상태 · MBTI · 애착유형 |
| **관계 규정** | 사진 속 사람을 `친구`·`연인`·`가족`·`동료`라고 부르지 않는다. `다른 사람과 함께 있는 장면`까지만 |
| **성격 변환** | 여행 → 자유로운 성격, 책 → 지적, 운동 → 자기관리 철저 같은 변환 금지 |
| **사람 분석** | 얼굴 점수 · 매력도 · 나이 추정 · 체형 평가 · 표정에서 감정 읽기 |

> Observed Me는 **Behavior / Activity / Environment**까지이고, Personality는 Declared Me와
> MBTI Supporting Lens의 영역이다.

프롬프트가 1차 방어, `safety.ts`의 `scanPhotoObservation`이 **최후 방어선**이다.

**검사는 라벨 단위로 돈다** — `카페 테이블`과 `친구들`이 같은 사진에서 나왔다면 앞의 것은 쓸 수
있는 관찰이므로 **사진 전체를 버리지 않는다.** 걸린 라벨은 **고쳐 쓰지 않고 버리고**,
"사진에서 추론하지 않기로 한 항목이 있어서 일부 관찰은 제외했어"를 한계에 남긴다.

#### Evidence Provenance

모든 신호가 `photoIds`를 들고 다니고, '근거 보기'는 사진 단위로 무엇을 봤는지 보여준다
(`사진 1 · 야구장으로 보이는 장소 · 경기 관람 · 유니폼`).
사용자 수정은 `signal.id`를 키로 저장되므로 이후 Cross-source 분석에서 **AI 원본이 아니라
사용자 확인/수정 결과**를 쓴다.

**신호 0개는 실패가 아니다** — 개수를 채우려고 약한 관찰을 만들지 않는다. 최대 6개.

#### 이미지 준비 — `imagePrep.ts`

| 항목 | 값 |
|---|---|
| 장변 상한 | 1024px |
| JPEG 품질 | 0.8 |
| 개당 상한 | 1,200,000 bytes (초과 시 skip) |
| 대상 | **업로드 사진만.** 샘플 타일은 실제 이미지가 아니라 전송 대상이 아니다 |
| **EXIF** | 캔버스 재인코딩으로 **자동 제거된다** — GPS 좌표·촬영 시각·기기 정보가 결과에 남지 않는다. 부수효과가 아니라 이 방식을 택한 이유 중 하나다 |
| 파일명 | **보내지 않는다.** 세션 내부 id만 사용 |
| 실패 처리 | 손상 파일·0바이트·디코드 실패는 조용히 skip하고 `skipped` 수를 화면에 알린다 |

```
photoFingerprint(photos) = photos.map(p => `${p.source}:${p.id}`).join('|') || 'empty'
```

사진 id와 **순서**를 모두 반영하므로 한 장만 바꿔도 지문이 달라진다.

### 8.6 Structured Output + 2단 검증

자유 텍스트 하나로 받지 않는다. 모든 Task가 JSON 스키마를 강제하고 **2단**으로 검증한다.

**① Schema Parse** — 타입·길이·enum·허용 id 검사
**② Business Validation** — 스키마는 맞지만 제품 규칙을 위반한 응답 처리

| 위반 | 처리 |
|---|---|
| Evidence 없는 Trait | **버린다** |
| 입력에 없는 `imageId` 참조 | 그 evidence를 버린다 |
| `confidence: high`인데 evidence 1개 | `medium`으로 **강등** (사진 1장 단정 금지) |
| 규칙이 판정하지 않은 축 | 버린다 |
| 현재 궁합에 없는 dimension | 버린다 |
| 강한 결론 + `evidenceRefs` 0개 + uncertainty 없음 | 버린다 |
| AI가 보낸 `state`/`kind` | **규칙 값으로 덮어쓴다** |
| Core 설명에 MBTI·사주·별자리 언급 | 버린다 — Core Task에 그 데이터를 **보내지도 않았다** |
| History에 성장·극복·좋아졌다 서사 | 버린다 |
| 표시 길이 초과 | **버리지 않고** 문장 경계에서 자른다 |
| 상대 마음 읽기 | 버린다 |

> **한 절 안에서 감정·의도 동사를 찾는다.** 주어와 동사가 붙어 있을 때만 걸리면
> '상대는 너를 **더** 좋아하고 있어서'가 통과한다.
>
> 단 **'상대가 어떻게 느낄지는 알 수 없어'처럼 모른다고 말하는 문장은 의도적으로 남긴다** —
> 그건 마음 읽기가 아니라 **정직한 한계 진술**이다.

오류 코드를 그대로 보여주지 않고 사람 말로 바꾼다.

### 8.8 Cache · Fingerprint

각 Narrative는 **자기 입력이 바뀔 때만** 다시 생성된다. 지문이 같으면 캐시를 쓰고, 달라지면
이전 응답은 stale로 버린다.

> ⚠️ **지문에 절대 넣지 않는 것** — 넣으면 위계가 무너진다.
>
> | 제외 | 이유 |
> |---|---|
> | MBTI | Supporting Lens가 Core 설명을 무효화시키면 안 된다 |
> | Birth Profile | Entertainment Lens |
> | Premium Intent / 가격 variant | **결제 의향이 분석을 흔들지 않는다** |
> | 사진 원본 | Observed Task는 `photoFingerprint`가 따로 만든다 |

즉 MBTI를 입력하거나 Premium을 눌러도 **Core AI 설명은 재호출되지 않는다.**

자유서술은 **원문이 아니라 길이만** 지문에 넣는다 — 사용자 문장을 지문에 남기지 않는다.

### 8.9 안전 경계 요약

| 경계 | 규칙 |
|---|---|
| Key 노출 | `server-only` import로 빌드 단계에서 차단 |
| Prompt Injection | 사용자 데이터는 system instruction과 섞지 않고 `wrapUserData()`로 delimit |
| Data Minimization | Task별 최소 컨텍스트만 전송. 상대 관계 맥락(`targetRelation`)은 **항상 `null`** |

| Rate Limit | 인스턴스 메모리 기반. `RateLimitStore` 인터페이스 경계만 준비됨 (**공유 저장소 미연결**) |
| 로깅 | `requestId`·task·duration·reason만. **사용자 원문·사진 미기록** |

## 9. Premium

### 9.0 무료 / Premium 경계 (v1.26 · P3-3)

> **무료에서는 하나의 관찰을 충분히 이해하게 하고,**
> **Premium에서는 서로 다른 관찰 사이의 연결을 해석한다.**

| | FREE | PREMIUM |
|---|---|---|
| 단위 | 한 Lens · 한 Signal | Signal **사이의 연결** |
| 질문 | 무엇이 보이는가 | 왜 함께 나타나는가 |
| 범위 | 한 장면 | 여러 장면의 패턴 |
| 깊이의 출처 | 그 관찰을 끝까지 설명 | Cross-source Interpretation |

**왜 재설계했나** — v1.25에서 무료 MBTI가 깊어지면서 "왜 ₩1,900을 내야 하지?"가 실제
제품 질문이 됐다. Audit 결과 Deep Report의 두 섹션이 무료 문장을 **글자 그대로** 다시
보여주고 있었다:

| 제거한 섹션 | 실체 |
|---|---|
| `궁합 심화 비교` | `buildCompatibilityDetail`이 무료 `SignalCard`와 같은 `dimension.evidence` / `dimension.scene`를 그대로 씀 (v1.23부터 남아 있던 Remaining Risk) |
| `실제로 일어날 수 있는 상황` | `situationFor`가 같은 `AXIS_DEFINITIONS.scene.watch` / `evidence.watch`를 재출력 |
| `이야기해볼 질문` | 무료 질문 텍스트를 그대로 옮김 → 연결을 검증하는 질문으로 대체 |
| `러비의 최종 관찰` | `insights[0].ruleSummary`를 리포트 맨 아래에 다시 적음(맨 위 CORE PATTERN과 동일) |

#### Cross-source 조합 (`lib/logic/crossSourceInsights.ts`)

| # | 조합 | 만들어지는 조건 | 비고 |
|---|---|---|---|
| ① | Declared ↔ Relationship (+Observed 보강) | Mirror 판정이 UNKNOWN이 아닐 때 | ④가 같은 축을 이으면 **억제**(중복) |
| ② | Relationship(hardest) ↔ Target | 과거 통증 축과 상대 특성이 겹칠 때 | |
| ③ | Current ↔ History | SHIFT/NEW · 반복 신호 | |
| **④** | **Compatibility ↔ Relationship / Mirror / History** | **v1.26 신설.** 동기화율에서 판정된 축이 Mirror·History와 같은 축을 가리킬 때 | 이 Engine이 v1.25까지 `CompatibilityResult`를 **입력으로 받지도 않았다** |
| **⑤** | **MBTI Lens ↔ Relationship Signal** | **v1.26 신설.** v1.24 Bridge가 DIFFERS로 판정한 축이 관계 경험과 겹칠 때 | 무료 4축 설명을 **재출력하지 않는다** |

④가 v1.26의 핵심이다. `buildCompatibility`는 관계 경험을 읽지 않고 `buildMirrorReport`는
상대 정보를 읽지 않는다 — **서로 독립적으로 계산된 두 판정이 같은 축을 가리키는 것**이
연결의 정보값이다.

#### 인과 vs 연관 (절대 경계)

| 금지 | 허용 |
|---|---|
| 과거 관계 **때문에** 지금 연락에 민감해졌다 | 과거에 비슷한 장면이 있었고, 지금 신호도 **같은 방향으로 보인다** |

그래서 모든 `DeepConnection`은 `limitation`을 **하나 갖는다** — 없으면 만들지 않는다.
`limitation`은 type이 아니라 **source 조합**에서 나온다(무엇을 이었는지가 무엇을 말할 수
없는지를 결정한다).

#### Deterministic vs AI

```
DETERMINISTIC  어떤 signal을 연결할지 선택        → ruleSummary (규칙)
AI             그 연결을 자연스럽게 설명          → narrativeText (문장)
```

AI는 **판정을 바꾸지 못한다.** `ruleSummary`가 항상 남고 `narrativeText`는 그 옆에 붙는다 —
AI가 실패하면 `narrativeText`가 null이고 리포트는 규칙 문장만으로 완결된다(§50 Retry는
AI 설명만 재시도하고 리포트는 사라지지 않는다).

#### AI Narrative Contract (v1.27)

```
AI_OUTPUT ⊆ DETERMINISTIC_EVIDENCE
```

v1.26 실측에서 **안전 검사를 전부 통과한** 두 종류의 실패 문장이 나왔다.

| 실패 | 규칙이 확인한 것 | AI가 쓴 것 |
|---|---|---|
| 인과 창작 | 두 관찰이 같은 축을 가리킨다 | `이 차이가 소통 방식에 영향을 미칠 수 있을 것 같아` |
| 되풀이 | `… 같은 축을 가리키고 있어.` | `… 같은 축을 가리키고 있어.` (글자 그대로) |

첫 번째는 헤지(`~수 있을 것 같아`)가 붙어 `hasUnsupportedCertainty`를 통과했다 —
**문제는 확신의 강도가 아니라 주장의 종류다.** 두 번째는 위험한 주장이 없어서 통과했지만
사용자는 같은 말을 두 번 읽는다.

**모델이 받는 세 칸** (`deep-report-v2-bounded`)

| 칸 | 내용 | 출처 |
|---|---|---|
| `OBSERVED FACTS` | 실제 세션 데이터로 만든 근거 | `aiEvidenceResolver` |
| `ALLOWED CONNECTION` | 규칙이 확인한 주장. **이것만 참이다** | `insight.ruleSummary` |
| `LIMITATION` | 이 연결이 말할 수 없는 것 | `limitationFor(sources)` |

v1.26까지는 evidence와 type 라벨만 보냈다 — 모델은 **규칙이 어디까지 확인했는지 몰랐다.**
`LIMITATION`은 화면에 보이는 것과 **같은 문자열**이고, **AI가 쓰지 않는다**(v1.26까지는
`narrative.uncertainty`가 규칙 경계를 덮어썼다).

**Quality Gate**

| 게이트 | 무엇을 막는가 | 위치 |
|---|---|---|
| (A) | 근거 2개 미만은 AI에 보내지 않는다 | `buildDeepReportContext` |
| (B)(C) | 일반론 · 근거 없는 확정 표현 | `scanDeepNarrative` |
| (D) | 마음 읽기 · 진단 · 민감 추론 | `scanForForbiddenInference` |
| (E) | 원래 Insight에 없던 `evidenceRef` | `evidenceRefsAreSubsetOf` |
| **(F)** | 규칙 문장 되풀이 (bigram novelty < 0.35 또는 글자 그대로 재사용) | `isRedundantNarrative` |
| **claim** | 인과 · 예측 · 의도 · 가치판정 | `scanClaimBoundary` |

⚠️ (F)의 임계값 `0.35`는 실측 3건으로 잡은 **초기 캘리브레이션 값**이다 — **NOT VALIDATED**.
상수는 `safety.ts` 한 곳에 있고, 관측치는 dev 로그의 `novel=`로 모은다.
`reference`(=`ruleSummary`)가 비어 있으면 판정하지 않는다(통과).

`scanClaimBoundary`는 **한계 문장을 예외로 둔다** — `원인이라고 말할 수 없어`를 막으면
경계 자체를 쓸 수 없다. 금지 대상은 **주장**이다.

걸리면 그 narrative만 버린다. 화면은 `ruleSummary`로 완결되므로 **AI가 하나도 안 남아도
리포트는 사라지지 않는다.**

그래서 **`AI 설명` 배지는 `mode`가 아니라 화면에 실제로 그려진 문장을 보고 붙인다**
(v1.28). Premium은 `narrativeText`가 붙은 연결이 있는지를, 무료 Compatibility는
`hasShowableNarrative`(렌더러와 같은 술어)를 본다 — 없는 것을 있다고 표시하지 않는다.
`규칙 기반 대체` 태그만 예외로 무조건 표시한다. AI가 있다는 주장이 아니라 AI 없이
규칙으로 채웠다는 고지라서, 문장이 없을 때 오히려 필요하다.

**실측**

```
[ai] deep-report filter parsed=5 refChecked=5 safe=5 novel=1
```

5개 전부 안전했지만 규칙에 뭔가를 더한 것은 1개다. AI narrative는 `모든 연결을 더 잘
설명하는 층`이 아니라 `추상적인 규칙 문장에 실제 값을 채워 넣을 수 있을 때만 값을 더하는
층`이다 — 분량을 억지로 늘리지 않는다.

#### Availability Gate — 무엇이 있으면 팔 수 있는가

`hasDeepConnection(insights)` 한 곳에서만 판정한다. Paywall 게이트(`premiumFeatureState`)와
리포트의 `available`이 **같은 기준**을 쓴다 — 다르면 "Paywall은 열리는데 리포트는 없다"가 된다.

| 조건 | 이유 |
|---|---|
| 서로 다른 source 종류 **2개 이상** | 이어야만 보이는 신호여야 한다 |
| 근거 ref **2개 이상** | 사용자가 확인할 수 있어야 한다 |

> **v1.26 Audit에서 고친 것** — 예전 게이트는 `insights.length > 0`이었다. 그래서 Mirror
> CHANGE 하나(`sources: [declared]`)만 있는 세션에서도 Paywall이 열리고, 열린 리포트에는
> 연결이 없어 단일 관찰 한 줄만 남았다. **실측 확인**: 수정 후 그 세션은 가격·CTA 없이
> "아직 서로 연결해서 볼 수 있는 신호가 부족해"로 정직하게 닫힌다.

⚠️ **`GAP`/`MATCH` 문자열은 화면에 노출되지 않는다.** v1.26에서 구 `DeepInsightCard`의
type 배지를 없앴으므로, type은 **순위 계산**과 **러비 관찰 선택**에만 쓰인다. 그래서
"GAP = 나쁨 / MATCH = 좋음"으로 읽힐 경로가 UI에 없다.

TYPE_RANK 순서는 v1.9부터의 기존 설계이고 '나쁨 우선'이 아니라 **'예상과 어긋난 것 우선'**
이다(CONTRADICTION → GAP → REPEATED → CHANGE → MATCH). 이 순서를 바꾸면 Mirror·History
화면의 기존 정렬까지 바뀌므로 v1.26에서 **변경하지 않았다.**

#### History 연결 — v1.26 실측으로 고친 3건

| 발견 | 조치 |
|---|---|
| `buildHistoryDetail`이 `previousText`/`currentText`를 `mine`/`theirs`에 담아 화면이 **나 / 상대**로 렌더 — 사실이 아닌 라벨 | `PremiumDetailSection.mineLabel`/`theirsLabel` 신설. History는 **이전 기록 / 최근 기록**. 다른 상세 4종은 기본값(나/상대) 그대로 |
| ④가 "이전 관찰에서도 **반복해서** 나온 축"이라고 말하면서 근거는 `entryIds[0]` **1건**만 걸었다 | 반복 판정에 쓰인 기록 **전부**를 근거로 건다 |
| ③ history CHANGE의 note는 **저장된 두 기록** 비교인데 두 번째 근거가 `declared`(현재값)라 화면에서 모순 — note "(2/5 → 3/5)" vs 근거 "5점 중 5" | 비교에 실제로 참여한 **두 기록**을 근거로 건다. source가 `history` 하나뿐이 되어 연결이 아닌 단일 관찰로 내려간다 — 그게 사실에 맞는 위계다 |
| 과거 근거 2건의 텍스트가 완전히 동일해 **'2번'을 확인할 수 없었다** | `resolveHistory`에 기록 날짜를 붙인다 (`2026.06.01 기록에서도 …`) |

| CASE | 기록 | 결과 |

| H1 | 0건 | HISTORY 섹션 미표시 · `과거 관찰` source 없음 · 억지 변화 서술 0 |
| H2 | 1건 | `comparable: false` — CHANGE/STABLE 선언 없음 · '반복' 표현 0 · 정직한 한계 문구 |

### 9.3 무료 / Premium 가치 경계

**무료에서 Core Value가 완성된다.** Premium은 무료 결과를 잘라내는 기능이 아니다.

> 새 점수를 만들지 않는다 — `buildCompatibilityDetail()`은 이미 계산된 `CompatibilityResult`를
> 그대로 읽는다.
>
> **Guardrail 3.** 무료가 **'Preview만 보여주고 결제하라는 화면'**처럼 느껴져도 안 된다.
> 무료 결과 자체로 적어도 하나의 작은 Aha가 있어야 한다.

### 9.4 Data Model

```
ResultLevel = 'summary' | 'detail'      // UI에서 잘라내지 않고 계약으로 분리

PremiumFeatureId = compatibility_detail | mirror_detail | history_detail
                 | mbti_detail | astrology_detail | saju_detail
                 | relationship_deep_report        // flagship 통합

PremiumFeature
├─ id · source · title · description · additions[]
├─ price   number | null      ← unavailable이면 null (가격을 붙이지 않는다)
└─ status  'available' | 'fake-door' | 'unavailable'    ← 기본은 fake-door

PremiumIntent                 // lym.premium-intent.v1 (세션 저장소와 분리)
└─ feature · source · price · variant · clickedAt · notifyIntent
```

> `PremiumIntent`를 `SessionAnswers`에 섞지 않은 이유 — **결제 상태가 분석 결과에 영향을 줄 수
> 없게 구조적으로 떼어놓기 위해서다.** Compatibility·Mirror·History 로직은 이 저장소를
> **import하지 않는다.**

`resetTargetContext()`(새 상대 시작)가 `clearPremiumIntents()`도 함께 호출한다 —
`PremiumIntent`가 `feature`로만 키를 잡고 Target을 구분하지 않아서, 지우지 않으면 이전
상대에게서 나온 '출시되면 알려줘' 클릭이 새 상대의 Paywall에 남아 있는 것처럼 보인다.

### 9.5 Relationship Deep Report (flagship)

`buildRelationshipDeepReport()`가 **8개 섹션**을 IA 순서대로 만든다. 데이터가 있는 섹션만 렌더한다.

```
Overview → Relationship Self → Cross-source Insight → Compatibility Deep Dive
        → Situations → Questions → History → Final Observation
```

| 항목 | 내용 |
|---|---|
| 가치 정의 | '더 긴 설명'이 아니라 **'따로 있던 결과를 연결했을 때만 보이는 것'** |
| Cross-source Insight | Declared · Relationship Evidence · Observed(사진) · History를 교차 |
| Evidence Hierarchy | Core > Supporting > Entertainment. 위계를 섞지 않는다 |
| AI 호출 시점 | **결제(또는 Preview Unlock) 이전에는 AI를 호출하지 않는다.** 규칙 기반 리포트 자체는 항상 준비돼 있다 |
| 규칙 기반 고지 | 일부 상세는 원래부터 100% 규칙 기반이다 — "데모라서 규칙 기반"이 아니라 **"원래부터 규칙 기반"**이라 AI_MODE와 무관하게 항상 표시한다 |

### 9.6 Paywall → Report 전환

`/premium` **한 Route**가 5 stage를 갖는다 (새 Route를 만들지 않았다 — Route를 나누면
layout continuity가 깨진다).

```
paywall → leaving → success → revealing → report
```

| 항목 | 내용 |
|---|---|
| 전환 시간 | 약 300ms — **상태 변화를 인지시키는 presentation layer 전용**. 실제 처리를 늦추지 않는다 |
| 연출 금지 | 자물쇠 · 금색 효과 · confetti · 폭죽 ❌ |

| 가격 노출 | 실제 `payment` mode에서만 |

### 9.7 Solo / First Contact (v1.29 · P4)

> **COUPLE — 나와 상대 사이의 차이**
> **SOLO — 나 안에서 함께 나타나는 기준**

기존 리포트는 전부 '두 사람'을 전제로 한다. 그래서 상대가 없고 경험도 없는 사용자는
동기화율 `?`와 "Mirror를 만들 수 없어"를 지나 홈으로 돌아갔다(P4 Audit 실측).

#### 세 상태 (`lib/logic/soloMode.ts`)

| mode | 뜻 | 판정 | 목적지 |
|---|---|---|---|
| `couple` | 비교할 만큼 안다 | `targetKnownCount >= TARGET_MIN_KNOWN(3)` | `/compatibility` |
| `unknown_target` | 사람은 있는데 아는 게 적다 | `relation !== null` 또는 known > 0 | `/first-contact` |
| `no_target` | 지금 특정 상대가 없다 | 그 외 | `/first-contact` |

⚠️ **새 점수를 만들지 않는다.** 이미 있는 `targetKnownCount`만 읽고, 동기화율·Mirror·
History 계산에는 들어가지 않는다.

⚠️ `unknown_target`이면 **상대를 추론하지 않는다** — 아직 `모름`으로 남긴 축에 대해서만
'물어볼 것'을 준다(`GETTING_TO_KNOW`).

⚠️ 프로필 결과 화면의 분기는 `soloModeOf`가 아니라 **`answers.status`**로 한다.
그 화면은 target 입력 **전**이라 모든 사용자가 `no_target`으로 읽힌다.

#### First Contact Report (`/first-contact` · `lib/logic/firstContact.ts`)

```
핵심 한 문장            두 답을 규칙으로 이어 붙인다(단계가 다르면 '지만', 같으면 '고')
01 WHAT YOU VALUE       내가 고른 값 그대로. 해석을 섞지 않는다
02 WHAT TO NOTICE       내 답변 두 개가 같은 자리를 가리킨다는 관찰 ← SOLO의 정보값
03 LOVY OBSERVATION     질문으로 끝난다(진단 아님)
04 GETTING TO KNOW      unknown_target에서만
05 FIRST CONTACT        TRY / ASK / NOTICE
06 OTHER LENSES         MBTI 있을 때만
```

- 랜덤이 없다. 같은 답에는 항상 같은 문장·같은 순서가 나온다.
- 섹션 번호는 **실제로 렌더되는 것만** 세어 붙인다. 데이터가 없으면 섹션이 아예 없다.
- 내 기준이 3개 미만이면 `available: false` — 빈 섹션을 늘어놓지 않는다.
- `firstContact.ts`는 `CompatibilityResult`도 `MirrorReport`도 **import하지 않는다.**

#### `WHAT TO NOTICE`의 규칙

`SELF_PAIR_RULES`에 등록된 조합만 나온다(전수 조합을 만들지 않는다). 각 항목은
**`limitation`을 반드시 갖는다** — Premium 연결과 같은 규칙이다. 하나도 안 맞으면
이 섹션은 비운다.

#### `해볼 수 있는 것`의 3칸 구조

```
SELF SIGNAL → WHY → ACTION
```

첫 칸이 없으면 일반 연애 팁이다. `FIRST_CONTACT_ACTIONS`가 축·단계로 걸러지므로
**목록 길이가 사람마다 다르다** — 분량을 맞추려고 채우지 않는다.

#### Solo Premium — 생성기 ⑥ `declared × observed`

Solo가 만들 수 있는 Cross-source 조합이 **하나도 없어서** Premium이 구조적으로
영구 unavailable이었다. 그래서 조합 하나를 신설했다.

```
declared   사용자가 답한 관계 기준
observed   사진에서 반복해서 나타난 활동(사용자가 확인·수정한 것만)
```

| | FREE | PREMIUM |
|---|---|---|
| Solo | 내 기준 하나씩 · 답변끼리 함께 나타난 것 | 내 기준 ↔ **사진 관찰**이 같은 축을 가리키는지 |

- **판정 기준은 커플과 동일**하다(`hasDeepConnection`: 서로 다른 source 2종 + 근거 2개).
  사진이 없으면 열리지 않는다.
- **이미 다른 조합이 덮은 축에는 만들지 않는다** — ①의 CONTRADICTION 승격이 같은
  observed 근거를 쓰므로, 커플 리포트가 바뀌지 않게 ⑥은 빈 자리만 채운다.
- 사진 한 장짜리 관찰과 반복 관찰을 같은 강도로 세지 않는다(`repeated` 분기).
- 사진으로 성격을 판단하지 않는다 — `limitationFor`의 `observed` 분기가 항상 붙는다.
- Premium unavailable 문구는 Solo에게 다르다: "사진을 올려서 관찰을 확인해두면" —
  **갈 수 없는 길을 알려주지 않는다.**

#### Navigation — 새 탭 0

`홈 / 나 / 분석 / 관찰기록` 유지. '분석' 탭이 Solo도 담당한다.

| | 목적지 | 열리는 조건 |
|---|---|---|
| couple | `/compatibility` | `completed.compatibility` |
| solo | `/first-contact` | `completed.profile` |

`couple`이 `/first-contact`로 직접 들어오면 `/compatibility`로 보낸다 — 빈 화면은 거짓이다.

#### 금지 (§19 · §29 · §47 · §48)

연애 성공 확률 · 연애 준비도 점수 · '솔로인 이유' 진단 · 애착 유형 · 자존감 ·

**관계 경험 없음은 결함이 아니다.** 그래서 문구도 '데이터가 부족해'로 끝내지 않는다:

| 터치 타깃 | 최소 44px (관계 칩 46px 실측) |
| 아이콘 전용 버튼 | `aria-label` 필수 |
| 토스트·로딩 | `aria-live="polite"` |
| 에러 | `role="alert"` |
| 색 단독 금지 | MATCH/GAP/CHANGE · 잘맞음/관찰필요 · 진행 단계 — **항상 텍스트를 함께 노출** |
| 포커스 | `:focus-visible` 2px outline — 색이 아니라 **형태로** 드러낸다 |
| Reduced Motion | `prefers-reduced-motion: reduce`에서 모든 CSS keyframe 정지. **꺼져도 각 단계의 최종 상태는 그대로 보인다**(정보가 사라지지 않는다) |
| 관찰 시퀀스 | 모션이 '무슨 일이 일어나는지'를 이해하는 **유일한 수단이 되면 안 된다** — 4단계를 목록으로 보여준다 |
| 승인된 줄바꿈 | `<br>`이 아니라 문장 단위 `span`(block) — 스크린리더가 한 문단을 억지로 끊어 읽지 않게 |
| 스크롤 복원 | **포커스를 옮기지 않는다.** `smooth` 미사용 |
| 앵커 이동 | 임시 `tabindex="-1"` 부여 후 포커스, blur 시 제거 |
| 한국어 줄바꿈 | `word-break: keep-all` + `text-wrap: pretty` |

### 12.1 시각 높이와 터치 영역의 분리 (v1.23)

`ResultSectionNav` 칩은 **보이는 높이 32px · 실제 터치 타깃 44px**이다.

```css
after:absolute after:inset-x-0 after:top-1/2 after:h-11 after:-translate-y-1/2
```

칩을 실제로 44px로 키우면 2줄 × 44px + gap으로 nav 한 덩어리가 100px을 넘어 LEVEL 1을
첫 viewport 밖으로 밀어낸다. 투명 `::after`로 hit area만 넓히면 시각 리듬을 유지하면서
접근성 목표(≥44px)를 만족한다. **가로는 칩 폭 그대로다** — 세로만 늘린다(gap 6px보다 넓히면
인접 칩과 겹쳐 오터치가 난다).

**실측(브라우저):** 시각 높이 32px × 5개, `::after` 높이 44px × 5개.
