## 0. 이번 UT의 핵심 신호

이전 UT 후속은 '입력이 많다 → 줄이자'였다. **이번은 반대다.**

```
"질문이 너무 얕았음. 이걸로 뭘 알겠어?"
"세부 질문이 부족했던 것 같다"
"질문이 벌써 끝났어?"
```

그래서 이번 작업의 축은 **질문을 줄이는 것도 늘리는 것도 아니고**,
틀린 근거를 막고 · 길을 명확히 하고 · 원하는 사람이 더 깊이 말할 수 있게 하는 것이다.

⚠️ 참가자 2명의 의견이다. 전체 타깃의 사실로 확대하지 않는다 — §5에 가설로 남겼다.

## 1. 관찰 → 문제 → 수정 → 검증

### P0-1 사진 오인이 관계 맥락으로 확장됐다

**관찰**
> "고양이 인형이 아님. 그리고 인형이 왜 '반려동물과 함께'에 포함되는 거임? 분석 결과가 일치하지 않음."
> (진행자) "스티치 인형을 고양이라고 인식한 것 같아요."

**문제** — 객체 인식 실패 자체가 아니다. 인식은 원래 틀린다.
**틀린 라벨 하나가 사용자 확인 없이 생활 맥락 주장으로 승격된 것**이 문제고, 그게 분석 전체의 신뢰를 깎았다.

파이프라인 audit에서 결함 셋을 찾았다.

| 단계 | source | 사용자 확인 | 결함 |
|---|---|---|---|
| 사진별 관찰 | Vision (`PHOTO_OBSERVATION_SYSTEM_PROMPT`) | 없음 | — |
| 범주 정규화 | `categorizeLabel` 키워드 | 없음 | **① `objects`의 라벨 하나가 곧장 `pet`(`반려동물과 함께`)이 됐다. confidence는 버려졌다** |
| 교차 집계 | `aggregatePhotoObservations` | 없음 | — |
| 사용자 확인 | S09 `observations[traitId]` | **여기서만** | — |
| Core 소비 | `observedItems` | 반영됨 | — |
| History 스냅샷 | `currentObservedSnapshot` | 부분 | **② `excluded`만 걸렀다. '아니야'만 누른 관찰은 기록에 남았다** |
| AI 인용 허용 | `allowedEvidence` · `contextBuilders` | 부분 | **③ `verdict:'no'`가 `unverified`로 떨어져 분석 근거로 그대로 쓰였다** |

**수정**

① **생활 맥락을 주장하는 범주는 사물 라벨로 만들지 않는다** (`observedSignals.ts`)
`pet` · `social`은 '사진에 무엇이 찍혔나'가 아니라 '이 사람이 어떻게 사는가'를 말한다. 셋을 모두 만족해야 만든다:
- 근거가 `scenes`/`activities`에 있다 (사물만으로는 안 된다)
- 같은 사진에 소품 라벨이 없다 (인형 · 피규어 · 포스터 · 화면 …)
- Provider confidence가 있으면 0.6 이상

**덜 세는 방향으로 틀린다.** 진짜 반려동물인데 Vision이 `objects`에만 적으면 범주가 안 생긴다 —
반대 방향(없는 생활 근거를 만드는 것)이 이 제품에서 더 큰 손해다.
다른 범주(등산 · 카페 · 여행 …)는 **그대로다.**

② **거절 판정을 한 곳으로 합쳤다** (`lib/logic/observationStatus.ts`)
화면 · 기록 · 근거 해석 · AI 허용 목록 · AI 입력 다섯 곳이 같은 함수를 쓴다.

③ **`ValidatedObservation`에 `rejected`를 추가했다**
예전에는 `unverified`(아직 안 물어봤다)와 구분되지 않아 분석에 그대로 들어갔다.

**검증** — `UT15-P0-01/02/03` (8건). 인형 사진 · 사물만 있는 사진 · 진짜 반려동물 사진 세 가지로
범주 생성 여부를 고정했고, 거절한 관찰이 `analysisReady` · AI 허용 목록 어디에도 없음을 확인했다.

### P0-2 분석 화면에서 길을 잃었다

**관찰**
> "분석 수정은 어떻게 하는 건지?" · "분석에 네비게이션 바 보이게."
> "(중요) 뒤로가기가 헷갈림. 뒤에 페이지가 더 있을 것 같은 느낌임."
> "이전 화면으로 가고 싶었던 거였는데 뭔가 다른 게 나왔다."

**문제** — Back 목적지가 틀린 게 아니었다(`ScreenHeader`는 이미 `useContextualBack`을 쓴다).
**결과 화면에 하단 Nav가 없었다.** `revisit`(Home · History에서 다시 열 때)에만 붙였기 때문이다.

의도는 '첫 퍼널 중에는 빠져나갈 길을 만들지 않는다'였는데, 정반대로 읽혔다.
결과 화면은 퍼널의 **중간이 아니라 끝**이다. 끝에 도착했는데 이동 수단이 Back 하나뿐이면
사용자는 그 Back을 '다음으로 가는 길'로 착각하거나 아직 단계가 남았다고 읽는다.
어떻게 도착했는지(퍼널/다시보기)는 **우리 내부 구분**이지 사용자의 문제가 아니다.

수정 진입점도 `/profile/result`에만 있었다. 분석 결과에서 내 답변이나 관계 경험을 고치려면
'나' 탭 → 프로필 → 수정까지 스스로 찾아가야 했다.

**수정**
- `/compatibility` · `/mirror` · `/profile/result` — **하단 Nav 항상 표시** (입력 화면에는 여전히 붙이지 않는다)
- 수정 허브를 `components/result/ResultEditSheet`로 빼고 결과 화면 3곳이 공유.
  **새 Route도 새 데이터 모델도 만들지 않았다** — 목적지는 전부 기존 편집 경로다.
- 헤더에 `수정` · `공유`를 나란히 둔다.

**검증** — `UT15-P0-04/05/06` + 브라우저 393×852 실측(스크린샷). Nav 4탭 · 수정 허브 6행 정상.

### P0-3 '연애 성공확률이 아니야'가 관계 상태와 안 맞았다

**관찰**
> (참가자) "그럼 연애가 아니라는 뜻인가?"

**문제** — 아직 사귀기 전 사용자에게 '이 숫자가 연애로 이어질 확률은 아니다'를 말하려던 고지인데,
**이미 연인·배우자인 사용자에게는 문장 자체가 성립하지 않는다.** 면책 문구가 오히려 관계 상태를 의심하게 만들었다.

**수정** — 관계 상태를 언급하지 않는 문장으로 바꿨다.

```
Before  연애 성공확률이 아니야
After   관계의 결과를 예측하는 점수는 아니야
```

공유 화면 문구도 같이 바꿨다. 단계별 `scoreUse` 한 줄(`stageCopy`)은 원래 관계 상태를 반영하므로 그대로다.

**검증** — `UT15-P0-08/09`. 관계 상태를 가리키는 말 7종(`연애` `연인` `커플` `부부` `배우자` `썸` `이전 관계`)이
설명에 하나도 없음을 고정했다. 393px에서 한 줄에 들어가는 것도 실측했다.

### P1-2 관계 경험 선택지에 '기타'가 없다

**관찰**
> "이전 관계 선택지에 '기타'가 있어서 입력할 수 있게 했음 좋겠음(300자)"

**적용 범위 audit** — 관계 경험 Q1~Q3 중 '기타'가 필요한 것은 **Q1 하나**다.
Q2(가장 힘들었던 순간)는 4지선다 판정값이라 자유 입력이 들어가면 축 매핑이 깨지고,
Q3에는 이미 300자 자유 서술(`experience.note`)이 있다. **모든 질문에 기계적으로 넣지 않았다.**

**수정** — `PastFactor`에 `other`를 더하고, 고른 사용자에게만 300자 칸을 연다.
자유서술 취급은 기존 `experience.note`와 **완전히 같다**(`sanitizeFreeText` · 지문은 길이만 · 새 privacy 표면 없음).

- `기타`를 고르고 비워두면 다음으로 넘어가지 않는다 — 라벨만으로는 근거가 되지 않기 때문이다.
- `기타`를 끄면 적어둔 내용도 함께 비운다 — 보이지 않는 자유서술이 저장소와 AI 입력에만 남지 않게.
- 화면 · AI · 근거 목록 어디에도 `기타` 세 글자가 나가지 않는다. 사용자가 적은 문장으로 바뀐다(`pastFactorLabels`).

**AI guard** — `SHARED_RULES`에 9번을 더했다.
```
'답장이 늦으면 서운했어'
 ⭕ '답장이 늦을 때 서운함이 커지는 편'
 ❌ '버림받을까 두려워한다' / '애착이 불안정하다' / '자존감이 낮다'
```

**검증** — `UT15-P1-04/05/07` + 브라우저 실측(칩 · 300자 카운터 · 빈 값 차단 · 저장 확인).

### P2-1 공유를 스스로 찾지 못했다

**관찰**
> "친구랑도 써보고 싶음."
> (진행자) "초반에 공유 버튼이 오른쪽 상단에 있었거든요… 너무 안 보이게 돼 있긴 해요."

**⚠️ audit에서 나온 중요한 불일치** — 진행자는 공유를
> "URL이 복사되고 상대방이 입력하면 제 화면에 결과가 떠요"

라고 설명했는데, **그 기능은 구현돼 있지 않다.** 실제 `useShare`는 결과 요약 문구를
Web Share / 클립보드로 보내고, 카드 이미지를 저장한다. URL도, 상대 답을 받아 합치는 경로도 없다.

**수정** — 새 기능을 만들지 않았다. 기존 기능을 **읽기를 마친 자리**에 한 줄 더 놓았다.
헤더 버튼은 그대로 둔다(이미 아는 사람의 경로).

```
이 결과를 친구에게 보내기
결과 카드 이미지나 요약 문구로 보낼 수 있어
```

⚠️ 라벨을 `상대의 답도 받아보기` 같은 것으로 쓰지 않았다 — **없는 기능을 라벨로 약속하지 않는다.**
이 자리는 §12('끝' 인식)도 함께 해결한다.

**검증** — `UT15-P2-01/02`.

## 4. 남은 위험

1. **참가자 2명이다.** 아래 모든 판단은 n=2에서 나왔다. 특히 '질문이 얕다'는 이전 UT의 '입력이 많다'와 방향이 반대라, 다음 UT에서 어느 쪽이 다수인지 다시 봐야 한다.
2. **심화 입력을 실제로 열지 안 열지 모른다.** 열지 않으면 이 기능은 코드만 늘린 것이 된다 — `deep_input_open` 이벤트로 본다.
3. **공유 기능에 대한 진행자/사용자의 기대가 구현보다 크다.** 상대 답을 받아 합치는 기능을 원하는 것이라면 그건 새 기능이고 이번 범위 밖이다.
4. **사진 pet 범주가 덜 잡힌다.** 진짜 반려동물 사진인데 Vision이 `objects`에만 적으면 범주가 안 생긴다. 의도한 방향이지만, 실제 빈도는 real 모드에서만 알 수 있다.
5. `declared_me_candidate` analytics가 답변 값을 property로 넘기고 sanitizer가 매번 걸러낸다(데이터는 나가지 않는다). 호출부 정리는 UT 이후 과제.
