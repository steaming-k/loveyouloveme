## 0. 표기 규칙

- **WF ID** — 화면 번호. `S01`~`S29` / `E1`~`E5` / `SH1`~`SH2`는 와이어프레임 원안 번호이고,
  `F1`·`F1-a`·`F2`·`F3`(History) · `S16a`(Adaptive) · `X1`·`X1-a`·`X1-b`(렌즈)는 v1.1 이후
  실구현에서 추가·분화된 번호다
- **Route** — 브라우저 주소 (`src/lib/routes.ts`의 `ROUTES` 상수)
- **파일** — 해당 화면의 실제 소스 경로 (`src/app/...`)
- **읽는 상태 / 쓰는 상태** — `SessionProvider`(`src/state/SessionProvider.tsx`)가 들고 있는
  `SessionAnswers`(`src/types/index.ts`) 중 이 화면이 참조·갱신하는 필드
- **그룹** — `Core`(필수 흐름) · `Key`(핵심 Product Moment) · `Edge`(예외/조건부 상태) ·
  `Future`(후속 버전 컨셉) · `Share`(공유 카드) · `Add-on`(보조 기능)
- 모든 화면은 `ScreenLayout`(`src/components/common/ScreenLayout.tsx`)의 **header / scroll body /
  sticky footer** 3단 골격을 공유한다. 화면별 설명에서는 이 골격 위에 얹히는 내용만 다룬다.

## 1. 전체 사용자 흐름 (Funnel)

```
새로운 사람에 대한 궁금증
  ↓ S01 스플래시 → S02~S04 온보딩
S05 관계 상태 선택
  ↓
S06~S18  AI Profile Building (Observed → Declared → Relationship → Relationship Profile)
  ↓        S18은 세 Source를 나열만 한다. 아직 비교하지 않는다.
S19 상대 정보 입력
  ↓
S20~S22  Compatibility (동기화율 → Compatibility Detail)
  │        S23~S25(Good/Friction/Questions)는 S22에서 링크로만 연결되는 선택 경로
  ↓
S26 Mirror Teaser  ◀── 여기서 처음으로 '나 vs 그 사람'이 아니라 '말한 나 vs 관계 속 나'를 비교한다.
  │                     Primary KPI 전환점 (relationship_mirror_entry_click / compatibility_result_view)
  ↓
S27 Relationship Mirror → S28 Core Insight
  ↓
S29 분석 후 홈  ◀── MVP 종료 지점
  ↓ (Future)
F1~F2 Relationship History
```

**제품 원칙:** 궁합 점수는 입구이고 결론이 아니다. 자기 발견(Declared vs Relationship 비교)은
서비스 전체에서 **딱 한 번**, S26에서 처음 일어나야 한다. S18에서 미리 그 결론을 말해버리면
Mirror가 '이미 본 내용의 반복'이 되므로, S18과 S26 이후는 서로 다른 코드 경로
(`buildRelationshipProfile()` vs `buildMirrorReport()`)를 쓰고 어느 쪽도 서로를 호출하지 않는다.

## 3. 공통 규칙 (전역 사양)

### 3.1 레이아웃 골격 — `ScreenLayout`

모든 화면은 세 영역으로 고정된다.

| 영역 | 규칙 |
|---|---|
| Header (flex-none) | `ScreenHeader` — 뒤로가기(←) · progress bar(선택) · 카운터(`질문 1/4` 등) · 오른쪽 액션(공유/수정 등) |
| Body (flex-1, scroll) | 좌우 여백 20px(`px-gutter`) 고정. `centered` 옵션이면 세로 중앙 정렬(스플래시·로딩·Empty·Error) |
| Footer (flex-none, sticky) | Primary CTA + 보조 액션. 하단 safe-area 26px(`pb-safe`) 항상 확보 |

스크롤이 필요한 모든 영역은 전역 CSS(`globals.css` base layer, `* { scrollbar-width: none }`)로
스크롤바만 숨기고 스크롤 동작 자체는 그대로 유지한다 — 화면마다 개별 클래스를 붙이지 않는다.

### 3.2 진행률(Progress) 표시

상단 progress bar는 **AI Profile Building 전 구간(S05~S19)에서 하나로 이어진다.**

| 화면 | 진행률 |
|---|---|
| S05 관계 상태 | 8% |
| S06 프로필 인트로 | 14% |
| S07 사진 입력 | 22% |
| S09 Observed 결과 | 30% |
| S10~S13 Declared 1~4 | 36% / 42% / 48% / 54% |
| S14 과거 관계 인트로 | 60% |
| S15~S16 과거 관계 Q1~Q2 | 66% / 72% |
| S16a Adaptive Follow-up (조건부) | 75% |
| S17 과거 관계 Q3 | 78% |
| S19 상대 정보 입력 | 88% |

S18, S21 이후(Compatibility·Mirror)는 별도 progress bar 없이 `title`/`centerLabel`만 쓴다.

### 3.3 검증 / 에러 처리 정책

`alert()`를 쓰지 않는다. 상황에 맞춰 4가지 패턴만 쓴다: 인라인 에러(`InlineError`) · 토스트
(`useToast`) · 바텀시트(`BottomSheet`) · 확인 모달(`ConfirmModal`).

### 3.4 데이터 영속성

- 세션 답변: `localStorage['lym.session.v1']` — `SessionProvider`가 마운트 시 복원, 변경마다 저장
- 분석 이벤트 로그: `localStorage['lym.analytics.v1']`
- KPI 이벤트 중복 방지 가드: `sessionStorage['lym.session_fired.*']` (§7 참고)
- **업로드 사진은 새로고침 후 세션에서 자동 제거된다.** `objectUrl`은 원래도 저장하지 않았고
  (v1.6부터는 사진을 분석에 **전송하지만 저장하지는 않는다** — §6.9.8), 예전에는 새로고침 후 남은 메타데이터가 '보이지 않는 사진'을
  유효한 것처럼 개수에 넣는 문제가 있었다. `SessionProvider`의 `deserialize()`가 복원 시점에
  `source === 'upload'` 사진을 필터링해서 없앤다 — 샘플 사진은 tone만으로 다시 그릴 수 있어 그대로
  유지한다.
- `hydrated` 플래그가 `true`가 되기 전에는 계산 결과를 보여주지 않는다 (`HydrationGate`)

### 3.5 로딩 시퀀스 공통 규칙 — `LovyLoading`

일반 스피너 하나로 끝내지 않는다. 러비의 관측 로그 4줄이 순서대로(줄당 1.1초) 쌓이고, 로그가
끝나면 자동으로 다음 화면으로 넘어간다. `prefers-reduced-motion`이면 로그를 한 번에 모두
보여주고 1.2초 뒤 넘어간다. 로딩에 실패하면(`?error=1`) 시퀀스 대신 E2 에러 화면을 보여준다.

### 3.6 접근성 공통 규칙

- 모든 선택 요소는 실제 `<input type="radio">` / `<input type="checkbox">` 기반
- 최소 터치 타깃 44px · 아이콘 전용 버튼 `aria-label` · 토스트/로딩 `aria-live` · 에러 `role="alert"`
- 게이지·상태 뱃지(MATCH/GAP/CHANGE, 잘맞음/관찰필요)는 색만으로 구분하지 않고 텍스트를 함께 노출
- `prefers-reduced-motion: reduce` 시 모든 CSS keyframe 애니메이션 정지

### 3.7 Hydration 안전장치 — `HydrationGate`

결과를 계산해서 보여주는 화면(`/compatibility`, `/mirror`, `/mirror/teaser`, `/profile/result`)은
`HydrationGate`로 감싼다. `localStorage` 복원이 끝나기 전에 렌더하면 "답변이 하나도 없는
상태"로 계산된 빈 결과가 한 프레임 스쳐 보이기 때문이다.

### 3.8 러비(Lovy) 사용 규칙

역할은 **관찰자**다. 상담가·점쟁이·전문가로 보이게 쓰지 않는다. 크게 쓰는 곳(96~200px):
Splash·Onboarding·로딩·Empty/Error·Mirror Teaser. 일반 입력 화면은 38~46px 아바타로 축소한다.

### 3.9 AI 모드 정직성 (v1.6에서 개편)

> v1.5까지는 **AI 백엔드 자체가 없었다.** v1.6에서 실제 파이프라인이 생겼으므로, 이 절은
> '가짜임을 알리는 규칙'에서 **'지금 무엇이 진짜인지 알리는 규칙'**으로 바뀌었다. 전체 구조는 §6.9.

결과의 `meta.mode`가 진실이고, 화면 배지는 그걸 그대로 따른다.

| mode | S09 배지 | 안내 |
|---|---|---|
| `real` | `AI OBSERVATION` + `근거: 사진 N/M장` | 사진 전송 사실 안내(`PRIVACY.photoTransfer`) |
| `demo` / `legacy-demo` | `DEMO AI` | 규칙 기반이며 **전송조차 없다**는 안내 |
| `fallback` | `규칙 기반 대체` | 사진 분석에 실패해 규칙으로 대체했다는 안내 |

- S07(사진 입력)에서 샘플 사진을 하나라도 선택하면 `샘플 데이터로 체험 중` 배지가 뜬다
  (샘플 타일은 실제 이미지가 아니므로 애초에 전송 대상이 아니다)
- `AI_MODE=real`인데 서버에 키가 없으면 **real이라고 표시하지 않는다** → `CONFIG_ERROR` (§6.9.3)
- `NEXT_PUBLIC_DEMO_AI` / `NEXT_PUBLIC_AI_MODE`는 첫 호출 이전 표시용 힌트일 뿐이고,
  실제 동작은 서버 `AI_MODE`가 정한다

계산값이 없을 때만 "예전에 직접 고른 별자리가 남아 있어, 생년월일을 넣어주면 다시 볼 수 있어"를
안내한다.

### 4.1 `RelationshipHistoryEntry` — 영구 데이터 (v1.3 신설)

`SessionAnswers`(진행 중인 분석)와 **완전히 분리된** 영구 기록이다. 저장소도 다르다.

```
RelationshipHistoryEntry
├─ id                     string            (crypto.randomUUID)
├─ analysisId             string            분석 입력 지문 — 중복 저장 방지 키
├─ createdAt              string            ISO
├─ context
│   ├─ relationshipStatus RelationshipStatus | null
│   └─ targetRelation     TargetRelation | null   ← 관계 '맥락'만. 상대 식별 정보 아님

**저장하지 않는 것 (§3 원칙).** 사진 원본·상대 이름·상대 사진·상대 자유서술 원문·민감정보.

`answers.experience.note`(자유서술)와 `photos`는 아예 스냅샷에 넣지 않는다.

### 4.2 History Storage

| 항목 | 값 |
|---|---|
| 저장 키 | `localStorage['lym.history.v1']` (세션 `lym.session.v1`과 분리) |
| 접근 경계 | `src/lib/historyRepository.ts`가 localStorage를 만지는 **유일한 지점**. 화면은 `HistoryProvider`의 `useHistory()`만 쓴다 |
| Repository API | `getHistory` · `getHistoryEntry` · `getLatestHistoryEntry` · `getPreviousHistoryEntry` · `hasHistoryEntryForAnalysis` · `addHistoryEntry` · `updateHistoryEntry` · `deleteHistoryEntry` · `clearHistory` · `createEntryId` |
| 정렬 | 항상 `createdAt` 오름차순(오래된 것 → 최신) |
| 손상 데이터 | 스키마가 안 맞는 항목은 복원 시 조용히 버린다 — 깨진 기록으로 화면을 터뜨리지 않는다 |
| 항목 식별 | **분석 시점(날짜)으로만** 표시한다(`src/lib/historyFormat.ts`). 상대 이름·연애 기간·'몇 번째 관계'로 라벨링하지 않는다 |

**MBTI를 `declared` 안에 넣지 않은 이유.** `DeclaredPreference`는 사용자가 직접 표현한 **관계
기준**(연락 중요도, 갈등 해결 방식 등)이고, MBTI는 별도의 **Self-described Personality Lens**다.
두 데이터를 섞으면 MBTI가 관계 기준의 하나처럼 취급되기 쉬우므로 `answers.mbti`로 분리했다.
`mbti`/`target.mbti` 모두 **Optional**이며, §6.1.1대로 동기화율·Mirror 계산에 관여하지 않는다.

**⚠️ v1.1에서 `TargetProfile`/`TargetAxisKey`/`AXIS_DEFINITIONS`에서 `talk`(대화 방식)·
`rhythm`(생활 리듬) 축을 완전히 제거했다.** 예전에는 이 두 축의 '나의 값'을 사진 관찰 고정값
(`talk=4`, `rhythm=3`)으로 하드코딩해서 계산에 넣었는데, 사용자가 실제로 준 데이터가 아니었다.
질문을 늘리는 대신(Option B) 축 자체를 뺐다 — 그래서 상대 정보 입력(S19)도 이제 6개가 아니라
4개 필드만 받는다.

> ⚠️ **아래 로직은 심리 검사나 과학적 진단이 아니다.** 입력값의 공통점·차이를 사용자가 직관적으로

### 6.1 동기화율 — **v1.1에서 공식을 다시 만들었다** (`src/lib/logic/compatibility.ts`)

**v1.0의 문제:** `score = 40 + floor(평균비율 × 52)`라는 인위적 하한선(Floor)이 있었다. 축이
다 어긋나도 최소 40점이 나와서, 실제 계산보다 궁합이 높아 보이는 착시를 줬다. 또한 `talk`(대화
방식)·`rhythm`(생활 리듬) 두 축의 '나의 값'을 사진 관찰 고정값(4, 3)으로 하드코딩해서 계산에
넣었는데, 사용자가 준 데이터가 아니었다.

**v1.1 공식 — 하한선 없음, 4개 축(contact/conflict/alone/affection)만 사용:**

```
difference    = |나의 값 - 상대의 값|                      // 둘 다 1~5 척도
axisSimilarity = 1 - (difference / 4)                       // 0~1
axisScore(%)   = round(axisSimilarity × 100)                // 표시용

score = round(
  mean(비교 가능한 축의 axisSimilarity) × 100
)
```

| 차이 | 동기화율 |
|---|---|
| 완전히 동일 | 100 |
| 1단계 차이 | 75 |
| 2단계 차이 | 50 |
| 3단계 차이 | 25 |
| 완전 반대(4단계) | 0 |

비교 가능한 축이 3개(`TARGET_MIN_KNOWN`) 미만이면 `score = null`(E3, 관측 정보 부족). '모름'
으로 남긴 축은 계산에서 완전히 빠진다. **점수 옆에는 항상 "비교 가능한 N개 신호 기준" 문구와
"연애 성공확률이 아니에요" 고지를 함께 둔다.**

내부적으로 UI 게이지(5칸)는 `alignment = round(axisSimilarity × 5)`로 0~5에 매핑해서 쓴다 —
완전 반대일 때 0칸이 되도록 재정의했다(v1.0의 `alignmentOf`는 `max(0, 5-diff)`라 diff=4에서도
1칸이 남는 오류가 있었다).

#### 6.1.1 MBTI는 동기화율에 들어가지 않는다 — **v1.2에서 되돌린 결정**

**v1.1 중간 구현의 문제:** MBTI 4글자 중 같은 글자 수를 `matches / 4`로 similarity화해서
contact/conflict/alone/affection과 **동일한 가중치**로 score 평균에 넣었다. E/I·S/N·T/F·J/P가
많이 같다고 두 사람이 더 좋은 관계를 형성한다는 의미가 아니므로, 이 방식은 '근거 없이 판정하지
않는다'는 AI 원칙과 정면으로 충돌했다. `buildMbtiDimension()`과 `mbtiSimilarity()`를 삭제했다.

**v1.2 — Main Sync Score는 다시 관계 행동 신호 4개만 사용한다:**

| 항목 | MBTI 포함 여부 |
|---|---|
| `score` 계산의 mean | ❌ |
| `comparedCount` (분모) | ❌ |
| `TARGET_MIN_KNOWN`(E3) 판단 | ❌ |
| `known_count` (S19 아는 항목) | ❌ |
| `goodSignals` / `frictionSignals` | ❌ |
| Relationship Mirror(§6.2) 판정 | ❌ |

즉 **'동기화율 55'는 오직 관계 행동 신호 기반 결과다.** MBTI를 넣거나 빼거나, 유형을 바꿔도
점수는 변하지 않는다.

#### 6.1.2 MBTI Lens — Supporting Lens (`src/lib/logic/mbtiLens.ts`)

MBTI 비교는 점수가 아니라 **대화 포인트**를 만든다. 4개 선호 지표를 각각 **독립적으로** 비교하고,
합산하지 않는다.

```
buildMbtiLens(mine, theirs)   // 둘 중 하나라도 없으면 null → 화면에서 렌즈 전체를 숨긴다
  → axes[4] : { key, eyebrow, label, mineLetter, theirsLetter, same, note }
  → sameCount / differentCount
```

| 축 | key | 글자 |
|---|---|---|
| 에너지를 회복하는 방식 | `energy` | I / E |
| 정보를 받아들이는 방식 | `information` | S / N |
| 결정할 때 먼저 보는 기준 | `decision` | T / F |
| 계획과 유연함 사이 | `lifestyle` | J / P |

> ⚠️ **표현 규칙.** 같은 글자를 '좋음', 다른 글자를 '나쁨'으로 표현하지 않는다.
> 화면 라벨은 `비슷한 성향` / `다르게 나타날 수 있는 성향` 두 가지만 쓴다.
> 금지: GOOD/BAD MATCH · 최고의 궁합 · 천생연분 · 상극 · 완벽한 조합 · MBTI 궁합 N점 · 퍼센트.
> 문장 톤은 항상 `~할 수 있어` / `~로 이야기되기도 해` / `실제로 그런지는 확인해봐`.

**관계 신호와의 관계:** MBTI로 실제 관계 신호를 *설명해버리지 않는다*. 예를 들어 갈등 방식에
실제 차이가 있고 MBTI의 `decision` 축도 다를 때, 두 현상이 같은 원인이라고 단정하지 않는다 —
Relationship Evidence가 우선이고 MBTI는 Supporting Lens다(정보 위계는 §5 S22 참고).

### 6.2 Relationship Mirror 판정 — **v1.1에서 완전히 다시 설계했다** (`src/lib/logic/mirror.ts`)

**v1.0의 문제:** 과거 관계 질문(S15~S17)은 전부 선택형이라 1~5 척도로 직접 수집된 적이 없는데도,
`toRelationshipMirrorValues()`가 `important.includes('contact') ? 4 : 2` 같은 규칙으로
Relationship Me 값을 억지로 숫자화했다. Declared(실제 척도)와 이 가짜 숫자를 빼서 MATCH/GAP/
CHANGE를 판정하니, 실제보다 정밀하게 측정된 것처럼 보이는 문제가 있었다. 또한 Declared가
미응답이면 중립값 3으로 채웠는데, Missing data를 중립으로 취급하는 것도 문제였다.

**v1.1 — 숫자를 빼지 않고, '근거의 종류'로 카테고리 판정한다:**

```
evidenceStrength(axis) =
  hardest(가장 힘들었던 순간)가 이 축과 강하게 연결됨   → 'hardest'   (가장 강한 근거)
  important(중요했던 요소)에 이 축이 포함됨              → 'important' (중간 근거)
  둘 다 아님                                             → 'absent'    (근거 없음)

state(declaredValue, strength) =
  strength='hardest' 이고 declared >= 4                  → MATCH
  strength='hardest' 이고 declared < 4                   → GAP
  strength='important' 이고 declared <= 2                → GAP
  strength='important' 이고 declared > 2                 → MATCH
  strength='absent' 이고 declared >= 4                    → CHANGE  (말했지만 근거가 안 보임)
  strength='absent' 이고 declared < 4                     → UNKNOWN (판정하지 않음)
```

`hardest`(가장 힘들었던 순간)는 `contact_drop→contact`, `fight_silence→conflict`,
`no_time→alone` 축에만 대응한다(`value_gap`은 5축 어디에도 명확히 대응하지 않아 대응表에서
뺐다).

**UNKNOWN은 `insights` 배열에 아예 포함되지 않는다** — 근거가 없는 축을 억지로 MATCH로 채우지
않기 위해서다. Mirror 헤더의 "비교 가능한 N개 기준에서"가 이 실제 판정 개수를 보여준다.

화면에는 두 숫자를 빼는 대신:
- **Declared 값**: 실제 1~5 척도로 수집된 축(`alone`, `contact`)만 `N/5`로 표시. 나머지
  (`hobby`, `conflict`, `affection`)는 3지선다를 내부 계산용으로 매핑한 값이라 숫자를 보여주지
  않고 문구만 보여준다(`declaredHasScale` 플래그)
- **Relationship 신호**: 숫자가 아니라 `relationshipSignalText()`가 만든 문장
  ("이전 관계에서 연락 감소가 가장 힘든 순간으로 선택" 등)

### 6.3 Teaser·Core Insight 축 선정

```
1순위: hardest 근거의 GAP 축
2순위: 그 외 GAP 축
3순위: CHANGE 축
4순위: 첫 번째 판정된 축 (모두 MATCH인 경우)
```

`contact` 축이 GAP으로 뽑히면 헤드라인은 고정 문구("너는 연락 자체보다...")를 쓰고, 그 외에는
`"너는 {label}에서 말한 기준보다 실제 관계에서 더 크게 반응하는 사람일지도 몰라."` 템플릿을 쓴다.

### 6.4 Adaptive Follow-up 트리거

```
pickAdaptiveTriggerAxis(declared, experience) =
  experience.skipped 면                → null
  buildInsights()로 판정한 focus 축이
  존재하고 상태가 GAP이면                → 그 축
  그 외                                  → null
```

즉 **Teaser/Core Insight의 focus 축과 Adaptive Follow-up이 물어보는 축은 항상 같다** — 그
축에 대한 이유를 미리 하나 더 받아서, S28의 근거를 더 풍부하게 만드는 구조다.

### 6.5 Relationship Profile Summary (S18)

```
declaredHighlight(declared)      // Declared 답변 중 가장 두드러지는 특징 1개 (우선순위 표)
relationshipHighlight(experience) // 관계 경험 중 가장 두드러지는 신호 1개 (hardest 우선, 없으면 important[0])

summary =
  둘 다 있으면   → "{declared 특징}, {relationship 신호}."
  하나만 있으면  → 있는 쪽만
  둘 다 없으면   → "아직 뚜렷한 특징을 관찰하기엔 정보가 조금 더 필요해."
```

두 문장은 **판정 없이 나란히 붙인다.** "~라고 답했지만 실제로는" 같은 비교·모순 표현은 이 함수
안 어디에도 없다 — Mirror(§6.2)와 코드가 완전히 분리돼 있어서 애초에 그런 문장을 만들 수 없다.

### 6.6 History Change Logic — **v1.3 신설** (`src/lib/logic/history.ts`)

> ⚠️ **Mirror State와 History Change State는 완전히 다른 축이다.**
> `Mirror (MATCH/GAP/CHANGE)` = 하나의 Snapshot 안에서 Declared vs Relationship Evidence
> `History (STABLE/SHIFT/NEW/INSUFFICIENT)` = 과거 Snapshot vs 현재 Snapshot

UI에서 비교를 계산하지 않는다 — 전부 이 파일을 거친다.

| 함수 | 역할 |
|---|---|
| `analysisFingerprint()` | 중복 저장 방지용 분석 지문 |
| `buildHistoryEntry()` | 세션 + Mirror → 저장할 Entry (불가하면 `null`) |
| `compareDeclaredSnapshots()` | **직접 1~5로 수집한 축만**(contact/alone) 값 비교 |
| `compareMirrorSnapshots()` | 축별 과거/현재 Mirror 상태 |
| `buildHistoryChanges()` | 축별 `HistoryAxisChange` |
| `getMostMeaningfulChange()` | SHIFT 우선 → NEW. 없으면 `null` |
| `buildHistorySummary()` | 러비 한 줄 요약 |
| `buildHistoryReport()` | 기록 2개 미만이면 `comparable: false` |
| `findRepeatedRelationshipSignals()` | 같은 축에서 GAP/CHANGE 반복 |
| `pastObservationFor()` | 특정 축의 Past Observation 한 줄 |

**판정 규칙**

```
pastState === null   → nowState ? 'NEW' : 'INSUFFICIENT'
nowState  === null   → 'INSUFFICIENT'        // 사라졌다고 단정하지 않는다
pastState !== nowState || declared 값이 실제로 달라짐 → 'SHIFT'
그 외                 → 'STABLE'
```

| State | Copy 규칙 |
|---|---|
| STABLE | "이전 관찰과 비슷하게 유지되고 있어." — '일관된 성격' 같은 Personality 판정 금지 |
| SHIFT | 척도 축이면 `(2/5 → 4/5)`까지 보여준다. "지난번보다 ~ 더/덜 중요하게 보고 있어." — **'성장했다' 금지** |
| NEW | "이번 관찰에서 처음 보였어." |
| INSUFFICIENT | "아직 ~ 비교할 정보가 부족해." — 판정하지 않는다 |

**척도 비교 제약.** `contact`/`alone`만 트랙 위 점으로 비교한다(직접 1~5로 수집한 값).
`conflict`/`affection`/`hobby`는 선택형이라 증감으로 말하지 않고 문장으로만 대조한다.
Relationship Evidence는 절대 숫자로 만들지 않는다.

#### 6.6.1 반복 신호 (Repeated Relationship Signal)

같은 축에서 **GAP/CHANGE가 2회 이상** 나타난 기록. MATCH는 반복 신호로 보지 않는다 —
'말한 대로 나타났다'가 되풀이되는 건 발견이 아니다.

- 기준은 **Mirror Evidence만.** MBTI 변화는 절대 반영하지 않는다
- Copy: `'이 신호… 처음 보는 게 아닌데.'` / "이 기준은 이전 관찰에서도 비슷한 신호가 있었어."
- 금지: '너는 항상 이래' / '반복되는 문제야' / '너의 연애 패턴은 이거야'

#### 6.6.2 Past Observation — Supporting Evidence

| 화면 | 위치 | 성격 |
|---|---|---|
| S27 `/mirror` | Mirror Gap Map **아래** | 반복 신호 알림 |
| S28 `/mirror/insight` | '이렇게 생각한 이유' 마지막 항목(`04`) | 근거 1줄 추가 |
| S22 `/compatibility/why` | Friction Signal **뒤**, MBTI Lens **앞** | 참고 섹션 |

> ⚠️ **Past Observation은 현재 판정을 바꾸지 않는다.**
> 현재 Mirror = 현재 데이터만 / Past History = Supporting Evidence.
> 현재 Evidence가 없으면 과거만으로 Gap을 만들지 않는다.
> 현재 분석이 이미 저장돼 있으면 그 항목은 과거에서 제외한다(자기 자신을 반복으로 세지 않는다).

**정보 위계 (§25) — S22에서 실측 확인:**
`① 실제 관계 신호 → ② 근거/상황 → ③ Past Observation → ④ MBTI Lens`
History도 MBTI도 실제 관계 신호보다 위에 오지 않고, **둘 다 동기화율 계산에 들어가지 않는다.**

### 6.7 Evidence Coverage (구 확신도)

이름을 '확신도'에서 **'관측 정보 충분/보통/부족'**으로 바꿨다. 이 값은 'AI가 얼마나 확신하는가'가
아니라 **'얼마나 많은 입력 근거가 확보됐는가'**를 뜻한다.

```
experience.skipped                                        → 부족
!(important.length >= 3 && selfGap !== null)                → 부족
note(서술)가 비어있지 않음                                    → 충분
그 외                                                        → 보통
```

자유서술을 많이 했다고 분석이 사실일 확률이 높아지는 건 아니다 — 그래서 이름을 근거량으로
한정했다.

### 6.8 Premium Architecture (v1.5) — Fake Door

> ⚠️ **실제 결제(PG)를 붙이지 않았다.** 이 버전의 목적은 '사용자가 무료 핵심 결과를 확인한 뒤,
> 더 깊은 결과를 보기 위해 실제로 결제 행동까지 시도하는가'를 측정하는 것이다.
> 설문의 지불 의향은 BM 검증이 아니므로, **결제 완료율보다 먼저 Premium Intent를 측정한다.**

#### 6.8.1 Fake Door의 정의 — 무엇을 하지 않는가

| 금지 | 이 구현에서 |
|---|---|
| 카드번호 입력 유도 후 중단 | ❌ 결제 수단을 아예 받지 않는다 |
| 결제가 가능한 것처럼 허위 표시 | ❌ '결제됩니다' 문구 없음. 구매 시도 **직후** 준비 중 공개 |
| 결제 완료 Fake 화면 | ❌ 없음 |
| 환불·구독이 있는 것처럼 표현 | ❌ `상세 분석 1회 · 구독 아님` 명시 |
| 이메일·전화번호 수집 | ❌ 알림 의향은 `notifyIntent: true` 로컬 기록만 |

흐름: **Premium CTA → 가치/가격 안내 → [상세 분석 열기] → '준비 중' 안내 → 관심 표시(선택)**

#### 6.8.2 무료 / Premium 경계

**무료에서 Core Value가 완성된다.** Premium은 무료 결과를 잘라내는 기능이 아니다.

| 영역 | FREE | PREMIUM DETAIL |
|---|---|---|
| Compatibility | 동기화율 · 비교 신호 수 · 대표 Good 1개 · 대표 Friction 1개 | 4축 전체 상세 차이 · 실제 상황 예시 · 대화 질문 · 과거 관찰 연결 |
| Mirror | 핵심 GAP/MATCH/CHANGE · Core Insight · 기본 근거 | 판정된 모든 축 상세 · Adaptive 응답 포함 심화 근거 · 과거 연결 |
| History | **저장 · 타임라인 · 기본 비교 · 삭제** | 축별 변화 상세 · 반복 신호 연결 설명 · 다음 관계 확인 기준 |
| MBTI | 4축 비교 요약 | 4축 상세 · 관계 신호와 나란히 비교할 질문 |
| Astrology | Sun Sign 기본 Lens | 태양궁 상세 · 원소 비교 확장 · 대화 주제 확장 |
| 사주 | UI·한계 안내 | **없음 (unavailable)** — 엔진이 없으므로 팔지 않는다 |

> **Guardrail.** 사용자 **본인의 저장 기록**은 무료다(§34). Premium으로 잠가서 자기 과거
> 기록을 못 보게 만들지 않는다 — 유료는 '해석의 깊이'만이다.
>
> **Premium에서도 수집하지 않은 데이터를 새로 추론하지 않는다.** 새 점수를 만들지 않는다 —
> `buildCompatibilityDetail()`은 이미 계산된 `CompatibilityResult`를 그대로 읽는다.

#### 6.8.3 Data Model

```
ResultLevel = 'summary' | 'detail'      // UI에서 잘라내지 않고 계약으로 분리

PremiumFeatureId = compatibility_detail | mirror_detail | history_detail
                 | mbti_detail | astrology_detail | saju_detail

PremiumFeature
├─ id · source · title · description · additions[]
├─ price   number | null      ← unavailable이면 null (가격을 붙이지 않는다)
└─ status  'available' | 'fake-door' | 'unavailable'    ← v1.5 기본은 fake-door

PremiumIntent                 // lym.premium-intent.v1 (세션 저장소와 분리)
└─ feature · source · price · variant · clickedAt · notifyIntent
```

`PremiumIntent`를 `SessionAnswers`에 섞지 않은 이유: 결제 상태가 분석 결과에 영향을 줄 수 없게
**구조적으로** 떼어놓기 위해서다. Compatibility·Mirror·History 로직은 이 저장소를 import하지
않는다.

#### 6.8.4 Feature Flag (`src/lib/env.ts`)

| 플래그 | 기본 | 역할 |
|---|---|---|
| `NEXT_PUBLIC_PREMIUM_FAKE_DOOR` | `true` | false면 Premium CTA 전부 숨김 + Paywall Route는 결과로 redirect |
| `NEXT_PUBLIC_PREMIUM_VARIANT` | `A` | 가격 실험. A=3,900 / B=4,900 |

| `NEXT_PUBLIC_PREMIUM_PREVIEW` | `false` | true면 `/premium-preview/[feature]` 개방(개발·UT용) |

**가격 고정 규칙(§30).** 같은 세션에서 가격이 바뀌면 안 되므로 첫 노출 시
`sessionStorage['lym.premium.variant']`에 고정하고, 새로고침·재진입에도 같은 값을 쓴다.
설문의 4,900원 이하 응답은 **검증된 가격이 아니다** — 두 후보의 의향 차이를 보기 위한 값이다.
UI에 정가·할인·이번 주만 같은 근거 없는 가격 마케팅 문구를 쓰지 않는다.

#### 6.8.5 Entry Point — 항상 Secondary

| 화면 | source | 위치 |

| S27 `/mirror` | `mirror` | 반복 신호 아래 |

> **Funnel 보호(§33).** S21 Hero 직후 강제 Paywall이 없다. S22의 Sticky Primary CTA는 여전히
> **다음 관찰 보기**(→ Mirror)이고, Premium은 본문 맨 아래 Secondary 행이다.
> Home에는 Premium 배너를 넣지 않았다 — Home의 주역은 History와 최근 관찰이다(§32).

#### 6.8.6 Paywall `/premium?source=...`

Route를 기능별로 늘리지 않고 `?source=`로 진입 지점을 구분한다 — 어디서 들어왔는지가
'무엇에 돈을 내고 싶어하는지'를 판단하는 핵심 데이터다(§31).

화면: 러비 인트로 → **무료로 본 내용**(✓ 되짚기) → **상세 분석에서 추가되는 내용** →
가격(`상세 분석 1회 · 구독 아님`) → `[상세 분석 열기]` / `[지금은 괜찮아]`

`status === 'unavailable'`이면 **Paywall을 띄우지 않는다** — 가격도 CTA도 없이 사유만 보여준다.

#### 6.8.7 Fake Door Reveal

`[상세 분석 열기]` → `premium_purchase_intent` 기록 → `premium_fake_door_reveal` →
BottomSheet: **"상세 분석은 지금 준비 중이에요"** + "방금 누른 건 결제가 아니라 관심 표시로만
기록했어" → `[출시되면 알려줘]`(선택) / `[괜찮아요]`

알림은 실제 시스템이 없으므로 **오는 것처럼 약속하지 않는다** — "지금은 알림 기능도 연결 전이라
관심 표시만 기록할게. 연락처는 받지 않아."

#### 6.8.8 개발용 Preview `/premium-preview/[feature]`

`NEXT_PUBLIC_PREMIUM_PREVIEW=true`일 때만 열린다. 일반 사용자는 Fake Door에서 이 화면에
도달하지 못한다. 상세 화면 자체를 UT·검토하기 위한 통로다.

금지: 금색 Premium · 왕관 · Countdown · '90%가 구매' · 가짜 리뷰 · 취소 버튼 숨김 ·

### 6.9 AI Analysis Pipeline (v1.6)

#### 6.9.1 가장 중요한 원칙 — 역할 분리

> **AI는 럽유럽미의 '판정자'가 아니다.**
>
> ```
> Evidence  →  Rule  →  AI Explanation  →  User Verification
> ```

| | 담당 |
|---|---|
| **Rule Logic** (deterministic) | 동기화율 점수 · Mirror MATCH/GAP/CHANGE · History STABLE/SHIFT/NEW · MBTI 축 비교 · Sun Sign · Evidence Coverage |
| **AI** | 관찰 · 정리 · 설명 · 개인화 문장 · 질문 생성 |

**AI가 생성할 수 없는 것:** Compatibility Score · Mirror State · History State · MBTI 결과 ·
Sun Sign · 사주 계산 · Premium 가격/가용성.

구조적 보장:
- `buildCompatibility()`는 AI 결과를 인자로 받지 않는다
- Mirror state는 서버에서 **규칙 값으로 덮어쓴다**(`attachRuleStates()`) — AI가 `state`를
  바꿔 보내도 무시된다
- focusAxis는 규칙이 고른다. AI가 고르지 않는다
- 실측 확인: AI 분석 결과를 통째로 조작해도 동기화율 55·신호 2/2·Mirror 판정이 불변이었다

#### 6.9.2 Architecture

```
UI (client)
  ↓  services/ai/aiClient.ts        — in-flight dedup · cache · stale 폐기 · analytics
POST /api/ai/{task}                  — Route Handler (server-only)
  ↓  app/api/ai/_shared.ts          — size limit · task allowlist · rate limit · requestId · 안전 로그
  ↓  services/ai/handlers.ts        — task 실행
  ↓  services/ai/provider.ts        — Provider 추상화 (OpenAI 호환, fetch 직접 호출)
  ↓  schemas.ts → safety.ts          — Schema Parse → Business Validation → 금지 추론 스캔
UI
```

| 파일 | 역할 |
|---|---|
| `services/ai/serverEnv.ts` | **server-only.** API Key·모델·타임아웃 |
| `services/ai/provider.ts` | Provider 인터페이스 + OpenAI 호환 구현. SDK 의존성 0 |
| `services/ai/promptTemplates.ts` | 버전 관리된 프롬프트 + 공통 System 원칙 |
| `services/ai/contextBuilders.ts` | Task별 최소 컨텍스트 (Data Minimization) |
| `services/ai/schemas.ts` | 손으로 쓴 검증 (프로젝트 관례 — zod 미도입) |
| `services/ai/safety.ts` | injection delimit + 금지 추론 스캔 |
| `services/ai/fallback.ts` | demo/fallback 결과 + Evidence Coverage 판정 |
| `services/ai/aiClient.ts` | 화면과 내부 API 사이의 유일한 통로 |
| `services/ai/imagePrep.ts` | 이미지 축소·검증 + 입력 지문 |

**API Key는 서버에만 있다.** `NEXT_PUBLIC_` prefix를 쓰지 않고, `serverEnv.ts`는 `server-only`를
import하므로 클라이언트에서 import하면 빌드가 실패한다.

#### 6.9.3 AI Mode

| mode | 의미 |
|---|---|
| `real` | 실제 Provider 응답 |
| `demo` | Provider 미호출. 규칙 기반 결과 (기본값 · 포트폴리오/로컬) |
| `fallback` | real을 시도했지만 실패 → 규칙 결과로 대체. **화면에 표시한다** |
| `legacy-demo` | v1.5 이전 세션에서 복원 |

실제 동작 모드는 **서버**(`AI_MODE`)가 결정하고, 결과의 `meta.mode`가 진실이다.
`NEXT_PUBLIC_AI_MODE`는 첫 호출 이전 배지 표시용 힌트일 뿐이다.

`AI_MODE=real`인데 키가 없으면 **real이라고 우기지 않는다** → `CONFIG_ERROR`.
실측: 키 없이 real 모드로 호출하면 `{"ok":false,"reason":"CONFIG_ERROR"}` — 가짜 결과를 만들지 않는다.

#### 6.9.4 Structured Output + 2단 검증

자유 텍스트 하나로 받지 않는다. 모든 Task가 JSON 스키마를 강제하고 **2단**으로 검증한다.

**① Schema Parse** — 타입·길이·enum·허용 id 검사
**② Business Validation** — 스키마는 맞지만 제품 규칙을 위반한 응답 처리

| 위반 | 처리 |
|---|---|
| Evidence 없는 Trait | **버린다** (§10) |
| 입력에 없는 `imageId` 참조 | 그 evidence를 버린다 |
| `confidence: high`인데 evidence 1개 | `medium`으로 **강등** (사진 1장 단정 금지) |
| 규칙이 판정하지 않은 축 | 버린다 |
| 현재 궁합에 없는 dimension | 버린다 |
| 강한 결론 + evidenceRefs 0개 + uncertainty 없음 | 버린다 (§91) |
| AI가 보낸 `state`/`kind` | **규칙 값으로 덮어쓴다** |
| **(v1.7)** Core 설명에 MBTI·사주·별자리 언급 | 버린다 — Core Task에 그 데이터를 보내지도 않았다(§36) |
| **(v1.7)** History에 성장·극복·좋아졌다 서사 | 버린다 (§27) |
| **(v1.7)** 표시 길이 초과 | **버리지 않고** 문장 경계에서 자른다(§37) |

> **v1.7에서 메운 구멍 두 개.**
> ① `성장 서사 금지`는 프롬프트에만 있고 **검사 장치가 없었다.**
>    '상처를 겪으며 성장해서 안정적인 사람이 됐어'는 민감 추론도 마음 읽기도 아니라서 기존 패턴을
>    전부 통과했다. `scanHistoryNarrative`로 막았다.
> ② `상대 마음 읽기` 패턴이 **주어와 동사가 붙어 있을 때만** 걸렸다.
>    '상대는 너를 **더** 좋아하고 있어서'가 통과하고, '상대가 서운해할 수 있어'는 목록에 없었다.
>    한 절 안에서 감정·의도 동사를 찾도록 고쳤다.
>    단 '상대가 어떻게 느낄지는 알 수 없어'처럼 **모른다고 말하는 문장은 의도적으로 남겼다** —
>    그건 마음 읽기가 아니라 정직한 한계 진술이다.

#### 6.9.5 Observed Me — 사진 분석

**추론 가능:** 반복 활동 · 장소 유형 · 스포츠 · 음식 · 여행 · 실내외 활동 · 등장 인물 수 ·
취미 물체 · 반려동물 · 일상 활동

**절대 추론 금지:** 성적 지향 · 정치 · 종교 · 정신건강 · 질병 · 장애 · 경제 수준 · 범죄성 ·
성생활 · 임신 · 민족 기반 성향 · 관계의 질 · 특정 인물과의 관계 · 상대 감정 · MBTI · 애착유형

**사람 분석 금지:** 얼굴 점수 · 매력도 · 외모 등급 · 나이 추정 · 체형 평가

프롬프트가 1차 방어이고, `safety.ts`의 11개 패턴 스캔이 최후 방어선이다. 걸린 trait은
통째로 버리고 "사진에서 추론하지 않기로 한 항목이 있어서 일부 관찰은 제외했어"를 한계에 남긴다.

**Evidence Coverage는 코드가 판정한다**(§11) — AI가 '충분하다'고 말하게 하지 않는다.
사진 장수가 아니라 실제로 쓸 만한 근거 수를 본다. 배지도 `근거: 사진 2/8장`처럼 실측을 쓴다.

**Trait 0개는 실패가 아니다**(§62) — '반복되는 신호를 못 찾았다'는 정상 상태이고, 개수를 채우려고
약한 관찰을 만들지 않는다. 최대 6개.

#### 6.9.6 User Correction 우선순위

```
USER CORRECTION  >  CONFIRMED AI  >  UNVERIFIED AI       (excluded는 제거)
```

**AI Original을 덮어쓰지 않는다**(§13). `ValidatedObservation`이 `original`과 `userCorrection`을
분리 보관하고, 화면도 "러비의 원래 관찰: …"을 함께 보여준다.

이후 분석 컨텍스트에는 `source: 'user' | 'ai'`를 함께 넘겨 AI가 무엇이 사용자 말인지 알게 한다.

> ⚠️ 기존 문구 **'사진은 브라우저 안에서만 쓰이고 서버로 보내지 않아요'는 실제 Vision을
> 붙이면서 거짓이 됐다.** 전수 검색해 수정했다.

| 위치 | 변경 |

우리 서비스가 하는 일(원본 미저장)만 말한다. 사진 원본은 요청 처리 후 메모리에서 사라지고,
세션에는 관찰 결과와 evidence metadata만 남는다.

#### 6.9.9 Failure / Fallback

| reason | 사용자에게 보이는 말 |
|---|---|
| `NETWORK_ERROR` | 사진을 읽다가 통신이 끊겼어 |
| `TIMEOUT` | 관찰이 생각보다 오래 걸리네 |
| `INVALID_OUTPUT` | 관찰 결과를 제대로 읽지 못했어 |
| `POLICY_BLOCK` | 이 사진들로는 분석을 진행할 수 없었어 |
| `NO_USABLE_IMAGE` | 분석에 쓸 수 있는 사진이 없었어 |
| `RATE_LIMIT` | 요청이 조금 몰렸어 |
| `SERVER_ERROR` | 관측 장비에 문제가 생겼어 |
| `CONFIG_ERROR` | 아직 분석 연결이 준비되지 않았어 |

기술 오류코드를 그대로 보여주지 않는다. 2회 이상 실패하면 "사진 관찰은 건너뛰고 질문으로
이어가도 괜찮아"를 덧붙인다 — **사진 분석 실패가 Core Funnel을 막지 않는다**(§63).

#### 6.9.10 AI Call Matrix (v1.7 — 전부 배선 완료)

| Task | Trigger | Input | Output | Cache Key | Fallback | Blocking |
|---|---|---|---|---|---|---|
| observed-profile | S08 진입 | 축소 이미지 + imageId | traits + coverage | photo fingerprint | demo/fallback 결과 | **blocking** |
| relationship-insight | **S26 prefetch** → S27/S28 | 규칙 판정 + focusAxis + 검증된 관찰 | narrative[] + core | relationship fingerprint | 기존 템플릿 headline | **non-blocking** |
| compatibility-narrative | **S22 진입** (S23/S24/S25 재사용) | 계산된 dimensions + kind | narrative[] | compatibility fingerprint | 기존 evidence/scene | **non-blocking** |
| history-insight | **F2 진입 (lazy)** | 규칙 변화 판정 | narrative[] | history fingerprint | 기존 note | **non-blocking** |

**화면당 호출 수는 최대 1회다**(§39). 같은 지문이면 캐시를 읽고, 여러 화면이 같은 Task를
공유한다:

| 화면 | 읽는 Narrative | 새로 호출하는가 |
|---|---|---|
| S22 궁합 상세 | compatibility | ⭕ (첫 진입) |
| S23 / S24 / S25 | compatibility | ❌ 캐시 |
| S26 Teaser | relationship | ⭕ **prefetch만** (화면에는 안 쓴다) |
| S27 Mirror | relationship | ❌ 캐시 |
| S28 Core Insight | relationship | ❌ 캐시 |
| F2 변화 리포트 | history | ⭕ (lazy) |
| F1 / F1-a / F3 | — | ❌ **호출하지 않는다** |

> **F1·F1-a·F3에서 호출하지 않는 이유(§31/§70).** 이 화면들은 **과거 Entry**를 보여준다.
> 과거 기록에 새 프롬프트로 만든 설명을 덧붙이면 그건 '그때의 관찰'이 아니다.
> 새 Narrative는 '이전 기록 vs 최신 기록'이라는 **현재 비교**(F2)에서만 만든다.

> **S26에서 prefetch하지만 쓰지 않는 이유(§61 + §88-6).**
> S26에 도달하면 focusAxis·Mirror state·evidence가 이미 계산 가능하므로 미리 만들어둘 수 있다.
> 하지만 Aha Moment는 S26의 deterministic 비교 그대로여야 한다 — AI 문장이 Teaser에 끼어들면
> 제품의 첫 발견 순간이 'AI가 말해준 것'으로 바뀐다. 그래서 **호출만 하고 화면은 건드리지 않는다.**

#### 6.9.11 Narrative 공통 구조 (§6)

Task마다 임의 형태로 흩어지지 않게 공통 봉투를 둔다.

```
AiNarrativeMeta  = AiAnalysisMeta + requestId?
GroundedNarrative = { explanation, evidenceRefs, uncertainty? }

CompatibilityNarrativeBundle = { narratives[], meta }
RelationshipNarrativeBundle  = { narratives[], core, meta }
HistoryNarrativeBundle       = { narratives[], meta }

AiNarrativeState<T> = { status, data, reason, mode }
  status: 'idle' | 'loading' | 'ready' | 'unavailable'
```

> `unavailable`은 **실패가 아니다.** 'AI 설명 없이 규칙 결과만 보여주는 정상 상태'다.
> demo 모드에서도 이 상태이고, 이때는 화면에 아무 고지도 하지 않는다 —
> 사용자 입장에서 달라진 게 없기 때문이다. **real을 시도했다가 실패한 경우만 알린다**(§15).

#### 6.9.12 Evidence Resolver (§34 · §35 · §73~§75)

> **AI가 근거 문장을 써서 보여주지 않는다.**
> AI는 `EvidenceRef`로 **어디를 봤는지만 지목**하고, 화면에 보이는 근거 텍스트는
> `src/lib/aiEvidenceResolver.ts`가 **실제 세션 데이터에서** 만든다.
> 그래서 AI가 근거를 그럴듯하게 지어내도 UI에 도달할 수 없다.

| ref.source | 화면 라벨 | 텍스트 출처 |
|---|---|---|
| `declared` | 내가 답한 내용 | 실제 선택한 답변 |
| `relationship` | 관계 경험 | 실제 고른 항목 라벨 |
| `adaptive` | 추가 질문 | 실제 고른 옵션 라벨 |
| `observed` (수정 없음) | 사진에서 관찰 | AI 원본 관찰 문장 |
| `observed` (**수정됨**) | **사용자 수정** | **사용자가 고친 문장** |
| `history` | 과거 관찰 | 그 Entry의 snapshot |

**신뢰 우선순위(§74)** — 뒤집히지 않는다:
```
USER DIRECT INPUT > USER CORRECTION > RELATIONSHIP EXPERIENCE
  > AI OBSERVATION > PAST AI OBSERVATION
```

**§75 실측 확인.** AI가 '야외 활동을 좋아하는 것 같아'로 관찰하고 사용자가
'사진은 여행 갔을 때만 찍어서 그렇게 보인 거고 평소엔 집에 있는 걸 좋아해'로 고친 경우 →
근거 목록에 `사용자 수정`으로 **고친 문장만** 표시되고, AI 원본은 화면에 나타나지 않았다.

**§35 유효하지 않은 ref는 렌더하지 않는다.** 현재 세션에 없는 필드·삭제된 Entry·사용자가
제외한 관찰은 조용히 빠진다. 유효한 근거가 하나도 없고 `uncertainty`도 없으면
**Narrative 자체를 보여주지 않는다**(`narrativeIsShowable`).

#### 6.9.13 AI Mode — `mock` 추가 (v1.7)

| mode | Provider 호출 | 검증 단계 | 표시 |
|---|---|---|---|
| `real` | ⭕ | 전부 통과 | `AI 설명` |
| `mock` | ❌ (고정 응답) | **전부 통과** | **`MOCK AI`** |
| `demo` | ❌ | — (Narrative 미생성) | 고지 없음 |
| `fallback` | 시도 후 실패 | — | `규칙 기반 대체` |

`mock`은 **개발 전용**이다. Provider Key 없이 배선·Resolver·규칙 덮어쓰기·캐시를
실제 코드 경로로 확인하려고 만들었다.

- 검증을 **우회하지 않는다** — 파싱·Business Validation·Safety Scan을 그대로 통과해야 화면에 닿는다
- 규칙 값을 일부러 뒤집어 보낸다(`GAP`→`MATCH`, `good`→`friction`) — 덮어쓰기가 실제로
  동작하는지 확인하기 위해서다
- `NODE_ENV=production`이면 **강제로 demo로 내려간다** (실측 확인)
- 결과 `meta.mode='mock'`이므로 real인 척하지 않는다

> ⚠️ **mock 통과는 실제 Provider 검증이 아니다.** 실제 응답의 형식 편차·거절·지연·토큰 한계는
> 여기서 재현되지 않는다. 문서가 `Real Provider E2E = Not Verified`를 유지하는 이유다(§93).

#### 6.9.14 Cache / Invalidation (§8 · §42)

각 Narrative는 **자기 입력이 바뀔 때만** 다시 생성된다 (`src/lib/aiFingerprint.ts`).

| 변경된 것 | compatibility | relationship | history |
|---|---|---|---|
| Declared 답변 | 🔄 재생성 | 🔄 재생성 | — |
| Target 정보 | 🔄 재생성 | — | — |
| Relationship Experience | — | 🔄 재생성 | — |
| Observed 확인/수정/제외 | — | 🔄 재생성 | — |
| History Entry 추가 | — | — | 🔄 재생성 |
| **MBTI** | ❌ 유지 | ❌ 유지 | ❌ 유지 |
| **Birth Profile** | ❌ 유지 | ❌ 유지 | ❌ 유지 |
| **Premium 의향 / 가격 variant** | ❌ 유지 | ❌ 유지 | ❌ 유지 |

> MBTI·출생정보·Premium은 **지문 함수의 인자에 애초에 없다** — '넣지 않기로 했다'가 아니라
> 구조적으로 넣을 수 없다. Lens를 만지작거려서 Core 설명이 재생성되면 위계가 무너진다.
> 자유서술(`note`)은 **길이만** 지문에 넣는다 — 지문에 사용자 문장을 남기지 않기 위해서다.

#### 6.9.18 Cost / Performance

- 이미지 장변 **1024px · JPEG 0.8**로 축소해 전송 (활동·장소 판단은 유지, 요청 크기는 크게 감소)
- 개당 1.2MB · 최대 9장 상한. 초과·손상·0바이트는 조용히 건너뛰고 한계에 알린다
- 샘플 타일은 실제 이미지가 아니라 **전송 대상이 아니다**
- `S08`은 최소 연출 시간과 실제 요청 완료를 **둘 다** 만족해야 이동한다(§74) —
  예전에는 애니메이션이 끝나면 결과와 무관하게 넘어갔다
- 중복 호출 방지: in-flight map + 세션 캐시 + `useRef` 가드 (StrictMode·리렌더·back navigation)
- stale 응답 폐기: 입력 지문이 바뀌면 늦게 온 응답이 새 결과를 덮지 않는다(§55)

#### 6.9.19 Security

| 항목 | 처리 |
|---|---|
| API Key | server-only. 클라이언트 번들 미포함 |
| 요청 크기 | `AI_MAX_REQUEST_BYTES`(기본 12MB) 초과 시 거부 |
| MIME | jpeg/png/webp만. data URL 형식 검증 |
| Task allowlist | 4개 고정 |
| Prompt Injection | 사용자 데이터를 `<user_data>` 블록으로 delimit + 태그 위조 무력화 + 제어문자 제거 |
| Provider 원문 에러 | 클라이언트 미노출. `AiFailureReason`으로만 분류 |
| Rate Limit | 세션/IP당 12회/분. **실측 확인** (13번째부터 RATE_LIMIT) |
| 로그 | requestId·task·duration·status만. **이미지·자유서술·birth data 금지** |

> ⚠️ **Rate Limit 한계 명시.** 인스턴스 메모리 기반이라 서버리스 다중 인스턴스에서는 정확하지 않다.
> 계정 시스템이 없어 완전한 보호도 불가능하다. 실서비스 전환 시 공유 저장소 기반으로 교체해야 한다
> (`_shared.ts`에 TODO 남김).

|---|---|
| Premium CTR | `premium_entry_click / premium_entry_view` |
| Paywall Intent Rate | `premium_purchase_intent / premium_paywall_view` |
| Notify Intent Rate | `premium_notify_intent / premium_fake_door_reveal` |

`source`별로 나눠 보면 **무엇에 돈을 내고 싶어하는지**를 판단할 수 있다
(compatibility / mirror / history / mbti / astrology).

> **BM 검증 상태.** 이 Funnel로 얻는 것은 **Fake Door 행동 데이터(FACT)**뿐이다.
> **실제 결제 전환은 아직 HYPOTHESIS**다 — 결제가 붙기 전까지 검증됐다고 말하지 않는다.
> 목표 수치는 만들지 않는다.

### 7.4 Entertainment Lens 지표 (v1.4)

Primary KPI는 **변경하지 않았다.** Entertainment Lens는 Optional이므로 별도 지표로만 본다.

```
Birth Info Completion Rate = birth_profile_complete / entertainment_lens_entry_click
Entertainment Lens View Rate = (saju_lens_view + astrology_lens_view) / compatibility_result_view
Saju Lens View Rate         = saju_lens_view / compatibility_result_view
Astrology Lens View Rate    = astrology_lens_view / compatibility_result_view
Lens → Question Save Rate   = lens_conversation_question_save / (saju + astrology lens_view)
```

> `lens_zodiac_set`은 v1.4에서 deprecated다 — 별자리 직접 선택이 생년월일 기반 계산으로
> 대체됐다. 이벤트 상수는 기존 로그 호환을 위해 남겨두되 새로 발생시키지 않는다.

### 7.5 History Retention 지표 (v1.3)

Primary KPI는 **변경하지 않았다.** History는 별도 Retention Metric으로만 본다.

```
History Save Rate     = relationship_history_entry_created / relationship_mirror_complete
History Revisit Rate  = History 보유 사용자 중 /history 재방문 비율
Repeat Analysis Rate  = 두 번째 Mirror 생성 사용자 / 첫 Mirror 완료 사용자
```

> 목표 수치(Target Value)는 아직 만들지 않는다 — 실제 사용 데이터를 본 뒤 정한다.

### 7.6 MBTI Supporting 지표

MBTI는 Optional이므로 **Primary Funnel KPI에는 넣지 않는다.** Primary KPI는 그대로 유지하고,
아래 두 개만 보조로 관찰한다.

```
MBTI 입력률       = both_mbti_available / compatibility_result_view
MBTI Lens 조회율  = mbti_lens_view      / both_mbti_available
```
