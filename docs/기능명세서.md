> 이 문서는 **실제 구현된 코드**를 기준으로 작성됐다. 기획 의도가 궁금하면
> [`럽유럽미_기획서_v1.md`](./럽유럽미_기획서_v1.md), 톤·컬러·컴포넌트 규칙이 궁금하면

> 프로젝트 루트의 [`README.md`](../README.md)를 함께 참고한다.

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.1 (Product Logic / UX Refinement 반영) |
| 작성 기준 | Next.js 15 App Router, `src/app/**/page.tsx` 29개 Route |
| 대상 독자 | PM, 디자이너, 신규 합류 개발자, 포트폴리오 리뷰어 |
| Source of Truth | `럽유럽미 와이어프레임.zip` (S01~S29 + Edge/Future/Share/Add-on) — 단, 아래 표시된 항목은 v1.1에서 와이어프레임 원안을 넘어 Product Logic 신뢰성 문제를 고치며 의도적으로 갈라진 부분이다 |

**v1.1에서 바뀐 것 (v1.0 대비)**

- S18(Relationship Profile)이 더 이상 Declared vs Relationship을 비교하지 않는다 — 그 비교는 S26부터 처음 등장한다
- 동기화율 계산에서 인위적 하한선(40~92)과 하드코딩 축(talk/rhythm)을 제거했다
- Relationship Mirror가 더 이상 숫자를 지어내지 않는다 — Evidence Signal 기반 카테고리 판정으로 바뀌었다
- Adaptive Follow-up(모순 후보 축에 한해 질문 1개 추가) 신설
- Compatibility Main Flow가 6화면→3화면으로 단축됐다 (Good/Friction/Questions는 Optional Detail로)
- Primary KPI 분모가 `compatibility_complete` → `compatibility_result_view`(세션당 1회 dedup)로 바뀌었다
- Relationship Mirror의 '진입(view)'과 '완료(complete)' 이벤트가 분리됐다
- 관계 상태(S05) 캡션이 실제로 지원하는 범위만 정직하게 말한다
- 관계 경험 없음(experience.skipped) 사용자에게는 Mirror 대신 전용 안내를 보여준다 — 가짜 비교를 만들지 않는다
- '확신도' 명칭을 '관측 정보 충분/보통/부족'으로 바꿨다 (AI의 확신이 아니라 입력 근거량을 뜻하므로)
- Demo AI 배지, 사진 새로고침 무효화 처리, HEIC 미지원 명시, 데이터 전체 삭제 기능 추가

## 0. 표기 규칙

- **WF ID** — 와이어프레임 화면 번호 (`S01`~`S29`, `E1`~`E4`, `F1`~`F2`, `SH1`~`SH2`, `X1`)
- **Route** — 브라우저 주소 (`src/lib/routes.ts`의 `ROUTES` 상수)
- **파일** — 해당 화면의 실제 소스 경로 (`src/app/...`)
- **읽는 상태 / 쓰는 상태** — `SessionProvider`(`src/state/SessionProvider.tsx`)가 들고 있는
  `SessionAnswers`(`src/types/index.ts`) 중 이 화면이 참조·갱신하는 필드
- **그룹** — `Core`(필수 흐름) · `Key`(핵심 Product Moment) · `Edge`(예외/조건부 상태) ·
  `Future`(후속 버전 컨셉) · `Share`(공유 카드) · `Add-on`(보조 기능)
- 모든 화면은 `ScreenLayout`(`src/components/common/ScreenLayout.tsx`)의 **header / scroll body /
  sticky footer** 3단 골격을 공유한다. 화면별 설명에서는 이 골격 위에 얹히는 내용만 다룬다.

## 1. 전체 사용자 흐름 (Funnel)

```
새로운 사람에 대한 궁금증
  ↓ S01 스플래시 → S02~S04 온보딩
S05 관계 상태 선택
  ↓
S06~S18  AI Profile Building (Observed → Declared → Relationship → Relationship Profile)
  ↓        S18은 세 Source를 나열만 한다. 아직 비교하지 않는다.
S19 상대 정보 입력
  ↓
S20~S22  Compatibility (동기화율 → Compatibility Detail)
  │        S23~S25(Good/Friction/Questions)는 S22에서 링크로만 연결되는 선택 경로
  ↓
S26 Mirror Teaser  ◀── 여기서 처음으로 '나 vs 그 사람'이 아니라 '말한 나 vs 관계 속 나'를 비교한다.
  │                     Primary KPI 전환점 (relationship_mirror_entry_click / compatibility_result_view)
  ↓
S27 Relationship Mirror → S28 Core Insight
  ↓
S29 분석 후 홈  ◀── MVP 종료 지점
  ↓ (Future)
F1~F2 Relationship History
```

**제품 원칙:** 궁합 점수는 입구이고 결론이 아니다. 자기 발견(Declared vs Relationship 비교)은
서비스 전체에서 **딱 한 번**, S26에서 처음 일어나야 한다. S18에서 미리 그 결론을 말해버리면
Mirror가 '이미 본 내용의 반복'이 되므로, S18과 S26 이후는 서로 다른 코드 경로
(`buildRelationshipProfile()` vs `buildMirrorReport()`)를 쓰고 어느 쪽도 서로를 호출하지 않는다.

## 3. 공통 규칙 (전역 사양)

### 3.1 레이아웃 골격 — `ScreenLayout`

모든 화면은 세 영역으로 고정된다.

| 영역 | 규칙 |
|---|---|
| Header (flex-none) | `ScreenHeader` — 뒤로가기(←) · progress bar(선택) · 카운터(`질문 1/4` 등) · 오른쪽 액션(공유/수정 등) |
| Body (flex-1, scroll) | 좌우 여백 20px(`px-gutter`) 고정. `centered` 옵션이면 세로 중앙 정렬(스플래시·로딩·Empty·Error) |
| Footer (flex-none, sticky) | Primary CTA + 보조 액션. 하단 safe-area 26px(`pb-safe`) 항상 확보 |

스크롤이 필요한 모든 영역은 전역 CSS(`globals.css` base layer, `* { scrollbar-width: none }`)로
스크롤바만 숨기고 스크롤 동작 자체는 그대로 유지한다 — 화면마다 개별 클래스를 붙이지 않는다.

### 3.2 진행률(Progress) 표시

상단 progress bar는 **AI Profile Building 전 구간(S05~S19)에서 하나로 이어진다.**

| 화면 | 진행률 |
|---|---|
| S05 관계 상태 | 8% |
| S06 프로필 인트로 | 14% |
| S07 사진 입력 | 22% |
| S09 Observed 결과 | 30% |
| S10~S13 Declared 1~4 | 36% / 42% / 48% / 54% |
| S14 과거 관계 인트로 | 60% |
| S15~S16 과거 관계 Q1~Q2 | 66% / 72% |
| S16a Adaptive Follow-up (조건부) | 75% |
| S17 과거 관계 Q3 | 78% |
| S19 상대 정보 입력 | 88% |

S18, S21 이후(Compatibility·Mirror)는 별도 progress bar 없이 `title`/`centerLabel`만 쓴다.

### 3.3 검증 / 에러 처리 정책

`alert()`를 쓰지 않는다. 상황에 맞춰 4가지 패턴만 쓴다: 인라인 에러(`InlineError`) · 토스트
(`useToast`) · 바텀시트(`BottomSheet`) · 확인 모달(`ConfirmModal`).

### 3.4 데이터 영속성

- 세션 답변: `localStorage['lym.session.v1']` — `SessionProvider`가 마운트 시 복원, 변경마다 저장
- 분석 이벤트 로그: `localStorage['lym.analytics.v1']`
- KPI 이벤트 중복 방지 가드: `sessionStorage['lym.session_fired.*']` (§7 참고)
- **업로드 사진은 새로고침 후 세션에서 자동 제거된다.** `objectUrl`은 원래도 저장하지 않았지만
  (사진을 서버로 보내지 않는다는 원칙), 예전에는 새로고침 후 남은 메타데이터가 '보이지 않는 사진'을
  유효한 것처럼 개수에 넣는 문제가 있었다. `SessionProvider`의 `deserialize()`가 복원 시점에
  `source === 'upload'` 사진을 필터링해서 없앤다 — 샘플 사진은 tone만으로 다시 그릴 수 있어 그대로
  유지한다.
- `hydrated` 플래그가 `true`가 되기 전에는 계산 결과를 보여주지 않는다 (`HydrationGate`)

### 3.5 로딩 시퀀스 공통 규칙 — `LovyLoading`

일반 스피너 하나로 끝내지 않는다. 러비의 관측 로그 4줄이 순서대로(줄당 1.1초) 쌓이고, 로그가
끝나면 자동으로 다음 화면으로 넘어간다. `prefers-reduced-motion`이면 로그를 한 번에 모두
보여주고 1.2초 뒤 넘어간다. 로딩에 실패하면(`?error=1`) 시퀀스 대신 E2 에러 화면을 보여준다.

### 3.6 접근성 공통 규칙

- 모든 선택 요소는 실제 `<input type="radio">` / `<input type="checkbox">` 기반
- 최소 터치 타깃 44px · 아이콘 전용 버튼 `aria-label` · 토스트/로딩 `aria-live` · 에러 `role="alert"`
- 게이지·상태 뱃지(MATCH/GAP/CHANGE, 잘맞음/관찰필요)는 색만으로 구분하지 않고 텍스트를 함께 노출
- `prefers-reduced-motion: reduce` 시 모든 CSS keyframe 애니메이션 정지

### 3.7 Hydration 안전장치 — `HydrationGate`

결과를 계산해서 보여주는 화면(`/compatibility`, `/mirror`, `/mirror/teaser`, `/profile/result`)은
`HydrationGate`로 감싼다. `localStorage` 복원이 끝나기 전에 렌더하면 "답변이 하나도 없는
상태"로 계산된 빈 결과가 한 프레임 스쳐 보이기 때문이다.

### 3.8 러비(Lovy) 사용 규칙

역할은 **관찰자**다. 상담가·점쟁이·전문가로 보이게 쓰지 않는다. 크게 쓰는 곳(96~200px):
Splash·Onboarding·로딩·Empty/Error·Mirror Teaser. 일반 입력 화면은 38~46px 아바타로 축소한다.

### 3.9 Demo AI 정직성 — `IS_DEMO_AI` (`src/lib/env.ts`)

실제 AI Vision/LLM 백엔드가 아직 없다. `NEXT_PUBLIC_DEMO_AI` 환경변수가 `'false'`가 아닌 한
(기본값) `IS_DEMO_AI = true`이며, 이때:

- S07(사진 입력)에서 샘플 사진을 하나라도 선택하면 `샘플 데이터로 체험 중` 배지가 뜬다
- S09(Observed Me 결과)에는 항상 `DEMO AI` 배지 + `PRIVACY.demoAi` 안내
  ("AI 분석은 데모용 규칙 기반 응답이에요. 실제 사진 내용을 분석하지 않아요.")가 붙는다 — 업로드한
  실제 사진이든 샘플이든, 실제로 이미지 내용을 분석하지 않는다는 사실을 숨기지 않는다

실제 백엔드가 붙으면 `NEXT_PUBLIC_DEMO_AI=false`로 이 배지들만 끌 수 있다.

## 4. 데이터 모델 (`SessionAnswers`)

```
SessionAnswers
├─ status              RelationshipStatus | null            (S05)
├─ photos               PhotoAsset[]                          (S07)
├─ observations          Record<traitId, ObservationFeedback>  (S09)
├─ declared              DeclaredPreference                    (S10~S13)
│   ├─ contact  1~5 | null
│   ├─ conflict 'now'|'soon'|'space' | null
│   ├─ alone    1~5 | null
│   ├─ affection 'a1'|'a2'|'a3' | null
│   └─ hobby     'h1'|'h2'|'h3' | null
├─ experience            RelationshipExperience                (S15~S17, S16a, E4)
│   ├─ important  PastFactor[] (최대 4개)
│   ├─ hardest    HardestMoment | null
│   ├─ selfGap    'yes'|'some'|'no' | null
│   ├─ note       string (선택, 최대 300자)
│   ├─ skipped    boolean  (E4 경로)
│   └─ adaptive   { axis: MirrorAxisKey; optionId: string } | null   (S16a, 조건부)
├─ target                TargetProfile                         (S19)
│   ├─ relation  'crush'|'friend'|'work'|'intro' | null
│   └─ contact/conflict/alone/affection: 'l'|'m'|'h'|'x'  (4축 — talk/rhythm은 v1.1에서 제거)
├─ savedQuestions        TargetAxisKey[]                        (S25)
├─ coreVerdict            'ok'|'no'|null                        (S28)
├─ coreCorrection         string                                 (S28)
├─ share                 { includeTargetInfo, includeDimensionScores } (SH1)
└─ completed              { onboarding, observed, declared, experience,
                             profile, compatibility, mirror }  — 진행 상태 플래그
```

**⚠️ v1.1에서 `TargetProfile`/`TargetAxisKey`/`AXIS_DEFINITIONS`에서 `talk`(대화 방식)·
`rhythm`(생활 리듬) 축을 완전히 제거했다.** 예전에는 이 두 축의 '나의 값'을 사진 관찰 고정값
(`talk=4`, `rhythm=3`)으로 하드코딩해서 계산에 넣었는데, 사용자가 실제로 준 데이터가 아니었다.
질문을 늘리는 대신(Option B) 축 자체를 뺐다 — 그래서 상대 정보 입력(S19)도 이제 6개가 아니라

## 6. 핵심 계산 로직 상세

> ⚠️ **아래 로직은 심리 검사나 과학적 진단이 아니다.** 입력값의 공통점·차이를 사용자가 직관적으로
> 읽을 수 있게 만든 **규칙 기반 데모 로직**이며, 실제 AI 백엔드가 붙으면 `src/services/aiService.ts`
> 구현만 교체하면 된다.

### 6.1 동기화율 — **v1.1에서 공식을 다시 만들었다** (`src/lib/logic/compatibility.ts`)

**v1.0의 문제:** `score = 40 + floor(평균비율 × 52)`라는 인위적 하한선(Floor)이 있었다. 축이
다 어긋나도 최소 40점이 나와서, 실제 계산보다 궁합이 높아 보이는 착시를 줬다. 또한 `talk`(대화
방식)·`rhythm`(생활 리듬) 두 축의 '나의 값'을 사진 관찰 고정값(4, 3)으로 하드코딩해서 계산에
넣었는데, 사용자가 준 데이터가 아니었다.

**v1.1 공식 — 하한선 없음, 4개 축(contact/conflict/alone/affection)만 사용:**

```
difference    = |나의 값 - 상대의 값|                      // 둘 다 1~5 척도
axisSimilarity = 1 - (difference / 4)                       // 0~1
axisScore(%)   = round(axisSimilarity × 100)                // 표시용

score = round(
  mean(비교 가능한 축의 axisSimilarity) × 100
)
```

| 차이 | 동기화율 |
|---|---|
| 완전히 동일 | 100 |
| 1단계 차이 | 75 |
| 2단계 차이 | 50 |
| 3단계 차이 | 25 |
| 완전 반대(4단계) | 0 |

비교 가능한 축이 3개(`TARGET_MIN_KNOWN`) 미만이면 `score = null`(E3, 관측 정보 부족). '모름'
으로 남긴 축은 계산에서 완전히 빠진다. **점수 옆에는 항상 "비교 가능한 N개 신호 기준" 문구와
"연애 성공확률이 아니에요" 고지를 함께 둔다.**

내부적으로 UI 게이지(5칸)는 `alignment = round(axisSimilarity × 5)`로 0~5에 매핑해서 쓴다 —
완전 반대일 때 0칸이 되도록 재정의했다(v1.0의 `alignmentOf`는 `max(0, 5-diff)`라 diff=4에서도
1칸이 남는 오류가 있었다).

### 6.2 Relationship Mirror 판정 — **v1.1에서 완전히 다시 설계했다** (`src/lib/logic/mirror.ts`)

**v1.0의 문제:** 과거 관계 질문(S15~S17)은 전부 선택형이라 1~5 척도로 직접 수집된 적이 없는데도,
`toRelationshipMirrorValues()`가 `important.includes('contact') ? 4 : 2` 같은 규칙으로
Relationship Me 값을 억지로 숫자화했다. Declared(실제 척도)와 이 가짜 숫자를 빼서 MATCH/GAP/
CHANGE를 판정하니, 실제보다 정밀하게 측정된 것처럼 보이는 문제가 있었다. 또한 Declared가
미응답이면 중립값 3으로 채웠는데, Missing data를 중립으로 취급하는 것도 문제였다.

**v1.1 — 숫자를 빼지 않고, '근거의 종류'로 카테고리 판정한다:**

```
evidenceStrength(axis) =
  hardest(가장 힘들었던 순간)가 이 축과 강하게 연결됨   → 'hardest'   (가장 강한 근거)
  important(중요했던 요소)에 이 축이 포함됨              → 'important' (중간 근거)
  둘 다 아님                                             → 'absent'    (근거 없음)

state(declaredValue, strength) =
  strength='hardest' 이고 declared >= 4                  → MATCH
  strength='hardest' 이고 declared < 4                   → GAP
  strength='important' 이고 declared <= 2                → GAP
  strength='important' 이고 declared > 2                 → MATCH
  strength='absent' 이고 declared >= 4                    → CHANGE  (말했지만 근거가 안 보임)
  strength='absent' 이고 declared < 4                     → UNKNOWN (판정하지 않음)
```

`hardest`(가장 힘들었던 순간)는 `contact_drop→contact`, `fight_silence→conflict`,
`no_time→alone` 축에만 대응한다(`value_gap`은 5축 어디에도 명확히 대응하지 않아 대응表에서
뺐다).

**UNKNOWN은 `insights` 배열에 아예 포함되지 않는다** — 근거가 없는 축을 억지로 MATCH로 채우지
않기 위해서다. Mirror 헤더의 "비교 가능한 N개 기준에서"가 이 실제 판정 개수를 보여준다.

화면에는 두 숫자를 빼는 대신:
- **Declared 값**: 실제 1~5 척도로 수집된 축(`alone`, `contact`)만 `N/5`로 표시. 나머지
  (`hobby`, `conflict`, `affection`)는 3지선다를 내부 계산용으로 매핑한 값이라 숫자를 보여주지
  않고 문구만 보여준다(`declaredHasScale` 플래그)
- **Relationship 신호**: 숫자가 아니라 `relationshipSignalText()`가 만든 문장
  ("이전 관계에서 연락 감소가 가장 힘든 순간으로 선택" 등)

### 6.3 Teaser·Core Insight 축 선정

```
1순위: hardest 근거의 GAP 축
2순위: 그 외 GAP 축
3순위: CHANGE 축
4순위: 첫 번째 판정된 축 (모두 MATCH인 경우)
```

`contact` 축이 GAP으로 뽑히면 헤드라인은 고정 문구("너는 연락 자체보다...")를 쓰고, 그 외에는
`"너는 {label}에서 말한 기준보다 실제 관계에서 더 크게 반응하는 사람일지도 몰라."` 템플릿을 쓴다.

### 6.4 Adaptive Follow-up 트리거

```
pickAdaptiveTriggerAxis(declared, experience) =
  experience.skipped 면                → null
  buildInsights()로 판정한 focus 축이
  존재하고 상태가 GAP이면                → 그 축
  그 외                                  → null
```

즉 **Teaser/Core Insight의 focus 축과 Adaptive Follow-up이 물어보는 축은 항상 같다** — 그
축에 대한 이유를 미리 하나 더 받아서, S28의 근거를 더 풍부하게 만드는 구조다.

### 6.5 Relationship Profile Summary (S18)

```
declaredHighlight(declared)      // Declared 답변 중 가장 두드러지는 특징 1개 (우선순위 표)
relationshipHighlight(experience) // 관계 경험 중 가장 두드러지는 신호 1개 (hardest 우선, 없으면 important[0])

summary =
  둘 다 있으면   → "{declared 특징}, {relationship 신호}."
  하나만 있으면  → 있는 쪽만
  둘 다 없으면   → "아직 뚜렷한 특징을 관찰하기엔 정보가 조금 더 필요해."
```

두 문장은 **판정 없이 나란히 붙인다.** "~라고 답했지만 실제로는" 같은 비교·모순 표현은 이 함수
안 어디에도 없다 — Mirror(§6.2)와 코드가 완전히 분리돼 있어서 애초에 그런 문장을 만들 수 없다.

### 6.6 Evidence Coverage (구 확신도)

이름을 '확신도'에서 **'관측 정보 충분/보통/부족'**으로 바꿨다. 이 값은 'AI가 얼마나 확신하는가'가
아니라 **'얼마나 많은 입력 근거가 확보됐는가'**를 뜻한다.

```
experience.skipped                                        → 부족
!(important.length >= 3 && selfGap !== null)                → 부족
note(서술)가 비어있지 않음                                    → 충분
그 외                                                        → 보통
```

자유서술을 많이 했다고 분석이 사실일 확률이 높아지는 건 아니다 — 그래서 이름을 근거량으로
한정했다.
