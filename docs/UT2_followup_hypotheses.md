## UT2-H1 — One-off Effort (일회성 입력 부담)

**관찰**: 일회성으로 쓰기에는 입력이 번거롭다 · 30분 안에 끝나지 않는다는 반응. 동시에 질문 수가 적어 "이걸로 뭘 알겠나"라는 반응도 있었다.

**가설**: 관계에 **변화가 생긴 시점**(새 사람 · 갈등 · 관계 전환 · 이별 · 재정리)에는 사용자가 지금 수준의 입력 비용을 감수한다. 부담의 원인은 입력 양 자체보다 **변화가 없는 시점에 들어온 것**이다.

**반증 조건**: 변화 시점을 떠올린 참가자도 "그때도 이만큼은 안 넣는다"고 답하는 비율이 과반이면 기각 → 입력 압축(질문 수가 아니라 화면 수 · 선택 입력 기본값)을 다시 본다.

**다음 UT에서 볼 것**
- "이 서비스를 언제 다시 쓸 것 같아?" (자유 응답 → 변화 시점 / 일상 / 안 씀으로 코딩)
- "그때 오늘만큼 입력할 의향이 있어? 어디까지는 괜찮아?" (화면 단위로 짚기)
- P1에서 줄인 화면 수(S14 · S18 · E4 · S09 평가 제거) 이후 체감 시간

**하지 않을 것**: 질문 수 추가 · 입력 강제 · streak/알림 같은 반복 사용 장치.

## UT2-H2 — Relationship History / Growth (변화 비교 Retention)

**관찰**: 실제 커플 · 배우자 관계에서 관계를 쌓고 변하는 과정을 기록하는 데 재사용 의향을 보였다.

**가설**: Retention의 핵심은 매일 쓰는 습관이 아니라 **관계에 변화가 생긴 시점마다 이전 관찰 기록과 비교**하는 것이다. 첫 결과보다 **두 번째 관찰 뒤의 비교 화면**이 재방문 이유가 된다.

**반증 조건**: 두 번째 관찰을 한 참가자가 비교 화면에서 "처음 결과와 다를 게 없다"고 느끼면 기각 → History의 비교 단위(축 · 사건 · 지금 관계 답)를 다시 본다.

**선행 조건**: Supabase persistence 실제 검증(현재 NXDOMAIN으로 RLS/auth BLOCKED). 로컬 History만으로 여러 날 비교 UT를 하지 않는다.

**다음 UT에서 볼 것**
- 같은 참가자의 2회차 세션(간격 ≥ 1주)에서 `/history/report` 반응
- "지난번과 뭐가 달라졌어?"에 참가자가 먼저 답한 것과 화면이 말한 것의 일치
- 저장한 관계를 다시 열어보는 동기(커플 · 배우자 vs 이전 관계)

**하지 않을 것**: 매일 기록 · 연속 기록 · 관계 점수 추이 그래프.

## UT2-H3 — Target Segment (관계 대응 기준이 불명확한 사용자)

**관찰**: "상대를 어떻게 대해야 할지 모르는 사람에게 유용할 것 같다"는 발언(1명).

**가설**: 관계 대응 기준이 불명확한 사용자(연애 경험이 적거나 · 관계 초기)일수록 **확인해볼 질문 · Next Move** 영역의 가치를 더 크게 느낀다.

**반증 조건**: 연애 경험 적음 / 많음 / 장기 관계 세 그룹 사이에 질문 · Action 영역 가치 평가 차이가 없으면 기각.

**⚠️ 주의**: '모쏠 서비스'로 포지셔닝을 바꾸지 않는다. 한 명의 해석이고, 현재 사용자 범위(모쏠 ~ 배우자)를 좁히는 결정은 데이터 없이 하지 않는다.

**다음 UT에서 볼 것**
- 참가자 모집을 세 그룹으로 나눠 최소 1명씩: 연애 경험 적음 · 연애 경험 많음 · 장기 관계(연인 · 배우자)
- 각 그룹에 "가장 쓸모 있었던 한 부분" 질문 → 점수 · 요약 · 질문 · Next Move · Premium 중 무엇인지 코딩
- generic 추천을 낮춘(P2-6) 뒤 '당연한 조언' 반응이 줄었는지

**하지 않을 것**: 타깃 전환 · 온보딩 카피를 특정 세그먼트용으로 바꾸기.

## UT2-H4 — Brand Positioning

**관찰**: 상대까지 입력해 나와 비교하는 구조는 기대감을 만들었지만, 결과는 "논문 · 보고서" 같다는 반응이 나왔다. 컨셉은 좋아했다.

**가설**: 럽유럽미의 현재 위치는 `재미 궁합` vs `진지한 보고서`의 양자택일이 아니라 **"가볍게 들어와서 필요한 만큼 깊게 보는 관계 관찰 서비스"**로 더 정확히 설명된다. P2(점수 먼저 · 접힌 근거 · 러비 checkpoint)가 이 위치를 화면에서 만든다.

**반증 조건**: 참가자의 한 문장 설명이 여전히 "궁합 테스트" 또는 "연애 분석 보고서" 한쪽으로만 나오면 기각 → 첫 viewport와 러비 비중을 다시 본다.

**다음 UT에서 볼 것**
- 마지막 질문: **"친구에게 이 서비스를 뭐라고 설명할 것 같아?"** (원문 기록 → 재미 / 관찰 / 보고서 / 기타로 코딩)
- 결과를 어디까지 펼쳤는지(접힌 근거 · accordion 열람)와 설명 문장의 관계

**하지 않을 것**: 브랜드 카피 전면 교체 · 캐릭터 비중 확대(모든 카드에 러비).

## UT2-H5 — Relationship Language

**관찰**: 서비스 범위는 모쏠 ~ 배우자까지인데, 관계 경험 입력의 상위 이름이 '이전 관계'였다. 배우자를 떠올린 참가자는 관계 선택지에서도 고를 보기가 없었다(P1에서 `연인 · 배우자` 추가).

**가설**: 상위 기능 이름을 '이전 관계'가 아니라 **'관계 경험'**으로 부르고, 지금 만나는 사람은 **'지금 관계 속의 나'**로 따로 받는 구조가 현재 · 과거 · 배우자 관계까지 기능 범위를 더 자연스럽게 전달한다. (용어 결정 근거 → `RELATIONSHIP_LANGUAGE.md` §2)

**반증 조건**
- 연인 · 배우자 참가자가 과거 관계 질문을 "과거 연애 전용이라 나와 상관없다"고 이해하고 결과의 '지금 관계 속의 나'도 발견하지 못하면 기각 → 과거 질문 도입부에서 현재 관계 입력으로 바로 잇는 경로를 다시 본다.
- 이전 연애가 있는 사용자가 '관계 경험'을 보고 지금 관계를 답해버리면(질문 문장은 '이전 관계에서') 기각 → 질문 문장 위계를 다시 본다.

**다음 UT에서 볼 것**
- "이 질문들은 누구와의 관계를 떠올리며 답했어?" (과거 / 지금 / 섞임)
- 연인 · 배우자 참가자가 결과의 '지금 관계 속의 나'를 스스로 여는지
- 모쏠 참가자가 `이전 연애가 없어 · 건너뛰기`에서 결핍감을 느끼는지

**하지 않을 것**: 내부 키 · route · analytics 이름 변경 · 과거/현재 근거를 한 source로 합치기.
