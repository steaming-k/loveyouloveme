# 0. 한눈에 보는 서비스

## 서비스 한 문장

**상대를 사랑하는 과정에서 나에 대해 더 깊게 이해하고, 나를 사랑하는
방법을 알아가는 서비스**

## 핵심 컨셉

럽유럽미는 단순히 '누구와 잘 맞는가'를 알려주는 궁합 서비스가 아니다.

사용자는 새로운 사람에 대한 궁금증으로 들어와 궁합점수를 확인하고, 그
이유와 충돌 가능성을 살펴보는 과정에서 자연스럽게 **'그런데 나는 연애할
때 어떤 사람이지?'**라는 질문으로 이동한다.

서비스는 사용자가 스스로 생각하는 모습과 실제 관계 경험에서 나타난
모습을 비교해 **관계 속의 나(Relationship Mirror)**를 보여준다.

## 브랜드 세계관

**'인간의 감정을 습득하기 위해 지구에 내려온 외계인이 제3자의 시선으로
인간의 관계를 관찰하고 분석한다.'**

외계인 친구 **러비(Lovy)**는 인간의 감정을 완벽하게 이해하는 상담사가
아니라, 인간을 관찰하며 배우는 제3자 관찰자다.

-   감정을 잘 모름 → 함부로 단정하지 않음
-   궁금한 것이 많음 → 사용자의 말과 경험 사이의 차이를 질문함
-   관찰력이 좋음 → 변화·모순·충돌 가능성을 발견함
-   인간을 계속 학습함 → 사용자의 데이터가 쌓일수록 개인화됨
-   약간 엉뚱함 → 분석·로딩·오류·빈 상태 등의 UX Writing을 재미있게
    전달함

> **러비의 장기 서사**\
> '인간의 사랑은 아직도 잘 모르겠어. 근데 너에 대해서는 전보다 조금 알
> 것 같아.'

# 1. 목표

## 1.1 서비스 목표

연애 전 사용자가 생각했던 자신의 관계 기준과 실제 관계 경험에서 드러난
행동·중요 기준을 비교하여, 사용자가 **'연애할 때의 나'를 구체적으로
이해할 수 있도록 돕는다.**

초기에는 궁합이라는 직관적이고 재미있는 경험으로 진입시키고, 궁합의
이유와 관계 속 자기분석으로 연결하여 단순 궁합 콘텐츠와 차별화한다.

## 1.2 제공하는 핵심 가치

### Acquisition / Hook

**'이 사람과 나는 얼마나 잘 맞을까?'**

궁합점수로 사용자의 첫 관심을 확보한다.

### Core Value

**'그런데 나는 연애할 때 어떤 사람이지?'**

사용자가 생각하는 나와 실제 관계 경험 속 나를 비교하여 차이·변화·모순을
근거와 함께 보여준다.

### Long-term Value

**'나는 관계를 거치며 어떻게 달라지고 있을까?'**

추후 Relationship History를 통해 관계 경험을 누적하고, 과거의 나까지
반영한 분석으로 발전시킨다.

# 2. 배경

## 2.1 리서치 목적

이번 리서치는 이미 정해진 서비스 아이디어를 증명하기 위한 것이 아니라
다음을 확인하기 위해 진행했다.

1.  관계를 통해 사용자가 실제로 새로운 자신의 모습을 발견하는가
2.  관계 전 생각한 기준과 실제 관계 경험 사이에 차이가 존재하는가
3.  사용자가 이러한 경험을 얼마나 구조적으로 정리·축적하고 있는가
4.  궁합·AI 분석·Relationship Mirror에 실제 관심이 있는가
5.  어떤 입력 방식과 분석 방식이 신뢰를 높일 수 있는가

> **주의:** 현재 설문은 탐색적 리서치다. 표본 편중이 존재하므로 시장
> 전체를 대표하는 통계로 해석하지 않는다.

### 사용자 언어에 대한 인사이트

'관계 패턴 분석'이라는 표현보다 다음 질문이 사용자 니즈에 더 가깝다.

-   '연애할 때 나는 어떤 사람이지?'
-   '나는 생각보다 뭘 중요하게 보는 걸까?'
-   '연애하면서 나는 어떻게 달라졌지?'

따라서 서비스 커뮤니케이션도 **'패턴 교정'보다 '관계 속의 나 발견'**을
중심으로 한다.

## 2.9 입력 방식에 대한 해석

설문에서는 가장 편한 입력 방식으로 **짧은 질문 57.7%**, 직접 선택·입력
38.5%, SNS 게시물 직접 선택 23.1%, 사진 AI 분석 초안 15.4% 등이
나타났다.

그러나 이 결과는 **입력 편의성**에 가까우며, 사진·SNS 데이터가 분석의
개인화 수준을 높인다는 가치까지 충분히 설명한 비교는 아니었다.

사진 기반 AI 초안 이용 의향 자체는 **긍정 50.0%, 중립 38.5%, 부정
11.5%**였고, SNS로 파악하기 어려운 관계 성향을 추가 질문으로 입력하는
것에는 **76.9%가 긍정**했다.

따라서 현재 단계에서는 사진과 질문을 대체 관계로 판단하지 않는다.

### AI Profile Building 구조

1.  **Observed Me** --- 사용자가 선택한 사진 등에서 관찰되는
    취향·라이프스타일
2.  **Declared Me** --- 짧은 질문을 통해 사용자가 스스로 설명한 나
3.  **Relationship Me** --- 과거·현재 관계 경험에서 나타난 나
4.  **User Validation** --- AI가 만든 프로필을 사용자가 확인·수정

> **짧은 질문은 입력 부담을 줄이는 장치이고, 사진·관계 경험은 분석의
> 해상도를 높이는 장치다.**

# 4. 문제 정의 및 솔루션 가설

## 4.1 문제 현상

> **사람들은 연애 전 자신이 중요하다고 생각했던 기준과 실제 관계에서
> 중요하게 느끼는 기준 사이의 차이를 경험하고, 관계를 통해 몰랐던 자신의
> 모습을 발견한다. 그러나 이러한 경험은 대부분 머릿속의 회고나 일회성
> 깨달음으로 남아 '관계 속의 나'에 대한 정보로 구조화·축적되지 않는다.**

### 문제 흐름

**관계 경험 발생**\
→ 새로운 자신의 모습·실제 중요 기준 발견\
→ 반복되는 갈등이나 행동 인지\
→ 관계 종료 또는 시간 경과\
→ 경험과 깨달음이 기억·감정 속에 흩어짐\
→ 다음 관계에서 활용할 수 있는 구조화된 자기 기준으로 남지 않을 가능성

마지막 단계는 현재 설문에서 인과까지 직접 검증된 FACT가 아니라 **후속
인터뷰에서 검증해야 할 문제 가설**이다.

## 4.5 Persona Scenario

### ① 새로운 사람이 생김

사랑에게 최근 관심 가는 사람이 생긴다.

> '이 사람이랑 나, 잘 맞으려나?'

궁합이라는 직관적인 궁금증을 해결하기 위해 럽유럽미에 진입한다.

### ② 나부터 관찰

러비가 말한다.

> '상대를 보기 전에 일단 너부터 조금 알아야겠어.'

사용자는 자신의 일상·취향이 드러나는 사진을 선택하고 추가 질문에 답한다.

AI가 취향·라이프스타일 초안을 생성하고 사용자가 수정한다.

### ③ 상대와 궁합 확인

상대 정보를 입력한 뒤 궁합점수를 확인한다.

예:

**동기화율 78%**

그러나 점수만 제공하지 않는다.

-   왜 이런 점수가 나왔는가
-   잘 맞는 부분
-   충돌 가능성이 있는 부분
-   실제 관계에서는 어떤 상황으로 나타날 수 있는가
-   서로 확인해볼 질문

을 함께 제공한다.

### ④ 상대를 보러 왔다가 나를 발견

러비가 사용자의 자기보고와 과거 관계 경험 사이의 차이를 발견한다.

> '잠깐. 너는 연락이 중요하지 않다고 했는데 이전 관계에서는 연락이
> 줄어드는 걸 가장 힘들어했네.'

사용자는 궁합을 보러 들어왔지만 자신이 실제 관계에서 무엇을 중요하게
보는지 발견한다.

### ⑤ Relationship Mirror

사용자가 생각하는 나와 실제 관계 경험 속 나를 비교한다.

**Declared Me ↔ Relationship Me**

이를 통해 사용자가 스스로 생각했던 연애 성향과 실제 관계에서 나타난
모습의 Gap을 확인한다.

------------------------------------------------------------------------

## 4.6 솔루션 가설

> **관계 전 사용자가 생각한 자신과 실제 관계 경험에서 나타난 자신을
> 비교하고, 변화·차이·모순을 구체적인 근거와 함께 보여주면 사용자는
> '연애할 때의 나'를 더 구체적으로 이해할 수 있을 것이다.**

### 궁합 Hook 가설

> **궁합점수로 사용자의 초기 호기심을 유발하고, 점수의 이유와 충돌
> 가능성을 설명하는 과정에서 Relationship Mirror로 연결하면 단순 궁합
> 콘텐츠를 자기이해 경험으로 전환할 수 있을 것이다.**

### AI 신뢰 가설

> **AI가 결론만 제시하지 않고 판단 근거를 함께 보여주며 사용자가 분석을
> 수정할 수 있게 하면, 일반적인 AI 연애상담보다 개인화와 신뢰를 높일 수
> 있을 것이다.**

### 입력 가설

> **짧은 질문만 사용하는 대신 사진에서 관찰한 일상 정보, 자기보고 질문,
> 실제 관계 경험을 함께 활용하면 형식적인 성향 분석보다 개인화된
> Relationship Profile을 만들 수 있을 것이다.**

## 5.4 궁합 분석 원칙

6.  서로 이야기해볼 질문

## 5.5 AI 분석 원칙

> **v1.6 — 이 원칙들이 실제 코드 장치로 옮겨졌다.** 아래 5개 원칙은 v1.5까지 '문구 규칙'이었고,
> v1.6에서 서버 검증 로직이 됐다. 각 원칙이 어떤 장치가 됐는지 §5.11에 정리했다.

### 1. 결론 + 근거

> '너는 갈등 상황에서 대화를 미루는 경향이 있어 보여.'

와 함께

> '이전 관계 경험에서 갈등 직후 대화를 피했다고 반복적으로 답했어.'

처럼 근거를 제공한다.

### 2. 사용자 수정 가능

> '내가 너를 잘못 이해했나 봐. 틀린 부분을 알려줘.'

AI 분석을 사용자가 수정·거절할 수 있게 한다.

### 3. 타인의 마음을 단정하지 않음

> '이건 네가 알려준 상대의 모습이야. 그 사람 자체를 분석한 건 아니라는
> 건 기억해줘.'

### 4. 불확실성을 숨기지 않음

정보가 부족하면 확정적인 표현 대신 관측 한계를 보여준다.

### 5. 제3자 관찰자

러비는 사용자를 평가하거나 무조건 위로하는 상담사가 아니다.

**관찰 → 이상한 점 발견 → 질문 → 근거 제시 → 사용자 확인 → 학습**

의 루프를 따른다.

## 5.8 MBTI Supporting Lens (v1.2 추가)

MBTI를 Phase 3 후보에서 **MVP Supporting Compatibility Lens**로 옮겼다.

### 정의

> **사용자와 상대가 직접 입력한 MBTI를 관계 행동 데이터와 별도의 Personality
> Lens로 비교해, 궁합 결과를 해석할 때 참고할 수 있는 보조 정보**

### 위치

  구분                내용
  ------------------- -------------------------------------------------
  내 MBTI 입력        S13 Declared Me 마지막 (Optional Section)
  상대 MBTI 입력      S19 상대 정보 입력 (Optional Section)
  결과 노출           S21 availability Tag → S22 Lens 섹션 → X1-a 상세
  Core Score 반영     **없음**

### 원칙

MBTI는 **Core Compatibility Score에 포함하지 않는다.** 궁합점수는 연락·갈등
해결·개인 시간·애정 표현이라는 실제 관계 행동 신호만으로 계산한다.

MBTI 유형만으로 관계 성공 가능성·사랑의 적합성·좋은 커플/나쁜 커플·이상적
조합을 판정하지 않는다. E/I·S/N·T/F·J/P 4개 축을 독립적으로 비교해 **'서로
다르게 반응할 수 있는 대화 주제'**로만 제시한다.

'같은 글자 = 좋음 / 다른 글자 = 나쁨'으로 표현하지 않는다 — `비슷한 성향` /
`다르게 나타날 수 있는 성향` 두 라벨만 사용한다.

### 왜 사주·점성술과 위계를 구분하는가

MBTI도 과학적인 궁합 예측 기능은 아니다. 다만 사용자가 **스스로 알고 있는
Personality Preference**를 대화의 출발점으로 활용한다는 점에서, 사주·점성술보다는
Relationship Analysis에 가까운 Supporting Lens로 둔다.

### 보조지표

  지표                 산식
  -------------------- ------------------------------------------------
  MBTI 입력률          both_mbti_available / compatibility_result_view
  MBTI Lens 조회율     mbti_lens_view / both_mbti_available

MBTI는 Optional이므로 **Primary KPI(궁합 결과 → Relationship Mirror
진입률)에는 포함하지 않는다.**

## 5.11 실제 AI 분석 파이프라인 (v1.6 추가)

### 왜 이 작업을 했는가

v1.5까지 럽유럽미의 사진 분석은 **규칙 기반 Demo**였다. 사진을 받아서 개수만 보고 미리 정해둔
문장을 돌려줬다. 배지와 안내로 그 사실을 숨기지는 않았지만, §2.9에서 '사진 입력'을 선택한 근거
— **말로 설명하기 어려운 자기 모습을 사진이 대신 보여준다** — 는 검증할 수 없는 상태였다.

v1.6은 그 구멍을 메웠다.

### 절대 뒤집지 않는 위계

```
Evidence  →  Rule  →  AI Explanation  →  User Verification
```

| | 담당 |
|---|---|
| **Rule** (deterministic) | 동기화율 · Mirror MATCH/GAP/CHANGE · History STABLE/SHIFT/NEW · MBTI · Sun Sign |
| **AI** | 관찰 · 정리 · 설명 · 질문 생성 |

**AI가 점수를 만들 수 없다.** 이건 문구 약속이 아니라 구조다 —
`buildCompatibility()`는 AI 결과를 인자로 받지 않고, Mirror state는 서버에서 규칙 값으로
덮어쓴다. 실측으로도 확인했다: AI 분석 결과를 통째로 조작해도 동기화율 55·신호 2/2·Mirror 판정이
바뀌지 않았다.

### §5.5 원칙 → 코드 장치

| 원칙 | v1.6에서 무엇이 됐는가 |
|---|---|
| ① 결론 + 근거 | 근거 없는 관찰은 **버린다.** 사진 1장만 근거면 `high` → `medium` 강등 |
| ② 사용자 수정 가능 | `USER CORRECTION > CONFIRMED > UNVERIFIED`. **AI 원문을 덮어쓰지 않고** 함께 보여준다 |
| ③ 타인의 마음 단정 금지 | 마음 읽기 패턴 스캔 → 걸리면 그 항목 폐기 |
| ④ 불확실성 은폐 금지 | Evidence Coverage를 **코드가** 판정한다. AI가 '충분하다'고 말하게 하지 않는다 |
| ⑤ 제3자 관찰자 | Trait 0개도 정상 상태로 취급 — 개수 채우려고 약한 관찰을 만들지 않는다 |

### 절대 추론하지 않는 것

사진에서 성적 지향 · 정치 · 종교 · 정신건강 · 질병 · 장애 · 경제 수준 · 범죄성 · 임신 ·
민족 기반 성향 · 관계의 질 · 상대의 감정 · MBTI · 애착유형을 **추론하지 않는다.**
얼굴 점수 · 매력도 · 나이 추정 · 체형 평가도 하지 않는다.

프롬프트가 1차 방어, 서버 패턴 스캔이 최후 방어선이다. 걸린 항목은 통째로 버리고
'추론하지 않기로 한 항목이 있어서 일부 관찰은 제외했다'를 사용자에게 알린다.

### Privacy — v1.6에서 고친 거짓말

> ⚠️ '사진은 브라우저 안에서만 쓰이고 서버로 보내지 않아요' — v1.5까지 사실이었고,
> **실제 Vision을 붙이는 순간 거짓이 됐다.** 전수 검색해 수정했다.

지금 말하는 것: 사진은 **분석을 위해 전송된다** · 앱 기록에는 **저장하지 않는다** ·
외모/나이/체형을 평가하지 않는다 · demo 모드에서는 전송 자체가 없다.
Provider의 보관·학습 정책은 우리가 검증하지 않았으므로 '즉시 완전 삭제' 같은 보장을 하지 않는다.

| S28 Core Insight | ⭕ **가장 강하게** | 제품의 종착점이고, 근거를 문장으로 연결해주는 가치가 가장 크다 |
| F2 변화 리포트 | ⭕ 변화 행마다 짧게 | 변화의 **의미**는 설명이 필요하다. 단 '~일 수도 있어' 수준으로만 |
| **S26 Teaser** | ❌ **prefetch만** | 여기가 서비스의 Aha Moment다. 첫 발견이 'AI가 말해준 것'이 되면 안 된다 |
| **반복 신호** | ❌ | 반복은 이미 사실 진술이다. 해석을 얹으면 '반복되는 문제'라는 판정으로 읽힌다 |
| **F1 / F1-a / F3** | ❌ | 과거 Entry에 새 설명을 덧붙이면 그건 '그때의 관찰'이 아니다 |
| **Astrology** | ❌ | Sun Sign은 deterministic이고 AI를 붙일 이유가 없다 |

> **S26에 안 붙인 것이 이 버전에서 가장 중요한 판단이다.**
> AI를 붙일 수 있는 자리에 다 붙이는 건 쉽다. 그런데 Relationship Mirror의 첫 발견 순간은
> **사용자가 자기 데이터에서 직접 보는 것**이어야 한다. 그래서 S26은 미리 계산만 해두고
> (다음 화면이 빨라진다) 화면은 v1.6 그대로 뒀다.

### 근거는 AI가 쓰지 않는다

v1.6에서도 '근거를 붙인다'는 원칙은 있었지만, 근거 문장 자체를 AI가 쓸 수 있었다.
v1.7에서는 AI가 **어디를 봤는지만 지목**하고(`EvidenceRef`), 화면에 보이는 근거 텍스트는
코드가 실제 세션 데이터에서 만든다.

```
AI:   "declared.contact를 봤어"
코드: "연락 중요도를 5점 중 2로 답했어"   ← 실제 답변에서 생성
```

그래서 AI가 근거를 그럴듯하게 지어내도 **화면에 도달할 수 없다.**
그리고 사용자가 고친 관찰은 `사용자 수정` 라벨로 표시되고, AI 원본은 화면에 나오지 않는다.

### AI 설명이 없어도 제품이 동작한다

AI Narrative는 **enhancement다.** 실측으로 확인한 것:

- AI가 실패해도 S22의 점수·신호·근거·CTA가 전부 그대로 렌더된다
- S28은 AI 실패 시 규칙 템플릿 headline으로 조용히 되돌아간다
- AI 로딩 중에도 Primary CTA가 동작한다 — Funnel이 막히지 않는다
- AI 결과가 붙어도 동기화율은 변하지 않는다 (45 → 45)

## 5.13 Premium 가치 재정의: 연결(Analysis Depth) vs 설명 (v1.9 추가)

### 왜 이 작업을 했는가

v1.7까지는 AI 설명이 Core Experience 전체에 붙었지만, 그 설명은 결국 사용자가 **이미
입력한 하나의 데이터**를 다시 풀어 말하는 것이었다. 사용자 입장에서는 "내가 방금 답한 걸
왜 또 말해주지?"에 가까웠고, 그 상태로는 상세 분석에 돈을 낼 이유가 약했다.

v1.9의 판단: Premium이 팔아야 하는 건 **"AI가 더 길게 말해주는 것"이 아니라 "따로 있던
데이터를 연결했을 때만 보이는 신호"**다.

> FREE: "오, 이거 좀 나 같은데?" (단일 소스 관찰)
> PREMIUM: "아, 이 두 가지가 연결돼 있었구나." (Cross-source 관찰)

그래서 이번 버전은 AI 프롬프트를 손대기 전에 먼저 **규칙 기반 Cross-source Insight
Engine**을 만들었다 — Declared(내가 말한 기준) ↔ Relationship(실제 경험), Relationship ↔
Target(상대에 대해 입력한 값), Current ↔ History(과거 기록)를 서로 대조한다. AI는 그
결과에 문장만 붙인다. 판정 자체는 여전히 규칙이 한다 — v1.6부터 지켜온 "AI는 판정자가
아니다" 원칙이 이번에도 바뀌지 않았다.

### 이번에도 절대 넘지 않은 경계

| 경계 | 유지 방법 |
|---|---|
| AI가 동기화율·Mirror·History를 새로 판정 | Cross-source Insight는 기존 판정을 **재표현**할 뿐, 새 계산을 하지 않는다 |
| MBTI/사주가 동기화율에 반영 | Cross-source 조합 목록에 MBTI/사주 소스가 없다 — 구조적으로 섞일 수 없다 |
| AI가 상대의 마음을 추론 | 프롬프트에 동일 규칙 유지 + Quality Gate가 위반 문장을 걸러 버린다 |
| Premium이 FREE 가치를 줄임 | FREE Recap 항목(동기화율/대표 신호/Mirror 핵심/기본 변화 요약)은 그대로 두고, Premium은 그 위에 얹는다 |

### 판단이 필요했던 지점: Adaptive Deep Question을 프로덕션에 바로 연결하지 않았다

Deep Question은 "우선순위가 높은 Insight에 대해 한두 가지 더 물어보는" 기능이다. 그런데
지금은 실제 결제도, 리포트 발송도 없다 — 물어봐도 사용자에게 돌아오는 보상이 없다.
**아무 보상 없이 프로덕션에서 심층적인 답변을 모으는 건 정직하지 않다**고 판단해서, 이번
버전은 이 기능을 개발·UT 통로로만 열어뒀다. Fake Door가 실제 결제로 바뀌고 리포트가 진짜
전달될 수 있을 때 프로덕션에 연결하는 게 순서라고 본다.

### 구현 상태 — 정확히 구분한다

| 항목 | 상태 |
|---|---|

## 5.15 Result Experience Consolidation (v1.11 추가)

### 왜 이 작업을 했는가

기능을 줄이기 위해서가 아니다. **같은 질문에 대한 결과를 한 맥락에서 읽게 하기 위해서다.**

v1.10까지 궁합 결과를 다 확인하려면 Hero(S21) → Detail(S22) → Good(S23)/Friction(S24)/
Questions(S25)까지 최대 5개 화면을 옮겨 다녀야 했다. Relationship Mirror도 Map(S27)과
Core Insight(S28)로 나뉘어 있었다. 둘 다 하나의 질문("우리 둘은 어떻게 맞는가?" /
"나는 관계에서 어떤 사람인가?")에 대한 답인데, 그 답을 읽는 도중에 사용자가 여러 번
페이지를 이동해야 했다. 그리고 분석을 끝낸 뒤 "이 결과를 다시 보고 싶다"는 순간에
들어갈 명확한 문이 Mirror 말고는 없었다.

### 핵심 판단: 무엇을 합치고 무엇을 남길 것인가

화면을 합치는 기준은 화면 수가 아니라 **Mental Model**이었다.

```
'나와 이 사람은 어떻게 맞는가?'      → Compatibility Result
'그런데 나는 관계에서 어떤 사람인가?' → Relationship Mirror Result
```

이 둘은 서로 다른 질문이므로 합치지 않았다. 그 사이에 있는 Mirror Teaser(S26)는
'상대 분석'에서 '자기 분석'으로 시선을 처음 돌리는 순간 — 이 서비스의 진짜 첫 Aha
Moment라서 **절대 유지**했다. 같은 질문 안에서 쪼개져 있던 화면(S21~S25, S27~S28)만
각각 하나로 합쳤다.

### Current Result Revisit — 그런데 History와는 다른 것

분석을 마친 뒤 그 결과를 다시 보고 싶을 때, 그건 '새로운 기록'이 아니라 '방금 만든
결과를 다시 여는 것'이다. 이걸 Relationship History(v1.3, 과거 관찰을 저장해 변화를
비교하는 기능)와 같은 취급을 하면 안 된다고 판단했다:

| | Current Result Revisit | Relationship History |
|---|---|---|
| 무엇을 보여주는가 | **지금** 세션의 분석 결과 | **그 당시** 저장된 스냅샷 |
| 입력을 고치면 | 즉시 반영된다 | 반영되지 않는다 — 그때 기록 그대로 |
| 데이터가 사라지면 | 세션 삭제 시 함께 사라진다(가짜로 만들어 보여주지 않는다) | 세션과 무관하게 남는다 |
| 제품에서의 역할 | '방금 본 걸 다시 보기' | '내가 어떻게 달라졌는지' |

그래서 Home 화면도 '최근 분석'(Current Result Revisit)과 'Relationship History'를
같은 목록이 아니라 **분리된 두 섹션**으로 나눴다.

### 구현 상태

| 항목 | 상태 |
|---|---|
| Compatibility Result 통합(`/compatibility`) | **Implemented** |
| Mirror Result 통합(`/mirror`) | **Implemented** |
| Mirror Teaser 유지 | **Implemented** — Route·문구·KPI 이벤트 전부 불변 |
| Current Result Revisit(궁합/Mirror/Profile) | **Implemented** |
| Legacy Route 5개 리다이렉트 | **Implemented** — 기존 링크·북마크 보존 |
| Edit Return(수정 후 Revisit으로 복귀) | **Implemented** |
| 계산 로직(동기화율·Mirror·History) | **불변 — 이번 작업에서 손대지 않았다** |
| Primary KPI(Mirror 진입률) | **불변** — Revisit은 별도 이벤트로만 집계 |
| typecheck / lint / build | **Verified** |
| Mobile(375px)·Accessibility 기본 확인 | **Verified**(기능명세서 §13.8) |

상세 화면 구성·Route 표·QA 케이스는 [`기능명세서.md`](./기능명세서.md) §13을 참고한다 —
이 문서는 '왜'를 남기고, 기능명세서는 '무엇을 어떻게'를 남긴다.

## 5.16 Launch & Measurement Readiness (v1.12 추가)

### 왜 이 작업을 했는가

새 Product Feature를 확장하지 않았다. v1.11.1까지의 가장 큰 미검증은 **기능 부족이
아니라 검증 가능성 부족**이었다 — ① 실제 AI가 end-to-end로 동작하는지, ② 사용자
행동을 실제로 측정할 수 있는지, ③ 사진·관계 데이터가 어디로 가는지 사실대로 설명할 수
있는지가 전부 코드로는 준비돼 있었지만 실제로 켜본 적이 없었다. v1.12는 이 세 가지를
**"만들었다"에서 "실제로 확인했다/켤 수 있다"로** 옮기는 작업이다.

### Real Provider — 이미 있던 걸 확인만 했다

AI Provider abstraction(`src/services/ai/provider.ts`)은 이미 OpenAI 호환 Chat
Completions를 fetch로 부르는 구조였고, Key는 처음부터 `server-only`로 격리돼 있었다.
`AI_PROVIDER` 환경변수도 이미 있었다 — 다만 실제로 분기하는 곳이 없는 메타데이터였다.
**Provider 이름을 하드코딩하지 않는다는 원칙은 `AI_BASE_URL`을 바꾸는 것만으로 다른
OpenAI 호환 엔드포인트로 옮길 수 있다는 형태로 이미 충족돼 있었다** — 이번에 새 추상화
계층을 얹지 않았다. 실제로 바뀐 건 없다: Key가 생기면 `AI_MODE=real`만으로 켜진다.
**Real Provider E2E는 여전히 NOT VERIFIED다** — Key가 없다(§14.1).

### Analytics를 "만들어만 뒀던 것"에서 "실제로 켤 수 있는 것"으로

GA4 Adapter(`createGa4Adapter`)는 v1.10부터 있었지만 gtag.js를 로드하는 코드가
없어서 Measurement ID를 넣어도 아무 일도 없었다. 이번에 `next/script`로 실제
연결했다 — 단, **동의 없이 바로 시작하지 않는다.** 최소한의 Consent Gate(배너 +
`/privacy`에서 언제든 변경)를 새로 만들었고, GA4는 `production && Measurement ID
있음 && Consent === 'granted'` 세 조건을 모두 만족할 때만 로드된다. 이건 실제 법률
자문을 거친 장치가 아니라 제품 UX 차원의 최소 안전장치다.

### Analysis-level Funnel — 같은 탭에서 두 번째 상대를 분석하면?

기존 Primary KPI(`compatibility_result_view` → `relationship_mirror_entry_click`)는
`sessionStorage[이벤트명]`으로만 dedup했다. 그래서 한 탭에서 상대를 두 번 분석하면
분모는 세션당 1번에 묶여 있는데 분자는 클릭할 때마다 계속 늘 수 있었다 — 반복 분석이
많은 세션일수록 비율이 실제보다 부풀 수 있는 구조였다. **기존 KPI 정의는 바꾸지
않았다**(과거 로그와의 비교가 끊기기 때문이다). 대신 `funnelAnalysisId`(상대가 바뀔
때마다 새로 발급되는 랜덤 UUID — Declared/Relationship 기반 deterministic
fingerprint인 History의 `analysisId`와는 다른 개념이다)로 dedup하는 별도의 Analysis
Funnel Conversion 지표를 **추가로** 만들었다. 브라우저 실측으로 Target A→B 두 번
분석했을 때 기존 지표는 1로 고정되고, 새 지표는 분석마다 정확히 1씩(합 2) 늘어나는
것을 확인했다(§14.3).

### Privacy — 실제 동작만 말한다

`docs/privacy-policy.md`를 새로 만들었다. 내용은 지어낸 게 아니라 기능명세서
§12.5 Data Inventory와 `src/data/copy.ts`의 `PRIVACY` 문구(v1.6부터 이미 정확했다)를
사용자가 읽을 수 있는 형태로 옮긴 것이다. 확인하지 않은 사실(AI Provider의 보관·학습
정책)은 여전히 보장하지 않는다. `/privacy` 화면을 새로 만들었고, Home과 사진 입력
화면(S07)에 진입점을 뒀다 — 새로운 대형 Settings 페이지는 만들지 않았다.

### Rate Limit — 경계만 준비했다

기존 rate limit(`src/app/api/ai/_shared.ts`)은 이미 있었고 이미 스스로 "서버리스
다중 인스턴스에서는 부정확하다"고 주석에 써 있었다. 이번에 `RateLimitStore`
인터페이스로 경계를 분리했지만, **실제로 연결할 공유 저장소(Redis 등) credential이
없어서 새 외부 dependency를 강제로 추가하지 않았다.** 지금도 Memory 구현체 그대로다
— production에서 이 상태이면 로그로 한 번 경고하고, `SHARED_RATE_LIMIT_URL`이 생기면
그 경계 함수 하나만 바꾸면 되게 해뒀다.

### UT Production Readiness

개발자 콘솔 없이 URL 하나로 실제 참가자에게 UT를 맡길 수 있어야 한다는 기준으로
"UT 결과 내보내기"(JSON 다운로드, 정량 응답만 — 자유서술 원문은 절대 포함하지 않는다)와
"다음 참가자를 위해 초기화"를 `UT_MODE`에서만 보이는 Home 섹션으로 추가했다. 새 UT
질문은 만들지 않았다 — 기존 v1.7(S09/S27R/F3)·v1.10(Deep Report 5문항) 구조 그대로다.

## 5.17 Target Preference + Approach Hints (v1.13 추가)

### Product Problem

Compatibility는 연락 방식·갈등 해결·개인 시간·애정 표현 4축으로 "우리 둘이 얼마나
비슷한가"를 설명한다. 하지만 사용자가 실제로 갖는 질문에는 답하지 않는다 — "그래서
이 사람은 뭘 좋아하지?", "내가 어떻게 다가가면 좀 더 편하게 느낄까?" v1.13은 이
빈 공간을 채운다.

### 이건 무엇이 아닌가 (Product Boundary)

**호감도 예측·공략법이 아니다.** 상대가 나를 좋아할 확률·고백 성공률·상대 감정
추론·밀당·질투 유발·의도적 답장 지연 같은 조작(Manipulation) 요소를 전부 배제한다.
이 기능은 **Preference-aware Responsiveness**다 — 기존 제품 원칙("이건 네가
알려준 상대의 모습이야. 그 사람 자체를 분석한 건 아니라는 건 기억해줘")을 그대로
따른다.

### HYPOTHESIS(검증되지 않은 가설)

> 상대가 좋아하는 것 + 관계 방식을 함께 보여주면, 단순 Compatibility 분석보다
> 사용자가 실제 행동으로 연결하기 쉬울 것이다.

이건 FACT가 아니다. 이번 버전에서 실제 사용자 가치는 **NOT VALIDATED**다 — UT에서
확인할 대상이다(§A.0 참고).

### 데이터 출처 원칙

새로 받는 정보(상대가 좋아하는 것, 최대 5개 — 미리 정의된 15개 카테고리 + 직접
입력)는 항상 **USER-REPORTED TARGET INFO**다. AI가 사진이나 다른 데이터에서 상대
취향을 추론해 채우지 않는다. 관계 행동(연락·갈등·개인 시간·애정 표현)은 새로
묻지 않고 기존 4축(S19)을 그대로 재사용한다 — 같은 질문을 두 번 만들지 않는다.

### Approach Hint Engine — 판단: AI를 연결하지 않는다

기존 원칙(Evidence → Rule → AI Explanation)을 그대로 따르되, **이번 버전에서는
AI 재작성 단계를 연결하지 않고 규칙 엔진(`src/lib/logic/approachHints.ts`)이 만든
문장을 그대로 화면에 쓴다.** 판단 근거:

1. 이 기능은 명시적으로 **검증되지 않은 가설**이다(§45) — 아직 증명되지 않은
   기능을 위해 새 AI Task(Route·Prompt·Schema·Safety Scanner) 전체를 새로 만드는
   건 이르다고 판단했다.
2. 조작(Manipulation) 위험이 이 서비스의 다른 어떤 AI Task보다 높다 — Prompt
   Injection·환각으로 만들어질 수 있는 위험 표면을 아예 없애는 쪽이, 프롬프트로
   막는 것보다 확실하다.
3. 규칙 엔진만으로도 §18~§24가 요구하는 우선순위(직접 입력한 관심사 → 관계 행동
   → 조합 → 근거 부족 시 질문)와 §52의 Copy Guardrail을 전부 만족하는 품질의
   문장을 만들 수 있었다(코드 리뷰로 검증 — §33/§34의 금지 표현이 템플릿 어디에도
   없음을 확인했다).
4. 이 서비스의 다른 AI Task(Compatibility·Mirror·History)도 "규칙이 먼저, AI는
   나중"의 순서로 진화했다 — 같은 패턴을 반복한 것이다.

**Type 계약은 AI 연결을 염두에 두고 설계했다**(`ApproachHint`·`TargetEvidenceRef`,
§16~§17) — `confidence: 'direct'|'contextual'`, `evidenceRefs` 구조가 이미 있어서
나중에 AI 설명 레이어를 얹어도 Evidence Rule 자체는 바뀌지 않는다.

### 절대 포함하지 않는 것

- Compatibility Score(§11) · Relationship Mirror MATCH/GAP/CHANGE(§12) — 취향
  일치는 연애 성공 예측 근거가 아니다.
- MBTI·사주·별자리를 Approach Hint의 근거로 쓰지 않는다(§49/§50).
- Relationship History에 상대 취향 목록을 통째로 저장하지 않는다(§13/§41).
- 공유 카드에 포함하지 않는다(§58, 상대에 대한 입력 정보가 공유될 수 있어서).

### 구현 상태

| 항목 | 상태 |
|---|---|
| Target Preference 입력(S19, Progressive Disclosure) | **Implemented** |
| Approach Hint Engine(규칙 기반, 최대 3개) | **Implemented, Verified**(브라우저 실측) |
| Compatibility Score/Mirror 영향 없음 | **Verified** — 계산 로직 파일을 열지 않음 |
| New Target 시 초기화 | **Verified**(`TargetProfile` 안에 있어 `resetTargetContext()`로 자동) |

| AI 재작성 레이어 | **의도적으로 미연결**(위 판단 근거 참고) |
| Analytics(raw text 미전송) | **Verified** |
| 실제 사용자 가치 | **NOT VALIDATED — HYPOTHESIS** |

## 5.18 Lovy Observation Experience (v1.20 추가)

> **원칙 한 줄 — Hook은 익숙하게, 해석은 다르게.**

### 왜 필요했나

사용자는 익숙한 기대를 가지고 들어온다. **궁합 점수 · MBTI 궁합 · 사주 · 별자리 ·
연애 성향.** 그 기대를 부정하고 시작하면 아무도 들어오지 않는다(§2.7 — 궁합은 Hook이다).

문제는 그다음이었다. v1.19까지의 결과 화면은 기대한 것을 **기대한 방식 그대로** 돌려줬다.
큰 숫자 하나와 같은 크기의 카드 7개. 화면 어디에도 "이 서비스는 관계를 어떻게 보는가"가
드러나지 않았고, 제품의 핵심 주장인 **'하나의 렌즈만으로 인간 관계를 설명하지 않는다'**는
렌즈 위계 문구(§5.8/§5.9)와 Lens Hub 캡션에만 적혀 있었다 — 무료 사용자가 결과를 읽는
흐름 안에서는 한 번도 만나지 못했다.

러비도 마찬가지였다. 세계관에서 러비는 **인간의 감정을 이해하지 못해 궁금해하는 관찰자**인데
(§0 브랜드 세계관), 화면에서는 말풍선 두 개짜리 장식이었다. 러비의 말투와 결과 문서의 말투가
같아서 "누가 말하고 있는가"도 구분되지 않았다.

### 무엇을 바꿨나 (기능이 아니라 해석의 표면)

**계산·판정·가격·KPI는 하나도 바꾸지 않았다.** 바꾼 것은 Brand Experience · Information
Architecture · Copy · Presentation · Motion이다.

1. **분석 = 관찰 과정.** 스피너에 자막을 얹는 대신 화면이 실제로 관찰을 한다 —
   **OBSERVE → COLLECT → CONNECT → REPORT.** 관계 신호 4개가 토큰으로 나타나고, 수집되고,
   선으로 이어져, 하나의 관찰 기록지가 된다. **연출을 위해 분석을 늦추지 않았다** — 총
   시간은 이전 로딩 시퀀스와 정확히 같은 상수다.
2. **결과 = 러비의 관찰 보고서.** 결과 화면 맨 위에 Report Header(무엇을 몇 개 관찰했고
   언제 쓴 기록인지)를 두고, 섹션에 번호(`01 SUMMARY` … `07 NEXT QUESTION`)와 얇은
   divider를 줬다. 같은 크기의 카드를 나열하는 대신 번호·구분선·주석·근거 블록으로 리듬을
   만든다.
3. **FIRST SURPRISE(무료).** 숫자를 이해한 직후, 근거를 읽기 전에 러비가 한 번 끼어든다 —
   *"잠깐. 숫자만 보면 놓치는 게 하나 있어."* 이건 **Paywall이 아니라 Product Aha다.**
   무료 사용자가 "이 서비스는 해석 방식이 다르다"를 이해하지 못하면, Premium은 애초에
   팔 수 있는 것이 아니다(§5.13 Premium 가치 원칙과 같은 방향).
4. **두 화법의 분리.** 러비(Mint · 호기심 · 혼잣말)와 보고서(Neutral · 차분함 ·
   evidence-first)를 색과 형태로 나눴다. **Lovy = personality, Report = credibility.**
5. **철학은 문구가 아니라 관찰로.** *"사랑은 참 어렵다"* 같은 일반 감성 문구를 쓰지 않는다.
   현재 결과와 연결된 러비의 **질문**만 남긴다 — 갈등 축에 차이가 있으면
   *"둘 다 갈등을 풀고 싶은 건 같아 보이는데, 한 사람에게 푼다는 건 바로 이야기하는 거고
   다른 사람에게는 생각할 시간을 갖는 걸 수도 있네."*

### 지키기로 한 경계

| 경계 | 내용 |
|---|---|
| 분석을 늦추지 않는다 | 연출을 보여주려고 지연을 넣지 않는다. 총 연출 시간은 이전과 동일 |
| 없는 걸 만들지 않는다 | 관측 정보가 부족하면(E3) FIRST SURPRISE도 러비 관찰 노트도 **표시하지 않는다** |
| 억지로 차이를 만들지 않는다 | 어긋나는 축이 없으면 "둘이 다르다"고 말하지 않고, 정렬 관점의 관찰로 바꾼다 |
| 러비는 아는 척하지 않는다 | `당신은 ~한 사람입니다` · `성공할 확률이 ~` · `심리학적으로 ~` 금지 |
| 같은 결과 = 같은 말 | 러비 문구를 랜덤 생성하지 않는다. 결과에서 결정론적으로 고른다 |
| Premium과 섞지 않는다 | FIRST SURPRISE에 가격·잠금·결제 CTA를 넣지 않는다 |

# 6. 기대효과 및 성공지표

## 6.1 핵심 성공지표

### Primary KPI

> ## **궁합 결과 → Relationship Mirror 진입률**

# 8. 현재 검증 상태

## FACT --- 설문에서 확인

-   관계를 통해 새로운 자신의 모습을 발견한다고 느끼는 사용자가 많음
-   연애 전후 중요 기준이 달라졌다는 응답이 높음
-   반복 패턴 자체를 어느 정도 인지하는 사용자가 많음
-   관계 경험을 구체적으로 정리하지 않은 사용자가 더 많음
-   궁합점수에 높은 관심이 존재함
-   점수 자체보다 점수의 이유·실제 관계 상황·충돌 가능성에 높은 관심
-   '연애할 때의 나' 분석이 서비스 기능 중 가장 높은 이용 의향
-   AI 분석에서는 근거와 솔직함을 중요하게 봄
-   Relationship History 관련 기록·재확인 의향이 존재함

## INTERPRETATION --- 현재 데이터에서 해석

-   사용자의 문제는 '자기 패턴을 전혀 모름'보다 **알고 있는 경험이
    구조적으로 축적되지 않는 것**에 가까울 가능성이 있음
-   궁합은 Acquisition Hook으로 사용하고 Relationship Mirror로 전환하는
    구조가 적합할 가능성이 있음
-   Daily Habit보다 Relationship Event 중심 Retention이 적합할 가능성이
    있음
-   러비의 제3자 관찰자 세계관은 사용자가 원하는 '근거 + 솔직함'과
    연결될 가능성이 있음

## HYPOTHESIS --- 추가 검증 필요

> **관계 경험을 구조적으로 정리·비교하지 못하기 때문에 다음 관계에서
> 자신의 기준을 충분히 활용하기 어렵다.**

설문에서는 '구체적으로 정리하지 않는다'까지 확인했지만, **정리하지 않는
것이 실제 다음 관계의 의사결정 문제로 이어지는 인과는 아직 직접 확인하지
못했다.**

후속 사용자 인터뷰에서 다음을 검증한다.

1.  과거 관계에서 얻은 깨달음을 다음 관계에서 실제로 어떻게 활용하는가
2.  기억만으로 충분한가, 아니면 기준이 다시 흐려지는가
3.  새로운 사람이 생겼을 때 과거 경험을 어떤 방식으로 떠올리는가
4.  Relationship Mirror가 기존 혼자 회고·친구·ChatGPT보다 실제로 더
    유용한가
5.  사진·질문·과거 관계 경험을 제공하는 비용보다 개인화된 분석 가치가
    큰가

## Premium 가치 검증 상태 (v1.19에서 추가) — ₩1,900 Premium 가치 검증 계획

### Problem

Deep Report는 **구현됐지만 지불 가치는 검증되지 않았다.**

v1.9에서 Cross-source Insight Engine과 Relationship Deep Report를 만들었고, v1.15에서
가격 가설을 ₩1,900으로 정하고 Contextual Hook 3개를 배치했다. 그런데 Premium이 안 팔릴 때
그 원인을 구분할 방법이 없었다.

- Premium 자체가 안 궁금한 건가?
- 궁금하지만 1,900원이 비싼 건가?
- 결제 의향은 있었는데 실제 Deep Report가 기대보다 약한 건가?
- 다 보고 나서도 1,900원 낼 가치가 있다고 느끼는가?

이 네 가지를 섞어서 보면 다음 의사결정(가치 강화 / 가격 조정 / PG 구현)을 고를 수 없다.
v1.15까지의 Analytics는 **① Hook 클릭까지만** 관측할 수 있었고 ③④는 아예 물어보지 않았다.

### Hypothesis

> Cross-source Analysis(따로 있던 답변을 연결했을 때만 보이는 신호)가 무료 결과보다
> 추가 가치를 제공하면, 사용자는 ₩1,900의 지불 의향을 보일 것이다.

**NOT VALIDATED.** 이 문장은 검증 대상이지 결론이 아니다.

### Experiment

```
Contextual Hook  →  Paywall  →  Purchase Intent  →  Deep Report  →  Post-view Evaluation
(궁금증)            (기대 가치)   (보기 전 의향)      (실제 소비)      (체감 가치)
```

각 구간을 GA4에서 분리해서 볼 수 있게 `funnel_analysis_id` · `hook_variant` · `source` ·
`price`를 전 구간에 일관되게 붙였다. **새 이벤트는 2개만 추가**했다
(`deep_report_value_rating`, `deep_report_wtp_after_view`) — 나머지는 기존 이벤트의
property만 늘렸다.

### Metrics

| | 지표 | 답하는 질문 |
|---|---|---|
| **Hook CTR** | `premium_entry_click` / `premium_entry_view` (Hook별) | 어떤 궁금증이 실제로 클릭을 만드나 |
| **Intent Rate** | `premium_purchase_intent` / `premium_paywall_view` | Paywall이 설득에 성공하나 |
| **Completion** | `deep_report_complete` / `deep_report_view` | 리포트를 실제로 끝까지 보나 |
| **Incremental Value** | `deep_report_value_rating` 4~5점 비율 | 무료 대비 추가 가치를 느꼈나 |
| **Post-view WTP** | `deep_report_wtp_after_view` = `yes` 비율 | 보고 나서도 낼 의향이 있나 |

### Decision — 결과에 따라 무엇을 바꾸나

| 관측 | 해석 | 다음 행동 |
|---|---|---|
| Hook CTR 낮음 | Premium 자체가 안 궁금하다 | **가치 강화** — Hook 카피·위치. 가격 문제가 아니다 |
| Hook CTR 높음 + Intent Rate 낮음 | 가격 / 상품 설명 / Preview 문제 | **Value Proposition 강화 또는 가격 조정** |
| Intent 높음 + Post-view WTP 낮음 | 기대보다 리포트가 약하다 | **가치 강화** — 콘텐츠. 가격 인하가 아니다 |
| Post-view WTP 높음 | 실제 결제 실험 후보 | **PG 구현 검토** |

> ⚠️ **Purchase Intent가 낮다 = 가격이 비싸다, 로 바로 읽지 않는다.** 이 표가 v1.19가
> 문서에 남기는 가장 중요한 것이다.

### 실제 PG 판단 Gate

다음 버전에서 결제를 붙이려면 아래가 모두 확인돼야 한다.

1. Hook별로 비교 가능한 노출 표본
2. Purchase Intent가 0이 아님
3. 해석 가능한 수준의 Deep Report Completion
4. Post-view WTP 긍정 신호
5. Value Rating 긍정 신호

**구체적 Threshold 숫자는 지금 정하지 않는다.** 초기 데이터 없이 정한 기준선은 근거가 아니라
자의적 숫자다.

# 10. 기획서 v1 핵심 요약

> **문제**\
> 연애 경험이 있는 현재 솔로는 관계를 통해 실제 자신의 연애 기준과 행동
> 특성을 발견하지만, 이를 관계별로 비교·축적하지 않아 다음 관계에서
> 활용할 명확한 자기 기준으로 만들기 어려울 가능성이 있다.

> **해결 방향**\
> 궁합이라는 직관적인 Hook으로 사용자를 진입시키고, 궁합의 이유와 실제
> 관계 경험을 연결해 '내가 생각한 나 vs 실제 관계 속 나'를 보여주는
> Relationship Mirror를 제공한다.

> **차별점**\
> 단순 성향 테스트나 궁합 판정이 아니라 **사용자가 말한 자기인식 + 관찰
> 가능한 일상 데이터 + 실제 관계 경험**을 비교하고 판단 근거를 보여준다.

> **MVP Core**\
> `AI Profile Building → 궁합점수 → 근거/충돌 가능성 → Relationship Mirror`

> **Primary KPI**\
> **궁합 결과 → Relationship Mirror 진입률**

> **Long-term Loop**\
> `궁합 → 자기발견 → 관계 경험 → 변화 발견 → Relationship History → 다음 관계 분석`

> **Brand**\
> 인간의 감정을 학습하기 위해 지구에 내려온 외계인 **러비(Lovy)**가
> 제3자의 시선으로 인간의 관계를 관찰한다.
