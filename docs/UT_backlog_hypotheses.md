## 2. H1 — 전국 퍼센타일 / 유사 사용자 통계

**상태: BLOCKED** (C1·C2·C3 전부 미충족)

UT 발언: `당신과 비슷한 성향은 전국의 몇 %` (참가자 1명 / 1회 언급)

### 2.1 Hypothesis

> 결과 화면에 **같은 세그먼트의 다른 사용자 대비 내 위치**를 보여주면,
> 결과 열람 후 (a) 다음 화면 진입률과 (b) 재방문율이 올라간다.

⚠️ 가설의 주어는 **"퍼센트 숫자"가 아니라 "비교 정보"**다. 숫자 표현(%, 밴드, 문장)은
가설이 참일 때 고르는 **표현 변수**이지 가설 자체가 아니다. 이 구분을 잃으면
"몇 %가 재미있었다"는 감상만 남고 검증이 안 된다.

### 2.2 Why (왜 후보에 올랐는가 / 왜 지금은 아닌가)

**올라온 이유**

- UT 참가자가 스스로 꺼낸 몇 안 되는 **자발적 기능 아이디어**였다.
- 현재 제품에서 가장 약한 가설이 `Relationship Mirror가 새로운 자기이해를 준다`(UT-1 판정: 약함)인데,
  비교 정보는 "이미 아는 내용"이라는 피드백을 정면으로 반박할 수 있는 몇 안 되는 재료다.
- 사주·별자리 Lens가 만든 호기심과 결이 같다(= Premium 가치 가설과 연결 가능).

**지금 만들면 안 되는 이유**

| 이유 | 구체적으로 |
|---|---|
| 모집단이 없다 | C1. 비교할 다른 사용자의 데이터가 **어디에도 저장되지 않는다** |
| 표본 편향 | C2. GA4 동의자만 집계되면 "전국"이 아니라 "동의 버튼을 누른 사람들" |
| 가짜 정밀도 | 표본 수십 명에서 `상위 12%`를 보여주는 것은 **숫자로 하는 거짓말** |
| 민감정보 aggregation | 관계·심리 응답은 민감 범주에 가깝다. 동의·익명화·보관기한 설계 없이 모으면 안 된다 |
| 제품 정체성 | 럽유럽미는 **관계를 해석**하는 서비스이지 사람을 **줄 세우는** 서비스가 아니다. 퍼센타일은 서열 UI로 읽히기 쉽다 |

### 2.3 Required Data

| 필요한 것 | 현재 상태 | 충족 조건 |
|---|---|---|
| 사용자 단위 식별자 | 없음(계정 없음). `funnelAnalysisId`는 상대마다 새로 발급되는 random UUID라 사용자 식별에 못 쓴다 | 익명 pseudonymous id + 그 id의 보관/삭제 정책 |
| 서버 저장소 | 없음(localStorage only) | 집계 전용 저장소. **원본 응답이 아니라 코드화된 값만** 적재 |
| 집계 대상 필드 | axis/level·lifecycle·audience는 이미 코드화돼 있음 ✅ | 자유서술·사진·생년월일 원본은 **영구 제외**(C3) |
| 동의 | 분석 동의(GA4) 하나뿐 | **별도의 '비교 통계 기여 동의'**(아래 D5) |
| 표본 | 0 | 세그먼트 셀당 최소 N(아래 D2) |
| 집계 반환 경로 | 없음 | 제품 화면이 읽을 수 있는 읽기 전용 집계 API |

### 2.4 설계 사양 — 구현 전에 확정해야 할 것

이 절이 이번 작업의 실질적 산출물이다. **아래 8개가 전부 확정되기 전에는 화면을 그리지 않는다.**

#### D1. Population denominator (분모) 정의

- 분모는 `전국 인구`가 **아니다**. 실제 분모는
  **"비교 통계 기여에 동의했고 · 같은 세그먼트에 속하며 · 같은 축을 완료한 사용자 수"**다.
- **카피는 분모를 그대로 말한다.** `전국의 12%` ❌ → `비슷한 상황을 기록한 사용자 <N>명 중` ✅
- 분모는 축(axis)마다 다르다. 축을 건너뛴 사용자는 그 축의 분모에서 빠진다 — 축별 N을 따로 센다.
- 시간 경계를 고정한다(예: 최근 180일 기여분). 무한 누적은 오래된 사용자층으로 분포가 굳는다.

#### D2. Minimum N threshold (표시 임계)

| 구분 | 제안값 | 근거 |
|---|---|---|
| 셀당 최소 표시 N | **≥ 200** | 이 아래에서는 한 명이 들어올 때마다 순위가 눈에 띄게 흔들린다. 확정 전 실제 분포로 재계산 |
| 전체 최소 기여자 | **≥ 1,000** | 세그먼트로 쪼개면 대부분의 셀이 비므로 총량이 훨씬 커야 한다 |
| 재계산 주기 | 최소 24시간 고정 | 실시간 갱신은 차분 공격(D4) 경로를 연다 |

⚠️ 이 값들은 **정밀도 목표에서 역산한 것이 아니라 출발점**이다. 확정 시
"어느 정도 오차까지 허용할 것인가"를 먼저 정하고 그 오차에서 N을 다시 뽑는다.

#### D3. Segment 기준

**허용 축 (이미 코드화된 값만)**

- 관계 lifecycle (알아가는 중 / 현재 관계 / 이전 관계 / 대상 없음)
- audience (`couple` / `solo`)
- 연령대 **10년 단위**(선택 입력, 미입력 허용)
- 성별(선택 입력, 미입력 허용)

**금지 축**

- 자유서술에서 파생된 무엇이든(C3) · 사진 파생 신호 · 생년월일 원본 · 출생시간 · 출생지
- 지역은 **시/도 이상**으로도 넣지 않는다 — "전국"이라는 단어를 정당화하려고 지역을 넣는 순간
  셀이 잘게 쪼개져 D2와 D4를 동시에 깬다.

**교차 한도: 최대 2개 축.** 3개 이상 교차하면 셀이 비고, 빈 셀을 채우려고 임계를 낮추는 압력이 생긴다.

#### D4. k-anonymity / 최소 셀 크기

- 표시되는 모든 셀은 **k ≥ 50**. 미달 셀은 **표시하지 않고**(suppression) 상위 세그먼트로 합치지도 않는다
  (합치면 사용자가 보는 분모와 카피가 어긋난다 — 그냥 D6 cold-start 문구로 간다).
- **차분 공격 방지**: 갱신 주기 고정(D2) + 결과 라운딩 + 동일 사용자의 반복 조회에 같은 스냅샷 제공.
- 개인이 자기 기여를 철회하면 다음 갱신 주기에 셀에서 빠진다. 철회가 셀을 k 미만으로 만들면 그 셀은 표시 중단.

#### D5. Consent

- **2단계 동의.** 기존 분석 동의(GA4)와 **분리한다**. 분석 동의 = 제품 개선용 이벤트,
  비교 통계 기여 동의 = **내 응답이 남의 화면의 분모가 되는 것**. 같은 동의로 묶으면 안 된다.
- 기본값 **off (opt-in)**. 미동의자도 제품은 100% 그대로 쓴다(§15 원칙 유지).
- 미동의자에게 **비교 결과를 보여줄지**를 먼저 정한다. 권장: **보여주지 않는다**
  (기여 없이 열람만 하는 구조는 "왜 나는 분모에 없냐"는 설명을 계속 만들어낸다).
- 철회 UI는 `/privacy` 한 곳에 둔다(현재 consent와 같은 지점). 철회 = 향후 집계 제외 + 기존 기여분 제거.

#### D6. Cold-start UI

숫자가 없을 때 **숫자 자리를 비워두지 않는다.** 3상태로 정의한다.

| 상태 | 조건 | 화면 |
|---|---|---|
| `NOT_COLLECTING` | 기여 동의 안 함 | 비교 영역 자체를 노출하지 않음 |
| `INSUFFICIENT` | 동의했지만 셀 N < D2 | `비슷한 답을 고른 사용자가 충분히 쌓이면 비교해볼 수 있어` (숫자·순위·진행률 바 모두 금지) |
| `AVAILABLE` | 셀 N ≥ D2 && k ≥ D4 | D7 규칙대로 표시 |

⚠️ `INSUFFICIENT`에서 **"현재 87명 / 200명" 같은 진행률을 보여주지 않는다.** 사용자를 모집책으로 만들고,
그 숫자 자체가 셀 크기를 노출해 D4를 깬다.

#### D7. Confidence / 표본 수 표시

- 표시할 때는 **항상** `분모 N` + `기준일`을 같은 화면에 붙인다.
- 1% 단위 금지. **10% 밴드** 또는 사분위 문구(`위쪽 4분의 1 정도`)만 허용.
- "상위/하위" 같은 **서열 어휘 금지** → `~한 쪽이 더 많았어 / 적었어` 같은 분포 어휘.
- 사용자가 분모를 직접 확인할 수 있는 설명 링크를 둔다(무엇을 어떻게 셌는지).

#### D8. 과학적 사실처럼 쓰지 않는 규칙 (가장 중요)

1. 퍼센타일은 **관찰 통계이지 진단이 아니다.** "당신은 ~한 사람"으로 번역 금지.
2. 퍼센타일 값을 **AI 프롬프트에 주입하지 않는다.** 주입하면 AI가 그 숫자를 근거로 서술을 지어낸다.
3. 퍼센타일을 **동기화율/궁합 점수·Lens 판정에 반영하지 않는다.**
   — MBTI를 Supporting Lens로만 쓰고 점수에는 넣지 않는 기존 원칙과 **정확히 같은 처리**다.
4. 퍼센타일에서 **조언·행동 제안을 생성하지 않는다.** 비교는 비교로 끝난다.
5. 근거 문장(`evidence`)으로 인용 금지 — 근거는 사용자 본인의 입력에서만 나온다.

### 2.5 Risk

| 위험 | 설명 | 완화 |
|---|---|---|
| 가짜 정밀도 | 작은 표본의 %가 사실처럼 읽힘 | D2 · D7(밴드 표시) |
| 표본 편향 | 동의자·초기 사용자층에 쏠림 | D1(분모 그대로 말하기) · "전국" 표현 영구 폐기 |
| 재식별 | 소수 세그먼트 + 반복 조회 | D3(교차 2축) · D4(k≥50, 라운딩, 고정 스냅샷) |
| 동의/규제 | 관계·심리 응답의 민감성 | D5(2단계 opt-in) · 외부 검토(V4) |
| 제품 정체성 훼손 | 해석 서비스 → 서열 서비스로 읽힘 | D7(서열 어휘 금지) · D8 |
| 운영 부담 | 집계 파이프라인·삭제 요청 처리 상시 비용 | 가치 검증(V1~V3) 전에는 착수 금지 |

### 2.6 Validation Method (코드 없이 순서대로)

| # | 방법 | 무엇을 보나 | 성공 라인(제안) | 실패 시 |
|---|---|---|---|---|

## 3. H2 — 여러 Target 누적 → '나는 어떤 사람인가'

**상태: BLOCKED** (C4 데이터 모델 · P0 Target 저장 안정화 선행)

### 3.1 Hypothesis

> 서로 다른 관계 **3건 이상**에서 반복해서 나타난 신호를 모아 보여주면,
> 사용자는 그것을 "이미 아는 내용"이 아니라 **새로 알게 된 자기 패턴**으로 받아들인다.

이 가설은 UT-1에서 **약하다고 판정된** `Relationship Mirror가 새로운 자기이해를 준다`의
직접적인 후속이다. 단일 관계에서 못 준 것을 **시간축과 관계 수**로 줄 수 있는가를 묻는다.

### 3.2 Why (지금은 아닌 이유)

- **C4**: History는 self signal snapshot만 저장하고 상대 identity를 남기지 않는다. 이건 버그가 아니라 설계다
  ("History는 누구와 몇 번 만났는지를 남기는 곳이 아니다"). Target별 분리는 **이 설계를 건드리는 결정**이다.
- **P0 선행**: Target 저장/선택이 단일 source-of-truth로 안정화되기 전에 누적을 쌓으면
  **잘못 섞인 데이터 위에 해석을 올리게 된다**. 되돌리기가 가장 어려운 종류의 부채다.
- **표본**: 현재 History에 3건 이상 쌓인 실제 사용자가 **없다**. 가치 검증을 할 데이터 자체가 없다.

### 3.3 Required Data

| 필요한 것 | 현재 상태 | 충족 조건 |
|---|---|---|
| 관찰 3건 이상 | 실사용 데이터 0 | UT-2 이후 재방문 사용자 확보 또는 fixture 시뮬레이션 |
| 관찰 간 구분 키 | `analysisId`(deterministic fingerprint) 존재 ✅ | **이걸 그대로 쓴다.** 상대 이름·identity 추가 저장은 하지 않는 안(A)을 기본으로 |
| 관계 맥락 | lifecycle·audience 저장됨 ✅ | 맥락이 다르면 합산하지 않는 규칙(R2) |
| 반복 임계 | `SOLO_REPEAT_MIN_OBSERVATIONS = 3` ✅ | **재사용**. 새 임계값을 만들지 않는다(C5) |

**선택지 A/B**

- **A (권장)**: identity를 저장하지 않고 `analysisId` 단위로만 구분. 개인정보 증가 0. 대신 사용자가
  "이건 누구였지"를 스스로 알아볼 수 없다 → 화면에서 상대를 특정하지 않는 카피가 필요.
- **B**: 사용자가 붙인 라벨(별칭)을 저장. 알아보기 쉬워지지만 **관계 이력 데이터베이스**가 되고,
  기기 분실·공유 시 위험이 커진다. 채택하려면 삭제·잠금 UX를 함께 설계해야 한다.

### 3.4 설계 규칙 (구현 시 반드시 지킬 것)

| # | 규칙 |
|---|---|
| **R1** | 최소 관찰 수 = **서로 다른 `analysisId` 3건**. `SOLO_REPEAT_MIN_OBSERVATIONS`와 **하나의 상수를 공유**한다 |
| **R2** | **맥락 분리**: lifecycle(알아가는 중 / 현재 / 이전)과 audience(couple/solo)가 다르면 같은 축이라도 **합산하지 않는다**. 섞으면 "연애 중의 나"와 "혼자일 때의 나"가 한 문장이 된다 |
| **R3** | **일반화 금지**: 주어는 사람이 아니라 관찰이다. `너는 거리를 두는 사람이야` ❌ → `3번의 관찰 중 2번, 가까워질수록 혼자 있는 시간을 찾는 장면이 있었어` ✅ (기존 soloHistory 문구 규칙 재사용) |
| **R4** | **`stable` / `repeated` 표현 기준을 분리**한다 (아래 표) |
| **R5** | **반증도 같이 보여준다.** 반복된 신호만 골라 보여주면 체리피킹이다. 달라진 관찰이 있으면 같은 화면에 표시 |
| **R6** | 기존 History에 파괴적 migration 금지(C6). 필드가 없는 과거 기록은 `INSUFFICIENT`로 읽고 다시 쓰지 않는다 |
| **R7** | 단일 관계만 있는 사용자에게 이 화면을 **노출하지 않는다**(빈 상태 티저 금지 — 사용자가 관계를 늘려야 한다는 압박으로 읽힌다) |

**R4 — 표현 기준**

| 판정 | 조건(제안) | 허용 어휘 |
|---|---|---|
| `INSUFFICIENT` | 같은 맥락의 관찰 < 3 | 판정 문장 없음. "아직 비교할 기록이 부족해" |
| `repeated` | 3건 중 **2건 이상**에서 같은 axis+level | `여러 번 나타났어` |
| `stable` | **3건 연속** 같은 axis+level | `계속 같았어` |
| `changed` | 최신 관찰이 이전과 다름 | `이번엔 달랐어` (R5에 따라 항상 함께 표시) |

### 3.5 Risk

| 위험 | 설명 | 완화 |
|---|---|---|
| 잘못된 일반화 | 관계 3건 = 인간 성향이 아니다 | R3 · R1 |
| 맥락 오염 | 연애/솔로/과거 관계를 한 문장으로 요약 | R2 |
| 체리피킹 | 반복만 보여주면 "역시 나는 그렇구나" 확증편향 | R5 |
| 데이터 모델 부채 | P0 Target 저장이 불안정한 상태에서 누적 | P0 완료를 게이트로 |
| 개인정보 증가 | 선택지 B 채택 시 관계 이력 DB화 | 기본은 A |
| 감정적 위해 | 과거 관계를 반복 노출 | ENDED lifecycle 규칙 재사용 · 접근/재회 유도 문구 금지 |

### 3.6 Validation Method

| # | 방법 | 성공 라인(제안) |
|---|---|---|
| **V1** | **Fixture 시뮬레이션** — 서로 다른 3~4건의 관찰을 합성해 R1~R5로 리포트를 만들어 본다(화면 없이 텍스트로) | 만들어진 문장이 R3를 **한 번도** 위반하지 않음 |
| **V2** | **Wizard-of-Oz** — V1 산출 텍스트를 UT-2 참가자에게 보여주고 "이게 당신에 대한 설명으로 맞느냐"를 묻는다 | 5명 중 3명 이상이 "새로 알게 된 것"이라고 답함 |
| **V3** | **재방문 데이터 관측** — History 2건 이상 보유 사용자 비율을 먼저 확인 | 기능을 만들 만한 모수가 실제로 생기는지 확인 |

### 3.7 Implement Gate (전부 AND)

- [ ] P0 (Target 단일 source-of-truth · 재진입 유지 · New Target 누수 0) **완료 및 QA 통과**
- [ ] R1~R7 확정, 특히 **R1이 `SOLO_REPEAT_MIN_OBSERVATIONS`를 재사용**하는 형태로 설계됨
- [ ] 선택지 A/B 결정 (B 선택 시 삭제·잠금 UX 동반 설계)
- [ ] V1 통과 (fixture 문장이 R3 위반 0)
- [ ] V2 통과 (UT-2)
- [ ] V3에서 History 2건 이상 사용자가 실제로 관측됨

## 4. H3 — 친구끼리 결과 공유

**상태: REJECTED — 구현하지 않는다.**

### 4.1 판단

UT-1 참가자는 **서비스 자체는 친구에게 추천할 수 있다**고 했지만
**서로의 분석 결과를 직접 보는 기능은 원하지 않는다**고 명확히 말했다.
`타인의 결과를 서로 공유하고 싶다` 가설은 UT-1에서 **부정**으로 판정됐다.

### 4.2 이 문서에 남기는 이유

지우면 다음 사이클에 **같은 아이디어가 새 아이디어인 척 다시 올라온다.**
"검토했고, 사용자 신호는 부정이었다"는 기록 자체가 산출물이다.

### 4.3 이미 충분한 것

서비스 추천 경로는 기존 `share_card_open` / `share_card_action`으로 이미 존재한다.
필요한 것은 **결과 상호 열람**이 아니라 **서비스 링크 공유**였고, 그건 이미 있다.

### 4.4 재개 조건 (이것 말고는 재검토하지 않는다)

- [ ] 서로 다른 UT에서 **참가자 과반**이 상호 열람을 **자발적으로** 요청
- [ ] 양방향 동의 모델(초대 · 수락 · 언제든 철회 · 철회 시 즉시 열람 중단) 설계 완료
- [ ] 상대가 **자기 데이터가 아닌 것**(내가 입력한 상대 정보)을 보게 되는 문제의 해법 제시

> ⚠️ 세 번째 항목이 핵심이다. 럽유럽미의 분석 대상은 **내가 관찰한 상대**이고,
> 그 관찰을 상대 본인에게 보여주는 것은 공유가 아니라 **관계 사고**다.
